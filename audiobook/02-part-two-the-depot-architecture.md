# Part Two: The Depot Architecture

## Chapter 3: The Main Agent Depot

Every agent defined in Agent-o-rama has its own dedicated depot. Not a shared channel, not a topic where all agents compete for attention — a depot belonging entirely to that agent, carrying every event that drives its execution from first invocation to final result. Think of it as the central nervous system of that agent's runtime life. Every heartbeat of an agent execution passes through this depot: the initial call, the news of each completed node, the signals to retry, the commands to fork. If you want to understand what has happened and is currently happening to an agent execution, this depot is where the record lives.

The depot does not use a standard hash partitioner. Instead, the Agent-o-rama team defined a custom partitioner that shapes how events are routed across the cluster. The logic is deliberate: if an event carries an explicit target task identifier, the partitioner sends that event directly to that task. If no task identifier is present, the event goes to a randomly selected task. This two-path routing is not an accident — it is the mechanism that makes co-location possible.

To understand why co-location matters, consider what happens at the start of an execution. An AgentInitiate event arrives at the depot without a target task identifier, so the partitioner selects a task at random. Let's say that task is task seventeen. The stream topology running on task seventeen processes the event and creates the execution's root records in its local PStates. From this point forward, every subsequent event that belongs to this execution will carry task seventeen as its target. Node completions carry it. Failure notifications carry it. Retry signals carry it. This embedded task identifier is what keeps the entire execution co-located — every event routes back to the same task, which means every read and write during the hot path of execution touches state that lives on that same task, without any network hop. The custom partitioner is the implementation of that guarantee.

The main agent depot carries five principal event types, and understanding each one is essential to understanding how execution actually works.

The first is AgentInitiate. This is the event that starts everything. When a client calls an agent, it appends an AgentInitiate to this depot. The event carries the invocation arguments, the execution metadata, the source identity of the caller, and optionally a forced task identifier or a forced agent identifier — both of which are used by the system when it needs precise control over placement, as in forking or in testing scenarios. Absent those forced values, the partitioner selects a task at random. The stream topology processes AgentInitiate by creating the root execution record, assigning a unique agent identifier, and scheduling the first node for execution.

The second event type is NodeComplete. This is the most frequent event in the system — every time a node finishes executing, a NodeComplete is what carries the news. The event contains the unique invoke identifier of the node that finished, the task it ran on, the retry number of the execution it belongs to, and the return value of the node function itself. It also carries the full list of emits the node declared: each emit specifies the target node name, the task that target node should run on, a freshly generated invoke identifier for the child, and the arguments to pass along. On top of that, NodeComplete carries any streaming information the node produced, and the complete list of nested operations recorded during execution — every model call, every store read, every tool invocation, every subagent call, each one captured as a structured entry with timing and outcome. The stream topology unpacks all of this and uses it to update the execution's state: recording what happened, creating new entries for the child nodes declared by the emits, and routing those child nodes off to their target tasks for execution.

The third event type is NodeFailure. When a node raises an exception, rather than completing, the node executor packages the exception and context into a NodeFailure event and appends it to the depot. The stream topology processes this by triggering the retry machinery: checking how many retries have occurred, deciding whether to retry the node or to escalate to an agent-level retry, and taking the appropriate action.

The fourth event type is RetryAgentInvoke. This is a synthetic event — it is not produced by a node, but by the stall detection system. The stall detector fires periodically and scans active executions looking for any that appear stuck: executions that have been running for longer than the configured threshold without producing a NodeComplete. When it finds one, it appends a RetryAgentInvoke to the main agent depot. This event carries the agent task identifier, the agent identifier, and the expected retry number. When the stream topology processes it, the execution is reset: the root PState entry is reinitialized, the retry count increments, and the first node is scheduled again from scratch. The retry number embedded in the event also serves as a fencing mechanism — any events from the previous stalled execution that are still in flight in the depot will arrive with the old retry number, and the stream topology's first step on every event is to verify the retry number is still current.

The fifth event type is ForkAgentInvoke. This event starts a new forked execution derived from an existing one. It carries the original execution's agent task identifier and agent identifier, along with a map from the original execution's node invoke identifiers to new argument lists. The fork feature is how the web UI's fork-and-replay capability works: you take a completed execution, modify some inputs, and replay it — the system creates a new execution that reuses cached results for the unchanged portions of the graph and re-executes only the affected parts. ForkAgentInvoke is also the mechanism behind experiments that compare different argument configurations against the same agent definition.

There is something important to understand about the role this depot plays beyond mere transport. A transport mechanism carries data from one place to another and then forgets it. This depot is not that. Because it is a Rama depot — an append-only log with durable storage — the record of every event is preserved. The fact that events are durable and ordered is what gives the execution model its reliability guarantees. When a machine fails mid-execution, Rama's fault recovery mechanism replays unprocessed events from the log onto a replacement machine. The execution does not need to know this happened; it simply continues processing events from where it left off. When the stall detector needs to assess whether an execution is stuck, it can consult the state derived from the event log. When a fork needs to replay a previous execution's graph, the node PState populated by NodeComplete events is the record it reads from. The depot is not a channel — it is the source of truth for what happened and when.

## Chapter 4: The Supporting Depots

The main agent depot handles execution. But execution is not the only concern an agent system has to manage. Streaming output, human input, configuration changes, garbage collection, analytics, global shared state, and safe writes to user-defined stores — each of these is a distinct concern, and each has its own depot. Understanding the supporting depots means understanding how Agent-o-rama divides its responsibilities and why each division was drawn where it was.

The streaming depot carries NodeStreamingResult events. Each event contains a chunk of data, the agent task identifier, the agent identifier, the node name, the invoke identifier of the specific node invocation that produced the chunk, a monotonically increasing index number, and the retry number. The retry number matters here for the same reason it matters in the main depot — if a node fails and restarts, streaming chunks from the failed attempt need to be discardable. The index number is what allows chunks to be reassembled in the correct order even if they arrive slightly out of sequence. The partitioning strategy for the streaming depot routes events by agent task identifier, which means streaming data always lands on the same task as the agent execution that produced it. This co-location is intentional: the stream topology handler for streaming events updates the root PState's streaming buffer, and having the streaming data arrive on the task that owns the root PState keeps that write task-local. The more architecturally significant decision, though, is the existence of a separate streaming depot at all. Streaming chunks can be large, and they arrive frequently. If they traveled through the main agent depot, they would share space and processing time with the NodeComplete events that are critical to execution progress. Isolating streaming to its own depot keeps the hot path of execution clear and uncontested.

The human input depot carries two event types that work in tandem. When a node pauses to wait for human input, a NodeHumanInputRequest event is appended to this depot, carrying the agent task identifier, the agent identifier, the node name, the specific invoke identifier of the waiting node, the task that node is running on, and the prompt string the human needs to answer. When a human provides a response — through the web UI or through the client API — a HumanInput event is appended to the same depot, carrying the original request record and the response string. The partitioner for this depot routes NodeHumanInputRequest events by agent task identifier and routes HumanInput events by the task identifier of the node that originally requested the input. This distinction reflects what co-location means for each type: the request must arrive where the agent execution lives, but the response must arrive where the waiting node lives, which may be a different task if the execution has spread across the cluster.

The config depot carries ChangeConfig events for per-agent settings. The most prominent example is the maximum retry count, which operators can adjust through the web UI without redeploying the module. Config changes are rare — they happen on human timescales, not execution timescales — and they do not need to be co-located with any particular execution. So the config depot uses random partitioning. Every task that processes the stream topology will receive and apply config updates, keeping all tasks consistent over time, without any requirement that a config event land on a specific task.

There are two time-driven depots, each firing on a schedule. The check-tick depot fires periodically — by default every several seconds — and drives the stall detection system. When a tick fires, the stall-detection microbatch topology wakes up and scans the set of active agent executions, checking each one for signs of progress. The GC tick depot fires on a slower schedule and drives garbage collection of completed executions. Completed executions remain in the PStates until the GC mechanism cleans them up according to the configured retention policy. The two separate tick depots reflect the fact that these two concerns operate at different time granularities and have different cost profiles: stall detection needs to fire frequently enough to catch stuck executions before they hold resources for too long, while garbage collection can afford to run less often.

The PState write depot handles all writes to user-defined stores: key-value stores, document stores, and PState stores. When a node running inside a topology writes to a store, that write does not go directly to the backing PState. Instead, it is recorded as a PStateWrite event and appended to this depot. Each event carries the store name, the path expression describing what to write, the value to write, and the agent source context — which includes the agent task identifier, agent identifier, and retry number. The partitioner routes writes by key, using a hash partitioner that sends each write to the task owning the relevant partition of the backing PState. This indirection exists to provide retry safety. Because the write is an event in a depot, the stream topology that processes it can check the retry number before applying the write. If the agent has since been retried and the write is from a now-stale execution, the topology simply discards it. Without this indirection, a write from a failed execution that happened to complete successfully before the failure occurred could be applied again during the retry, potentially creating inconsistent state. The depot ensures the write happens exactly once, attributable to exactly the right execution generation.

The analytics tick depot fires periodically and wakes up the analytics microbatch topology, which is responsible for rule evaluation and telemetry aggregation. When the tick fires, the analytics topology scans recently completed invocations from a cursor position, evaluates configured rules against them, applies actions for matching runs, and accumulates metric values into the telemetry PState.

The global actions depot carries mutations to shared global state — the additions and removals of rules, evaluators, human metrics, feedback queue configurations, datasets, experiment configurations, and similar cross-cutting concerns. These events are processed by the analytics microbatch topology rather than by the per-agent stream topology, because they affect global state that all agents share rather than the state of any individual execution. Random partitioning is used here, consistent with the same reasoning applied to the config depot: global actions are infrequent and do not need to be co-located with any specific task's execution state.

Taken together, these depots form a deliberate division of concerns. The main agent depot owns the execution lifecycle. The streaming depot owns output delivery. The human input depot owns the pause-and-resume lifecycle of human interaction. The config depot owns operator settings. The tick depots own time-driven maintenance. The PState write depot owns safe mutation of user-defined state. The global actions depot owns mutations to the module's shared configuration. Each depot has its own partitioning strategy, and each strategy reflects what co-location means for that specific class of events. Where events need to land on the same task as an execution, the partitioner carries a task identifier. Where events are global or infrequent, the partitioner uses random distribution. The sum of these choices is a system where the hot path of agent execution is isolated, protected, and fast, while auxiliary concerns run on separate rails without interfering.
