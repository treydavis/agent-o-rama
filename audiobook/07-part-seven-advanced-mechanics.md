# Part Seven: Advanced Mechanics

## Chapter 19: Module Updates and the Graph Version System

One of the harder problems in any long-running distributed system is what happens to in-flight work when you deploy new code. In a web server, the answer is simple: requests are short-lived, so you wait for active requests to drain and then restart the process with the new version. In a batch job, the answer is also manageable: jobs run to completion before you redeploy, or you restart the job from scratch with the new code. But in an agent system, "in-flight work" has a different character entirely. An agent execution may span minutes, hours, or longer. It may be suspended, waiting for a human to respond. It may be executing a deep fan-out of parallel branches, each waiting on a language model. These executions did not just start — they are partway through their graphs, with some nodes already completed and their results recorded, with downstream nodes queued and waiting for results that have not yet arrived. Telling users they cannot deploy updates until all active executions complete is not a viable answer. Agent-o-rama's solution to this problem is the graph version system.

The core idea is straightforward even though the implementation has subtleties. Every time an agent's node definitions change, the system assigns a new version number to that agent's graph definition. This version number is not merely a deployment label — it has operational significance at runtime. When an update arrives and the graph version increments, every active execution in the system has a record of which version governs it. That record lives in the root PState entry for the execution, stored alongside the agent-id, the arguments, and the timing information we have discussed in earlier chapters. The execution's graph version is the lens through which all subsequent processing must be interpreted.

The stream topology enforces three update modes, each representing a different answer to the question of how a particular update should interact with executions already in progress. The first mode is Continue. When the topology processes a node event for an execution, it checks the graph version stored in that execution's root PState entry against the current version of the agent graph. If the versions differ, the topology applies new node definitions to the remaining unexecuted work. Any nodes that have already run keep their results — those are committed, immutable entries in the node PState, and they do not change. But any emit records from those completed nodes that have not yet spawned their downstream child nodes, and any nodes already scheduled but not yet executed, will be processed using the new code. This is the lowest-disruption mode. The execution does not restart. It simply transitions to the new code as it encounters fresh work. An execution that is sixty percent complete when you deploy an update will finish its remaining forty percent under the new definitions, while the already-completed sixty percent remains unchanged.

The second mode is Restart. When the topology detects a version mismatch in Restart mode, it sends the execution a RetryAgentInvoke event carrying the new graph version. This causes the execution to begin again from the start — the initial AgentInitiate event is replayed, a fresh root PState entry is created with the new graph version, and the execution proceeds as if it had never started. The node PState entries from the old attempt are still present and correctly labeled with their retry generation, but the retry filter we examined in Chapter Nine ensures they no longer affect the new attempt. Restart mode is appropriate when the changes between graph versions are substantial enough that old and new code are genuinely incompatible. If a node's output shape changes, or if the graph's structure changes such that the sequence of nodes in the old version corresponds to a different sequence in the new version, trying to splice new code into a half-completed old execution could produce incoherent results. Restart avoids the incoherence by starting fresh.

The third mode is Drop. In Drop mode, when the topology detects a version mismatch, the execution is simply removed from the active-invokes set and its results are discarded. No retry, no continuation, no record of a result. Drop is forceful. It is appropriate for cases where the update reflects such a fundamental change that completing the old execution — in any form — is not meaningful. If the agent's purpose has been redefined, if the output format has changed in a way that would confuse downstream consumers, or if correctness requires that all results be produced by the same version of the code, Drop is the right answer.

The history of which graph versions have existed is stored in the shared PState, keyed by version number. Old versions are not deleted when a new version is deployed. They are retained as long as there are active executions still using them. This is necessary because Continue mode, in particular, may need to examine an older version to determine which nodes were already completed under that version. Once all active executions have either finished, restarted, or been dropped, the old version's entry in the shared PState becomes eligible for garbage collection.

The subtlety of Continue mode deserves more attention, because it is not just a matter of running new code on future nodes. It is running new code against execution state that was produced by old code. The node functions may have different signatures. They may emit to different downstream targets. They may produce outputs in a different format than the old code expected its consumers to receive. Continue mode is safe only when the developer has designed the update to be backward-compatible with in-flight state. This is the same challenge that database schema migrations face — changing a live system without invalidating existing data — and it requires the same discipline. The system supports Continue mode because there are genuine cases where updates are backward-compatible, and the smooth continuation of in-flight executions is worth preserving in those cases. But the system cannot verify backward compatibility for you. That judgment belongs to the developer.

This brings us to the deeper observation that the graph version system depends on. Making deployment non-disruptive to in-flight executions requires the system to know, in precise detail, what state those executions are in. Which nodes have completed. Which emits have been processed. Which downstream nodes are scheduled. This is exactly what the root PState and node PState record. The event-sourced design that we established in Part One — the design that stores every completion and every emit as durable, committed state — turns out to be a prerequisite for this feature. A system that tracked execution progress only in memory, or only in the stream topology's own local state, could not offer any of these three update modes. It would have no reliable picture of in-flight executions from which to reason about how to handle an update. The graph version system is one more downstream benefit of the event-sourced design, which keeps revealing new consequences as the system's requirements grow more sophisticated.

## Chapter 20: Forking — How the UI's Fork Feature Works

The web UI includes a feature that, once you understand it, becomes one of the most useful tools for iterative development and debugging. It is called forking. Forking lets you take any completed execution, modify its inputs or metadata, and run it again. Not just by submitting a new invocation with different arguments — that is trivially possible with any agent system. Forking is more specific and more powerful than that. It lets you re-run only the parts of the execution that would be affected by your changes, replaying the unchanged parts from cache rather than re-executing them. If your agent has an expensive first stage that retrieves and processes a large corpus of documents, and you want to change only the final synthesis step, forking lets you run the modified synthesis step without paying the cost of the retrieval step again.

A fork begins with a ForkAgentInvoke event appended to the main agent depot. This event carries the original execution's agent-id, the modified arguments or metadata that represent the change you want to explore, and a fork context. The fork context is the heart of the mechanism — it describes which specific nodes in the original execution should be re-executed with the new inputs and which should be replayed from the original's cached results. The stream topology's fork handler receives this event and begins constructing the forked execution. It creates a new root PState entry with a fresh agent-id, so the fork is a distinct execution with its own identity and its own result. It stores the fork context alongside the standard execution metadata. Then it replays the original execution's graph up to the fork point by reading the node PState entries of the original execution and re-creating them in the fork's namespace.

The determination of which nodes are affected is called the fork-affected nodes calculation, and it is not as simple as identifying the nodes whose immediate inputs changed. In an agent graph, nodes can have complex dependency relationships. If you change the input to node A, and node A's output feeds into node B, and node B's output feeds into an aggregation that also receives input from nodes C and D, then the fork needs to re-execute A and B at minimum, and may need to re-examine the aggregation as well. The topology works through the graph structure, identifying which aggregation boundaries are downstream of the changed inputs and tracing the consequences forward. Only the affected portions of the graph are re-executed. Nodes upstream of the fork point that produced unchanged outputs are replayed from the cached results in the original execution's node PState.

To see how this plays out in practice, consider an agent that has three stages. The first stage calls a retrieval tool to fetch relevant documents from a knowledge base. The second stage runs those documents through a scoring model to rank them by relevance. The third stage synthesizes the top-ranked documents into a final answer using a language model. You ran this agent, examined the results, and decided that the prompt for the synthesis stage needs adjustment. That change affects only the third stage. When you submit a fork with the modified prompt, the fork-affected nodes calculation determines that the first and second stages are upstream of the change and their outputs are unchanged. Those stages are replayed from cache — their node PState entries are copied into the fork's namespace, effectively telling the stream topology that those nodes already completed with known results. Only the third stage is re-executed. The cost of the fork is the cost of one model call for synthesis, not three stages of work. If the retrieval call was expensive or the scoring model was slow, the savings are substantial.

The fork context that is constructed from this analysis is a precise specification: these invoke-ids from the original execution are to be replayed from cache, and these invoke-ids are to be re-executed from scratch. The fork context is stored in the new execution's root PState entry so that the stream topology can consult it as it processes each node. When the topology encounters a node that the fork context marks for replay, it copies the original node PState entry rather than scheduling a NodeOp. When it encounters a node marked for re-execution, it schedules a NodeOp as it would for any normal execution. The two paths converge on the same topology logic for handling the downstream consequences of each node's completion, whether the completion came from real execution or from replay.

Replaying from cache is worth explaining precisely, because it is doing something that sounds trivial but is architecturally significant. Instead of running the node function again and waiting for new results, the system copies the output records from the original execution's node PState entry into the forked execution's node PState entry, under the forked execution's agent-id and invoke-ids. From the perspective of the stream topology processing the fork, these entries are indistinguishable from freshly computed results. The topology sees a node PState entry with a completed status, an emit list, a nested ops record, and timing information, and it processes it exactly as it would process a NodeComplete event from a real execution. The node, in every sense the topology can observe, ran instantaneously. The performance benefit is that the underlying work — the model calls, the store reads, the expensive external operations — does not happen again. The correctness property is that the topology does not need a special path for replay; it treats replayed results identically to real results.

The ack-val requires careful handling when a fork changes which branches of an aggregation are executed. When a fork re-executes some children of an aggregation but replays others from cache, the initial ack-val for that aggregation in the fork cannot be the same as in the original execution. It must be calculated to reflect only the branches that are being re-run. A query topology computes the adjusted ack-val before the fork execution begins. This adjusted value accounts for the contributions that will be replayed — they are effectively pre-loaded into the ack-val in their completed state — so that the aggregation end node fires correctly when only the re-run branches have reported back. The XOR properties we examined in Chapter Twelve make this pre-loading straightforward: to pre-load a replayed branch's contribution in its completed state is simply to not include that contribution in the initial ack-val at all.

It is worth pausing to appreciate why forking is a first-class feature rather than an afterthought, and why it would be difficult to add to a system that was not designed for it. The node PState already records everything needed to replay an execution. Every input the node received, every output it produced, every emit it declared, every nested operation it performed — all of it is in the node PState, committed durably, identified by a stable invoke-id. Forking is the natural consequence of having a complete execution record. The infrastructure that was built to provide observability — to let you examine any execution in the trace page and understand exactly what happened — turns out to also be the infrastructure that enables replayability. The two features are not independent. The design that makes an execution fully inspectable also makes it fully replayable. This is a pattern worth recognizing: in systems built on event sourcing and explicit state recording, observability and reproducibility tend to come together as a pair.

## Chapter 21: The Query Topology Layer — Serving the UI and Clients

Everything we have examined so far has been push-driven. Events arrive at depots, stream topologies process them, PStates are updated. The system reacts to inputs. But clients — whether the web UI browsing executions or a program waiting on a result — need to pull information out of the system. They need to ask questions and receive answers. This is the role of query topologies. Query topologies provide the synchronous read path, and they are the layer through which all external consumers interact with the system's accumulated state.

A query topology is a named procedure that accepts arguments, reads from one or more PStates using path expressions, and returns a result. It is not a stream processor. It does not run continuously. It runs when called, completes when it has assembled a result, and returns. From the caller's perspective, it behaves like a remote function call.

The trace page query is the most structurally complex of the query topologies. Given an agent-id, it traverses the node PState starting from the root invoke-id for that execution. It follows the emit chains recorded in each node's entry, expanding children depth-first, reconstructing the execution tree in memory as it reads. The result is a hierarchical structure of nodes with their timing, nested ops, and status — the data that the trace page renders as a visual execution tree. The query does not compute this structure; it reads a structure that was written incrementally by the stream topology as the execution progressed. Each NodeComplete event that was processed wrote another piece of the puzzle into the node PState, and the trace page query assembles those pieces on demand.

The invocations list query is a paginated scan of the root PState, returning summaries of recent or matching executions. It supports filtering by metadata, time range, and completion status. Metadata-based filtering is efficient because the shared PState maintains a metadata index — an additional index structure, written by the stream topology at execution start, that maps metadata keys and values to sets of agent-ids. The invocations list query reads this index first to identify matching executions, then fetches the corresponding root PState entries. Without this index, metadata filtering would require a full scan of the root PState, which would be prohibitively slow as the number of executions grows.

The current graph query returns the current agent graph definition: node names, edges, configuration, and the current version number. It reads from the latest entry in the shared history PState. This is the query the web UI uses to render the graph visualization, and it is also used internally by the fork-affected nodes calculation to understand the structure of the graph at the time of a fork.

The dataset and evaluator queries support the evaluation infrastructure. They search the global datasets PState by name, description, or tag and return paginated results. These queries are structurally simpler than the execution queries — the datasets PState is organized for retrieval by these fields, and the queries are direct lookups into that organization. The experiment results query is more computationally involved: it aggregates per-invocation scores stored in the datasets PState into summary statistics — average scores, latency distributions, comparisons across evaluation targets. This aggregation happens at query time, reading the individual result records and computing the statistics in the query topology itself.

The client API's blocking result method deserves particular attention because it illustrates a capability that is not commonly available in distributed systems. When a client calls this method, it is asking to receive the result of an execution that may not yet be complete. Under the hood, this is implemented as a foreign proxy on the root PState's result field. In Rama, a foreign proxy is a mechanism for reading a PState field reactively: the proxy does not poll for the field to change, and it does not impose a timeout that requires a retry. It simply parks the calling thread until the field transitions from null to a non-null value, then returns the value. The stream topology writes to the result field when it processes an execution's final completion. The moment that write commits, the proxy unblocks and the value is returned to the client. No polling, no exponential backoff, no coordination protocol between the client and the system. The liveness guarantee comes from Rama's foreign proxy mechanism, and the only condition under which the call does not eventually return is the condition under which the execution itself never completes.

The performance characteristic of query topologies follows from the same co-location principle that governs everything else in the system. Query topologies run on the Rama task that owns the relevant PState partition. A trace page query for an execution whose node PState is partitioned to task seven runs on task seven. The reads are local to that task. There is no query planner, no optimizer, no temporary materialization of intermediate results. There are direct reads from co-located state, assembled according to the logic of the query procedure, and returned. This is fast not because any particular implementation trick is employed, but because the architecture ensures the data is where the computation is.

This is also the right moment to contrast query topologies with the stream and microbatch topologies we examined earlier. Stream and microbatch topologies are push-driven: events arrive and processing happens in response. Query topologies are pull-driven: a client asks and the system reads. They represent fundamentally different computation models, and the distinction is not merely academic. Push-driven topologies have guaranteed execution ordering, retry semantics, and exactly-once processing guarantees enforced by the Rama platform. Pull-driven query topologies have none of these properties by default — they run once, return a result, and do not have retry guarantees in the same sense. But they share the same state store. A stream topology writes execution records, and a query topology reads them. The two models coexist because the system's needs are genuinely different in the two directions: durable, ordered, exactly-once processing on the write side, and low-latency, synchronous reads on the query side.

## Chapter 22: Cross-Module Communication — Mirror Depots and PStates

Agent-o-rama is a multi-module system. A module is the unit of deployment in Rama — a self-contained package of depots, PStates, and topologies that is deployed to a cluster and runs as an independent service. Agent-o-rama itself is organized into multiple modules, and the agents it manages can span module boundaries. An agent defined in one module can call an agent defined in another module as a subagent. At the application level, this looks no different from calling a subagent within the same module. Under the surface, the mechanism is different, and understanding it reveals something important about how Rama composes distributed systems.

When two components exist in the same module, their interactions are straightforward. An event appended to a depot in module A is processed by a topology in module A. A PState written by module A's topology is readable by any query topology in module A. Everything is co-located by definition. Cross-module interaction breaks this assumption. If module A wants to append to a depot owned by module B, the append must cross a module boundary — which in a distributed system means crossing a network boundary.

Rama's mirror mechanism is the answer to this challenge. A module can declare a mirror of another module's depot or PState. The mirror is a local structure that the Rama platform keeps up to date with the source. Reads from a mirror are task-local and do not require network calls to the source module. The platform handles the replication. From the perspective of code running in the mirroring module, a mirror looks and behaves like a locally owned resource.

Mirror depots work in the outbound direction. When a node function in module A wants to append an event to a depot owned by module B, it uses a mirror depot declaration. The append goes to the local mirror first, and the Rama platform takes responsibility for routing it to the source module asynchronously. The node function does not need to know that module B exists, where module B is deployed, or which tasks module B runs on. It appends to the mirror, and the platform handles the rest. The delivery semantics — durability, ordering, exactly-once guarantees — are preserved across the module boundary.

Mirror PStates work in the inbound direction. When a node function in module A wants to read a PState owned by module B, it uses a read-only mirror. The platform replicates the relevant partitions of module B's PState into module A's task structure. Reads from this mirror are local reads — no network hop, no coordination with module B. The mirror is updated by the platform as module B's topology writes to the original PState. The replication is not instantaneous — there is a propagation delay — but for the typical use case of reading configuration, agent definitions, or the output of recently completed executions, the delay is small enough to be unimportant.

When a node calls get-mirror-store, it receives a store implementation backed by a mirror PState. The interface is the same as a regular store — the node function does not need to know whether the backing PState is local or mirrored. Reads work the same way. The one explicit difference is that writes are rejected. Mirror stores are read-only by design. Allowing writes would create an ownership ambiguity — who owns this data? — and would make the replication semantics much harder to reason about. The read-only constraint is not a limitation in practice, because the correct way to write to another module's state is always through events appended to that module's depot, not through direct PState writes.

Mirror query topology invocation follows a different path. When a node calls get-mirror-query-topology-client, it receives a proxy that routes query calls to the source module's query topology. The routing in this case does cross the module boundary — query topology calls are not replicated locally because they involve computation, not just data. But from the node function's perspective, the proxy interface is the same as a local query topology client. The function calls a named query with arguments and receives a result. The platform handles the routing, and the result comes back synchronously.

The design implication of the mirror mechanism is worth making explicit. Cross-module agent calls are not fundamentally different from within-module calls at the application level. The module boundary is a deployment concern, not an application concern. A node function that calls a subagent does not need to specify whether that subagent lives in the same module or a different module. If it lives in a different module, the mirror mechanism handles the bridging. The node function issues the same call, receives the same result, and works through the same AgentNode interface. The infrastructure difference — local versus mirrored — is resolved at the framework level, not at the application level.

This has a consequence for how you think about module organization. Modules are the unit of deployment, and they can be updated independently. An organization that manages a large Agent-o-rama deployment might divide agents across modules by team, by business function, or by scaling requirements. Team A's agents are in module A, Team B's agents are in module B. Either team can update their module without coordinating with the other. Agents in module A can still call agents in module B, through mirror depots and mirror PStates, without any changes to the application code. The mirror mechanism is what allows this independence to coexist with genuine interconnection.

The broader point is that the mirror mechanism resolves a tension that would otherwise be irreconcilable. A system composed of independent modules gains flexibility: modules can be scaled, updated, and maintained independently. But a system whose components cannot communicate efficiently is a system whose components cannot collaborate. The mirror mechanism gives you both. Each module is self-contained in the sense that matters for deployment and operations. But the platform replicates the data structures that enable communication, so module boundaries do not become communication barriers. Modules are the unit of deployment but not the unit of isolation. The system scales and deploys as a collection of independent modules, but it reasons and communicates as a single coherent system.
