# Part Eight: Putting It All Together

## Chapter 23: A Complete Trace Through the System

Every chapter up to this point has examined one component in depth: a particular depot, a specific PState, a topology's processing logic, a partitioning mechanism. That approach is necessary — you cannot understand the whole without understanding the parts. But there comes a point where the parts need to be reassembled, and that is what this chapter does. What follows is a single agent invocation traced from beginning to end, touching every layer of the system in the order it actually encounters them. Nothing here is new. The point is to watch it all work together.

The scenario is deliberately simple: an agent with two nodes, no fan-out, no aggregation, no retry. The client calls agent.invoke. What happens next is a sequence of eleven steps, each of which will be described with enough detail to locate it in the architecture you now know.

---

The first step is the client call itself. When a client calls agent.invoke, the client library constructs an AgentInitiate event containing the invocation arguments, the agent identifier, and the metadata the caller supplied. It then appends this event to the main agent depot. The critical question — which task receives it? — is answered by the depot partitioner. For AgentInitiate events, the partitioner makes a random selection from the available tasks. Say it selects task 7. The event is appended to task 7's partition of the main depot, and task 7 will be the home task for this execution. The assignment is made here, once, and it will govern every subsequent routing decision for the lifetime of this invocation. The client's call has now returned from its perspective — the submission is complete — though the result is nowhere near ready yet.

The second step belongs to the stream topology running on task 7. It picks up the AgentInitiate event from the depot. The first thing it does, as always, is check the retry generation — this is a fresh execution, so the check passes trivially. Then it creates an entry in the root PState for this execution, keyed by the agent-id A that was assigned to this invocation. That entry records the invocation arguments, the graph version governing this run, the caller's metadata, and an initial ack-val. Alongside the root PState entry, the topology creates an entry in the node PState for the first node, assigning it invoke-id N1, recording which node it corresponds to, marking it as pending, and noting that its target task is task 7 — the home task, where the first node will run by default. Finally, the topology constructs a NodeOp message targeting N1 on task 7 and routes it. The topology commits. Its work for this event is done. The root PState now reflects an active execution, and task 7 has a pending NodeOp in its queue.

The third step is the node executor on task 7 picking up the NodeOp for N1. The executor pulls a virtual thread from its pool, constructs an AgentNode context for the invocation, initializes the thread-local list of NestedOp records, and calls the user's first node function with the invocation arguments. The function begins executing. From the user's perspective, this is ordinary code — a function receiving arguments and about to do some work. From the system's perspective, the virtual thread is now live on task 7, and everything it does is being quietly observed.

The fourth step is the model call inside the node function. The user's code calls the AgentNode interface to invoke a language model. The client library underneath that interface sends an HTTP request to the model provider and parks the virtual thread on the response. The virtual thread is now suspended — it holds no operating system thread, just a lightweight continuation object on the heap. The node executor's carrier thread is free to pick up other work. Some time passes — milliseconds to seconds, depending on the model and the prompt. The model responds. The JVM wakes the virtual thread, delivering the response as the return value of the model call. The thread resumes as if it had simply been waiting in line. The AgentNode implementation records the model call as a NestedOp entry in the thread-local list: the model name, the token counts, the latency, the result. The user's function continues.

The fifth step is the emit call. The user's first node function calls emit on the AgentNode, passing the name of the second node and the value it wants to hand downstream. The emit is not sent anywhere yet — it is recorded in a second thread-local list alongside the NestedOps. The function returns. There is nothing more to do on this thread.

The sixth step is the executor's cleanup. Now that the node function has returned, the executor collects everything: the list of emits the function declared, the accumulated NestedOps, and the result if the function declared one. It packages these into a NodeComplete event addressed to the home task — task 7 — and appends that event to the main agent depot. The event carries the invoke-id N1, the agent-id A, the agent-task-id pointing to task 7, and the full payload of emits and nested ops. The virtual thread is released back to the pool. The executor's responsibility ends here. It has produced exactly one artifact — the NodeComplete event — and handed it to the depot.

The seventh step is the stream topology on task 7 processing the NodeComplete for N1. The topology confirms the retry generation, then updates the node PState entry for N1: it writes in the emit list, the nested ops, the timing information, and marks N1 as complete. Then it works through the emits. There is one emit — to the second node. The topology creates a new node PState entry for this second node, assigning it invoke-id N2. It needs to choose a target task for N2. For a regular, non-aggregating node, the choice is random. Say it selects task 12. The node PState entry for N2 records task 12 as its target, notes the invoking emit, and marks N2 as pending. The topology constructs a NodeOp for N2 and routes it to task 12. It commits. At this point, N1 is fully recorded in the node PState with all its nested operations, and task 12 has a new NodeOp waiting for it.

The eighth step takes place on task 12. The node executor there picks up the NodeOp for N2 and runs the second node function on a virtual thread, just as task 7 ran the first. The second node reads from a key-value store. This read is implemented as a task-local select on the backing PState for that store, and because the backing PState is partitioned by key and the appropriate key's partition lives on task 12, the read is local — no network hop is required. The result comes back immediately and is recorded as a NestedOp in the thread-local list, along with the key, the path, and the timing. The second node calls result, declaring the final output of the entire invocation as a specific value.

The ninth step is the executor on task 12 constructing the final NodeComplete. It packages N2's result, its NestedOps — including the store read — and the absence of any emits into a NodeComplete event. This event is addressed to the home task, task 7, because all lifecycle events for this execution route back to the agent-task-id regardless of where the node ran. The event is appended to task 7's partition of the main depot.

The tenth step is the stream topology on task 7 processing this final NodeComplete. It confirms the retry generation, then updates the node PState entry for N2 with the NestedOps, the result, and timing information, marking N2 as complete. Because this NodeComplete carries a final result — rather than merely emits — the topology does two additional things. It updates the root PState entry for agent-id A, writing the result value into the result field and marking the execution as complete. And it removes A from the active-invokes set in the shared PState, which tracks which executions are currently in flight across the cluster. The topology commits. The execution is finished. Every record that describes what happened, from the initial arguments to the model call's token count to the store read's latency, is now persisted in the PStates on task 7.

The eleventh step returns us to the client. When the client called agent.invoke, it did not simply submit the event and walk away — it also established a foreign proxy on the result field of the root PState entry for agent-id A. The foreign proxy is a live subscription: Rama evaluates the read path when it is first established and re-evaluates it whenever the underlying PState changes. For most of the execution's lifetime, the result field is null. But in the tenth step, the stream topology wrote the result value into that field. The change is detected by the foreign proxy. Rama re-evaluates the read path, sees the populated result field, and delivers the value to the client thread that has been waiting on it. The client's invoke call returns. From the caller's perspective, the call was blocking: they submitted arguments and received a result. Everything described in the preceding ten steps happened invisibly between those two moments.

---

Stepping back from the sequence, a few properties of this execution are worth naming explicitly, because they are not obvious from the individual steps but emerge clearly when you see the whole.

The execution touched exactly two tasks: task 7, which was the home task and processed all lifecycle events for the execution, and task 12, which ran the second node. No other task was involved. The routing mechanism ensured that the AgentInitiate event, both NodeComplete events, and all PState reads and writes for the execution's core records landed on task 7. The second node ran on task 12 because a randomly selected target happened to be task 12, not because any coordination step placed it there. Each task operated on its own local data.

No network hop was required to read PState during node execution on each respective task. When task 7 ran the first node, any PState access was local to task 7. When task 12 ran the second node, the key-value store read was a local select because the relevant key's partition happened to live on task 12. This is the co-location strategy in action: the placement decisions made upfront — home task assigned at AgentInitiate time, target task assigned at emit time — are what make local reads possible. The locality is not accidental; it is the payoff of the partitioning design.

The result was delivered to the client via a reactive read with no polling. The client did not submit a request and then loop asking whether the result was ready. The foreign proxy mechanism delivered the result the moment it became visible in the PState, driven by the topology's commit rather than by any client-initiated check. This is what makes the system responsive rather than merely fast: the notification path runs from the infrastructure outward to the client, not from the client inward to the infrastructure.

The complete trace of this execution is now stored in the node PState on task 7, including the model call's timing and token counts from N1 and the store read's timing from N2. This record is the raw material for the analytics pipeline. When the cursor-based analytics topology eventually scans past this execution, it will find everything it needs to compute percentiles, detect anomalies, and update the telemetry PState — because the node executor recorded it, the NodeComplete event carried it, and the stream topology persisted it. Observability is not an add-on. It is woven into the execution model.


## Chapter 24: Design Decisions and the Tradeoffs They Create

A system's architecture is a record of decisions made under uncertainty. Every design choice in Agent-o-rama reflects a judgment about what matters: what to optimize for, what to accept as a cost, and what to treat as non-negotiable. This chapter examines those choices honestly — not as a celebration of clever engineering, but as an accounting of what each decision costs and what it buys. Understanding the tradeoffs is what lets you reason about the system's behavior in cases the documentation does not cover.

---

The most foundational decision in the system is the choice of event sourcing over direct mutation. When the stream topology processes an event, it does not simply update the PState. An event first arrives at the depot — which means it is durably logged — and only then does the topology apply it as a PState transition. Every state change in the system follows this path. The upside is significant: if the topology crashes mid-processing, Rama restarts it from the last committed position in the depot. The log is still there. The PStates reflect exactly the state as of the last successful commit. The processing logic picks up where it left off with no data loss and no need for crash recovery logic. Replay, which would otherwise require careful engineering, comes for free from the log. Retries become safe because the log is immutable and the retry generation filter is the only mechanism needed to distinguish current events from stale ones.

The cost of this approach is write amplification. Every state change requires two writes: one to append the event to the depot, and one to apply the event to the PState. For a system processing thousands of NodeComplete events per second, those depot writes accumulate. Depot append latency is low but not zero, and the volume of appends is proportional to the activity of the system. An alternative design — writing directly to a distributed state store, accepting that failures may produce partially applied states and require compensating logic — would have lower write overhead at the cost of significantly more complex failure handling. Agent-o-rama judges that the complexity of handling partial mutations is a worse problem than the overhead of the double write. That judgment is reasonable, but it means the depot is a resource that grows over time and must be managed.

---

The partitioning strategy is the second fundamental decision: using a custom depot partitioner that reads a pre-assigned task identifier from each event, rather than deriving a partition from a hash of the event's content. Hash partitioning is the default in most distributed systems because it distributes load automatically and requires no upfront assignment. Agent-o-rama's custom partitioner does something different — it uses a routing key embedded in the event to route to a specific task, and that routing key is assigned when the execution begins, not when the event is created.

The benefit of this approach is co-location: because all events for an execution route to the same task, and because PStates are partitioned by the same key, the stream topology on that task can read and write PState without network round-trips. The execution's home task becomes a self-contained processing environment for that execution. This is the property that makes the trace described in the previous chapter efficient.

The cost is that load distribution is not automatic. If a long-running execution happens to be assigned to task 7, and then ten more long-running executions are also assigned to task 7 by chance, task 7 carries a disproportionate load for the duration of those executions. Hash partitioning would have spread those executions across the cluster. The custom partitioner concentrates them on whatever task was randomly selected. In practice, with a large enough cluster and a large enough volume of concurrent executions, the law of large numbers smooths out these fluctuations. But the system does not guarantee uniform load distribution, and workloads with a small number of very heavy executions can create task hotspots that hash partitioning would have avoided.

---

The choice of virtual threads over asynchronous futures is a decision about the programming model as much as the execution model. An asynchronous future-based system — the kind built on CompletableFutures chained with callbacks, or on reactive streams frameworks — can achieve similar concurrency properties. When a model call is pending, the calling thread does not block; instead, a callback is registered to receive the result when it arrives. The thread is free to do other work in the meantime.

Agent-o-rama uses virtual threads instead, which means node functions are written as ordinary blocking code. You call a method to invoke a model, and you wait. The thread parks. The result arrives and the thread wakes. This is the simplest possible programming model: sequential code, one thing after another, exactly as you would write it for a single-threaded application. The benefit is readability and debuggability. Stack traces reflect actual call sequences. Error handling is try-catch rather than error-callback chaining. Testing is straightforward because the code is not split across multiple callbacks.

The cost is a dependency on Java 21 and a JVM that correctly implements virtual thread carrier-thread unmounting on blocking operations. Virtual threads were a preview feature for years before becoming stable in Java 21. Not every library that claims to support virtual threads actually unmounts the carrier thread on every blocking call — some operations still pin the virtual thread to its carrier thread, which defeats the point. The system requires careful validation that every blocking call in the hot path correctly unmounts. That validation work is ongoing rather than a one-time cost. An async future-based system would not have this dependency and would run on earlier JVM versions. The tradeoff is a better programming model at the cost of a tighter platform dependency.

---

The XOR ack-val mechanism for detecting aggregation completion is a choice with a particularly tight shape. The alternative — a counter that is incremented when a child is created and decremented when a child completes — is simpler to explain and simpler to implement locally. The ack-val is less obvious. It requires understanding XOR's commutativity and self-inverse properties to trust it.

The benefit of the ack-val is that it requires no centralized coordination. Each XOR operation is local to the task that processes it. The aggregation task monitors a single field in its local PState. No task needs to consult any other task to determine whether the aggregation is complete. In a large fan-out with hundreds of parallel children, this matters: a centralized counter becomes a serialization point that all children must pass through to report their completion. The ack-val eliminates that bottleneck.

The cost is the requirement that branch counts and ack contributions are computed correctly at emit time. If a contribution is XORed in when a child is created but the same contribution is not correctly XORed out when the child completes, the ack-val never returns to its initial value and the aggregation never fires. The correctness of the mechanism depends on the contributions being symmetric. This is not difficult to maintain — the framework manages it, not the application author — but it means the mechanism is less forgiving of implementation errors than a counter would be. A counter that fails to decrement will eventually produce an obviously wrong result. An ack-val that fails to remove a contribution will silently stall the aggregation forever. The ack-val trades a more obvious failure mode for a better performance characteristic.

---

For telemetry, the system uses T-Digest sketches rather than storing raw measurement values. T-Digest is a data structure that computes approximate quantiles — median, ninety-fifth percentile, ninety-ninth percentile — from a stream of values using a fixed, configurable amount of memory, regardless of how many measurements are incorporated. The benefit is straightforward: a T-Digest for an execution node that has run ten million times occupies the same memory as one for a node that has run a hundred times. The telemetry PState does not grow unboundedly as the system processes more executions. Percentiles are available immediately from the sketch without scanning raw data.

The cost is approximation. A T-Digest's percentile estimates are not exact. The error is bounded and configurable, and in practice the ninety-fifth and ninety-ninth percentile estimates are accurate to within a fraction of a percent for most distributions. But if the exact timing of the slowest one percent of executions matters for your analysis — if you are debugging a specific extreme outlier — the T-Digest cannot give you the precise value, only a close estimate. If exact values were required, the system would need to store raw measurements, which either means unbounded storage growth or a bounded window that loses historical data. For the use case of operational monitoring and performance trending, approximate percentiles are entirely sufficient. For forensic analysis of individual extreme events, you would need to look at the node PState records directly rather than the telemetry sketches.

---

The analytics pipeline uses cursor-based scanning rather than a publish-subscribe model. When a NodeComplete event is processed by the stream topology, the analytics pipeline does not receive a notification immediately. Instead, the cursor-based analytics topology periodically scans the node PState looking for records it has not yet processed, advances a cursor as it goes, and applies telemetry rules to each newly discovered record. The benefit of this approach is that it provides exactly-once processing semantics for analytics. Because the cursor marks a stable position in the PState, a failure mid-scan simply restarts from the last cursor position. No record is processed twice, and no record is skipped. This also means backfill is trivially supported: if a new telemetry rule is deployed, you can reset the cursor to the beginning of history and the rule will be applied to all past records as if they were new.

The cost is latency between execution completion and analytics visibility. There is a delay — typically seconds, configurable — between the moment a NodeComplete event is processed by the stream topology and the moment the cursor-based analytics topology discovers the resulting node PState record and updates the telemetry sketches. For operational dashboards where near-real-time visibility is expected, this delay may be noticeable. A publish-subscribe model — where the stream topology notifies the analytics pipeline directly when a record is created — would eliminate this latency. But a pub-sub model introduces at-least-once delivery semantics by default, requires additional logic to prevent duplicate processing, and does not naturally support backfill. The cursor-based approach accepts a fixed latency in exchange for strong processing guarantees and operational simplicity.

---

The separate streaming depot is a choice about traffic isolation. When a node emits a streaming chunk, that chunk goes to a dedicated streaming depot rather than the main agent depot. The benefit is that streaming throughput does not compete with execution management traffic. During a long generation where a language model produces dozens of chunks per second, those chunks would otherwise intermingle with NodeComplete events and AgentInitiate events on the main depot. A busy streaming session could delay execution events that are on the critical path of other agents' progress. The separate depot gives each class of traffic its own processing pipeline with no cross-contamination.

The cost is an additional depot write for every streaming chunk. Each chunk requires an append to the streaming depot before it can be processed by the streaming topology and become visible in the root PState. This adds a layer of latency to the streaming path — small, but present. A system that routed streaming chunks through the main depot would have one fewer write per chunk. The tradeoff is that the streaming path is slightly slower in isolation, but the rest of the system is protected from being slowed by streaming volume. For a production system where streaming sessions can be high-volume and unpredictable, protecting the main execution path is worth the marginal cost.

---

Stepping back from the individual tradeoffs, a pattern emerges. Every decision described in this chapter makes the same kind of choice: it accepts a modest cost in raw performance or implementation simplicity in exchange for a stronger guarantee in reliability, observability, or correctness under failure. Event sourcing adds write overhead but makes failure recovery trivial. Custom partitioning may create hotspots but makes task-local processing the default. The ack-val requires careful contribution tracking but eliminates coordination bottlenecks. T-Digest accepts approximation but bounds telemetry storage. Cursor-based analytics introduces latency but provides exactly-once guarantees. The separate streaming depot adds a depot write but protects the main execution path.

This coherence is not accidental. It is the mark of a system built with a specific set of priorities held consistently throughout the design. The priorities are production reliability, observability, and fault tolerance — not implementation simplicity and not raw throughput maximization. When you encounter a behavior in Agent-o-rama that puzzles you, asking "which of these priorities does it serve?" will usually lead you directly to the explanation. The design is coherent in the sense that all the decisions point in the same direction. They are not a collection of locally optimal choices assembled from convenient components. They are a single consistent argument about what a distributed agent framework should optimize for, expressed in every layer of the architecture.
