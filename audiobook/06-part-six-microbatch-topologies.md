# Part Six: The Microbatch Topologies

## Chapter 16: The Stall Detector — How Retries Are Triggered

Every distributed system must eventually answer the question of how it knows when something is stuck. In a single-threaded program running on a single machine, this is almost trivial — a watchdog process on the same machine can check whether a thread is making progress and take action if it is not. The machine has full visibility into the work it is doing. But in a distributed system, the work of a single logical operation is often spread across many tasks running on many machines, and no single machine has a complete view of the whole. This is the fundamental challenge that Agent-o-rama's stall detector must solve: how do you know when an agent execution has stopped making progress when the execution itself is a distributed thing, with its events flowing through a depot and its state maintained across a cluster of tasks?

Agent-o-rama's answer is a dedicated microbatch topology driven by a periodic tick depot. A tick depot is simply a depot that emits events on a schedule — once per second, once per ten seconds, whatever interval the configuration calls for. Each tick is a heartbeat that wakes up the stall detector topology and tells it to do its work. The topology itself does not run continuously; it sleeps until a tick arrives, then performs a coordinated scan of the cluster's execution state, then sleeps again until the next tick.

When the tick fires, the stall detector topology scans the active-invokes set in the shared PState. The active-invokes set is exactly what its name suggests: the collection of all agent-ids for executions that are currently running. An execution enters this set when it is first created and leaves it when it completes, either successfully or with a terminal error. Any execution that remains in the set is, by definition, still active. The stall detector walks through every entry in this set and asks a simple question: has this execution made progress recently?

Progress, in this context, is defined precisely. A NodeComplete event being processed is progress. When the stream topology receives a NodeComplete event for a given agent execution, it records a timestamp — the "last-progress" timestamp — in the execution's record in the root PState. The stall detector compares the current time against this recorded timestamp. If the difference exceeds a configurable threshold, the execution is considered stalled. The threshold is typically generous enough that transient slowdowns — a language model API taking longer than usual, a network hiccup causing a retry of a downstream call — do not trigger a false stall detection. But if a node has been running for several minutes with no NodeComplete arriving, it is reasonable to conclude that something has gone wrong.

This is where the valid-invokes PState becomes essential. The valid-invokes PState is maintained by the stall detector microbatch topology, and it records, for each active execution, a retry generation number. When an execution is first created, its generation is zero. When the stall detector decides that an execution is stalled and needs to be retried, it increments the generation number for that execution in the valid-invokes PState. The generation number is a version counter, and it is the mechanism by which Agent-o-rama fences off stale events from earlier, now-abandoned execution attempts.

To understand why this matters, consider what happens in the interval between when a stall is detected and when the retry begins to run. There may be events already in flight — NodeComplete events from a node that was, in fact, making slow progress and did eventually finish, or ack events acknowledging work that was dispatched some time ago. These in-flight events were generated by the old execution attempt. Without some way to identify them as stale, the stream topology would process them, updating PState entries that now belong to the new execution attempt. The result would be corrupted execution state — records from two different attempts interleaved in a single logical execution.

The generation number solves this cleanly. Every event that carries execution context — NodeComplete, ack messages, and so on — carries the generation number it was created with. When the stream topology receives an event, it looks up the current generation for that execution in the valid-invokes PState. If the event's generation number does not match the current generation, the event is discarded. It is stale. It belongs to an old attempt that has already been superseded. This filter operates on the hot path of event processing, and it is precise: events from the current generation pass through, events from any previous generation are silently dropped.

When the stall detector determines that an execution needs to be retried, it takes two actions atomically, within a single microbatch commit. First, it increments the generation number in the valid-invokes PState. Second, it appends a RetryAgentInvoke event to the main agent depot. This event carries both the agent-id and the new, incremented generation number. The stream topology receives this event, reads the retry invocation, reinitializes the execution state in the root PState for the new generation, and schedules the first node of the execution again. The old execution is effectively erased and replaced with a fresh start, but with the same identity — the same agent-id — so that clients waiting on the result are none the wiser.

This brings us to why microbatch is the right choice for the stall detector, rather than stream. The difference is not cosmetic. A stream topology processes events individually — one tick, one processing step, one commit. If you tried to implement the stall detector as a stream topology, each tick event would trigger a scan of the active-invokes set, but that scan would happen within the processing of a single event, without any atomic relationship to the scans happening on other tasks for other partitions. There would be no single moment at which the state of all active executions was inspected together and all retry decisions were committed together. Some executions might be scanned on one tick and others on the next, creating a window during which the valid-invokes PState and the retry events written to the depot are out of sync.

With microbatch, the entire scan of the active-invokes set — across all tasks, across all active executions — happens within a single batch commit. All stall detections and all generation increments and all RetryAgentInvoke events are committed together as an atomic unit. Either the entire batch succeeds and the system is in a consistent state where stalled executions have been retried and their generations have been incremented, or the batch fails and none of it happened and the next tick will try again. This is the atomic coordination boundary that microbatch provides, and it is exactly what reliable stall detection requires.

The stall detector and the generation filter are two halves of a single fencing mechanism. The stall detector decides when to act. The generation filter ensures that when it acts, the old execution cannot contaminate the new one. Neither half works without the other. Together they form the foundation of Agent-o-rama's ability to recover from stuck executions without operator intervention — a production system that can heal itself when individual nodes or network calls fail to complete.

## Chapter 17: The Analytics Microbatch Topology — Rules and Telemetry

The analytics topology is Agent-o-rama's system for making sense of what has already happened. Where the stream topology is concerned with what is happening right now — executing nodes, updating execution records, emitting results — the analytics topology sits downstream of that activity and asks a different kind of question: of all the executions that have completed, which ones should trigger an action? Which ones should contribute to a metric? What does the population of completed executions tell us about how the system is performing?

The topology has two jobs, and it does them in the same pass. The first job is rule evaluation: for each completed invocation that has not yet been evaluated against a given rule, check whether it satisfies the rule's conditions and, if so, trigger the rule's configured action. The second job is telemetry aggregation: for each completed invocation, extract any defined metric values and accumulate them into the time-series telemetry PState. Both jobs are driven by the same tick depot, which fires on a configured schedule — typically every few seconds — and both jobs share the same scanning mechanism: the cursor.

The cursor is the organizing principle of the analytics topology, and it is worth spending some time with it because the same pattern appears in many distributed systems that need to process an ever-growing log of data reliably. Each rule has a cursor per task. A cursor is simply a pointer — specifically, the invoke-id of the most recently processed invocation for that rule on that task. When the analytics tick fires, each task looks at the root PState starting from the position of the cursor and reads forward up to a configurable batch size. These are the invocations that have completed since the last tick but have not yet been evaluated against this rule. The topology processes them in order, advances the cursor to the invoke-id of the last invocation it processed, and commits. On the next tick, scanning resumes from exactly where it left off.

Think of it this way: the cursor is a bookmark in a very long book of completed invocations. Each tick, the topology opens the book to the bookmark, reads a chapter, moves the bookmark forward, and closes the book. The book grows at its front end as new invocations complete, and the bookmark pursues it from behind. The distance between the front of the book and the bookmark is the lag: the number of invocations that have completed but not yet been evaluated. In a healthy system, this lag stays small. In a system under heavy load or with a slow rule action, the lag may grow. The cursor makes this visible and measurable.

Rule evaluation is more than just checking whether an invocation completed. A rule is a filter with a structured set of conditions. When the topology evaluates a rule against an invocation, it checks several things in sequence. First, scope: is this rule configured to apply to all agents, or only to a specific one? If the invocation belongs to an agent that the rule does not cover, it is skipped immediately. Second, status: did this invocation succeed, or did it error? Some rules are only interested in successful executions; others specifically target failures. Third, sampling rate: rules can be configured to apply to only a fraction of matching invocations, which is useful when you want to evaluate a slow or expensive action — like calling a language model judge — on a representative sample rather than every execution. Fourth, conditions on the invocation's input, output, and metadata: a rule might specify that it only applies to invocations where a particular metadata field is set, or where the output contains a certain structure, or where the input exceeds a certain size.

An invocation that passes all of these filters is considered a match. The topology then dispatches the match to the rule's action. The action function receives the full context of the invocation: the input that was passed to the agent or node, the output that was produced, the metadata the invocation carried, the timing information including how long each node took, and the run information that identifies which experiment or configuration was active during this execution. What the action does with this context depends on what the rule is configured to do. It might call an LLM judge and store the resulting evaluation score. It might add the invocation to a dataset for later fine-tuning. It might call a webhook to notify an external system. It might execute custom logic — any code the developer has registered as a rule action. The analytics topology does not prescribe what actions do; it guarantees that matching invocations reach them exactly in the order they completed, with no invocation being missed and no invocation being skipped over.

After all invocations in the current batch have been processed, the cursor advances to the invoke-id of the last invocation in the batch, and the commit happens. The cursor advancement and all resulting state changes — scores written to the telemetry PState, dataset entries created, whatever the actions produced — are committed atomically as a single microbatch. Either all of it commits, or none of it does.

This atomic commit boundary is also what makes backfill straightforward. If you define a new rule and want it to evaluate against historical invocations — perhaps you want to score everything from the past month against a new quality judge — you simply reset the cursor for that rule to the invoke-id of the earliest invocation you want to include. The topology will begin reading forward from that position on the next tick. There is no special backfill mode, no batch job to launch, no separate infrastructure to configure. The cursor is just a number, and moving it backward is the same operation as moving it forward. The topology does not know or care whether it is doing forward processing or backfill. It reads from the cursor, processes, advances, and commits. This uniformity is a significant operational advantage: the code that handles normal operation is identical to the code that handles historical replay.

The second job of the analytics topology — telemetry aggregation — happens in the same scan pass. As the topology reads each unprocessed invocation, it also evaluates any metric definitions that apply to it. A metric is defined by a value function: a function that takes an invocation record and extracts a number from it. Latency is a common metric — the total wall-clock time from when the invocation was created to when it completed. Token count is another — the total number of tokens consumed by all language model calls within the execution. Error flag is a binary metric that is one if the invocation failed and zero if it succeeded. Evaluator scores, if any rules ran LLM judges against this invocation, can themselves be aggregated as metrics. Human feedback scores, if a human reviewer rated the output, are another.

The extracted value is accumulated into the telemetry PState using a data structure called a T-Digest sketch. A T-Digest is a probabilistic data structure designed for streaming computation of percentile statistics. Rather than storing every individual value — which would grow without bound as more invocations complete — a T-Digest maintains a compact summary of the distribution of values it has seen. From this summary you can compute the median, the ninety-fifth percentile, the ninety-ninth percentile, and similar statistics with bounded error. The analytics topology appends each new metric value to the appropriate T-Digest in the telemetry PState, and the telemetry PState reflects the up-to-date distribution of that metric across all invocations processed so far.

The processing guarantee for the analytics topology is worth stating precisely. Because the cursor advances atomically with the processing commit, if the topology fails partway through a batch — say, a machine crashes after processing ten invocations but before the batch is committed — the topology will restart from the same cursor position. Those ten invocations will be processed again. This means the guarantee is "at least once" rather than "exactly once." An LLM judge might evaluate the same invocation twice; a T-Digest might receive the same value twice. For analytics purposes, this is almost always acceptable. The error introduced by an occasional duplicate is small compared to the operational complexity of a true exactly-once system. If a specific use case requires exactly-once guarantees, additional deduplication logic can be added to the action, but the default behavior embraces the simplicity of at-least-once.

The parallelism of the analytics topology is one of its most important properties. Because each task has its own cursor, rule evaluation across the entire cluster is embarrassingly parallel. If the module is configured with thirty-two tasks, then thirty-two independent portions of the invocation history are being evaluated simultaneously and independently. Task twelve is evaluating its slice of invocations while task seven evaluates its slice and task twenty-nine evaluates its own. There is no coordination between tasks during the evaluation phase. Each task commits its own cursor independently. The only shared state is the telemetry PState, and writes to it are partitioned by metric identity, so even those writes are distributed. This is one of the reasons that adding tasks to the cluster scales the analytics throughput nearly linearly — there is very little work that cannot be parallelized by simply adding more tasks.

## Chapter 18: The Garbage Collector — Managing State Growth

The root PState and the node PState are the living memory of Agent-o-rama's execution machinery. Every running execution has entries in these PStates — the execution record, the node records, the timing data, the token counts, the nested operation logs. As long as an execution is active or recently completed, these entries need to be there. But in a long-running production system, executions complete and new ones begin continuously, around the clock. If completed executions are never removed, both PStates grow without bound. After weeks or months of operation, the memory footprint would be enormous, reads would slow down as data structures grew larger, and the system's resource consumption would be driven not by the current load but by the accumulated history of everything that had ever run.

Agent-o-rama addresses this with a dedicated garbage collection topology, driven by its own tick depot. The GC tick fires on a much slower schedule than the stall detector or analytics ticks — perhaps every few minutes — because the consequences of a GC cycle are durable state deletions, and there is no urgency to GC individual executions the moment they become eligible. The GC topology is background infrastructure: it runs when it runs, it cleans up what it can, and it leaves the hot-path stream topology free to focus entirely on active executions.

When the GC tick fires, the topology identifies completed executions that are old enough to be eligible for removal. What "old enough" means is determined by the retention policy, which is a configurable parameter. An execution might be retained for a day — long enough for a developer to inspect the trace if something went wrong. It might be retained for a week in environments where historical analysis is important. It might even be retained until the analytics topology has confirmed, via the cursor mechanism, that it has been fully processed against all configured rules, ensuring that no invocation is GC'd before every rule has had a chance to evaluate it. The retention policy is a knob, and the right setting depends on the operational needs of the deployment.

The GC topology does its work in two phases, and understanding why requires thinking about what other parts of the system might be doing at the same moment the GC is running.

In the first phase, the topology moves completed invocations that have passed their retention deadline into a GC-marked set within the shared PState. The entries themselves are not deleted yet — they are simply flagged as candidates for deletion. The GC-marked set is a staging area. The GC commits this marking atomically at the end of the first batch.

Then, in a subsequent tick, the topology reads from the GC-marked set and performs the actual deletions: it removes the flagged entries from the root PState and from the node PState. This commit completes the cleanup.

The reason for this two-phase design is that deletion is not safe the moment an execution completes. Other parts of the system may still be actively reading that execution's data. The analytics topology, if it is running behind its cursor, might be processing an invocation that the GC would otherwise delete. A client application might be in the middle of fetching the trace for a completed execution to display in the web UI. A query topology call might be reading the execution's node records to assemble a full view of what happened.

If the GC deleted entries immediately on the first pass, any in-flight read that happened to be looking at one of those entries at the moment of deletion would encounter a sudden absence. The data would simply be gone mid-read. The result, depending on the system, would be an error returned to the client, a corrupted trace view, or — in the case of the analytics cursor — an invocation that was never processed because it was deleted before the cursor reached it.

The two-phase approach handles this gracefully. The first phase marks the entries but leaves them in place. In-flight reads that are happening during the first phase can still see the full data. By the time the second phase runs — in the next GC tick, minutes later — those in-flight reads have long since completed. The data has been read by everything that needed it, and now it can be safely removed. Think of it as a graceful shutdown protocol applied to data rather than to services. When you want to shut down a server, you stop accepting new connections but finish serving the connections that are already open. When the GC wants to delete an execution record, it stops the record from being considered an active part of the system but finishes serving the reads that are already in progress.

The relationship between the GC and the analytics cursor deserves explicit attention. The analytics cursor creates a soft ordering constraint: the GC should not delete an invocation before the analytics topology has advanced its cursor past that invocation. If it did, the analytics topology would try to read an invocation record that no longer exists. The retention policy is the mechanism that enforces this constraint in practice. By configuring the retention window to be longer than the maximum expected analytics lag — if the analytics topology is running a few seconds behind and the retention is set to twenty-four hours, there is an enormous safety margin — you ensure that the GC never races ahead of the analytics cursor. In deployments where the analytics topology is slow for some reason — perhaps a rule is dispatching to a slow LLM judge and creating a large backlog — the retention policy can be extended to prevent data loss.

This interaction between the GC and the analytics cursor illustrates a broader principle: in a distributed system built on microbatch topologies, the topologies are not truly independent. They operate on shared state, and the timing relationships between them have consequences. The GC assumes that the analytics cursor is not too far behind. The analytics cursor assumes that the invocations it wants to read have not yet been GC'd. These assumptions are managed through the retention policy, which is a single configuration knob that controls the margin of safety between the two.

To close this part of the book, step back and look at all three microbatch topologies together. The stall detector, the analytics engine, and the garbage collector are structurally the same. Each is woken by a periodic tick from a tick depot. Each performs a scan of shared PState — the active-invokes set, the invocation history, the completed executions — and derives a set of actions from the scan. Each commits the results of that scan atomically, so that the post-commit state is always consistent and complete. Each tracks its position in the data it is scanning, so that on the next tick it can resume where it left off rather than starting over.

The choice to implement all three as microbatch topologies rather than stream topologies is not arbitrary. It reflects the nature of the work each one does. Stall detection requires looking at many executions together and making coordinated decisions about which ones to retry. Analytics requires scanning a shared history and advancing a shared cursor. Garbage collection requires a two-phase commit across a shared set of PState entries. All of these tasks involve coordination across multiple data points, and all of them require the atomic commit boundary that microbatch provides. A stream topology, processing events one at a time, could not provide that boundary. Microbatch can.

The trio of topologies forms a complete operational picture. The stall detector ensures that stuck executions are recovered. The analytics engine ensures that completed executions contribute to rules, metrics, and datasets. The garbage collector ensures that the system does not accumulate state without limit. Together, they constitute the background intelligence of Agent-o-rama — the processes that keep the system healthy, measurable, and sustainable over the long lifetime of a production deployment.
