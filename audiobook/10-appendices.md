# Appendices

## Appendix A: Depot, PState, Topology — Verbal Definitions

A depot is an append-only, durably stored, partitioned event log. You interact with a depot by writing events to it. Once written, an event is stored persistently and replicated across the cluster according to the configured replication factor. Events within a single partition are ordered strictly: an event written before another will always be read before it. A depot is not passive storage. Topologies subscribe to depots and receive events as they arrive, making a depot the trigger for computation as well as the record of it. If you have used Kafka, the mental model is similar, but the integration between depot and topology in Rama is tighter: the platform manages the relationship between writing to the depot and consuming from it, removing the operational gap that exists when you wire together a broker and a processing framework separately.

A PState, which stands for partitioned state, is a distributed, indexed, durable data structure — the persistent state layer of a Rama application. The simplest way to picture it is as a very large nested map: paths within the map can hold any combination of maps, lists, and scalar values, and the whole structure is partitioned across the tasks that make up the topology. PState writes happen within topology processing, and they are consistent within a partition: two writes to the same partition are always serialized, and a reader on the same partition sees the effects of all prior writes. A PState can also be read from any other part of the cluster through a foreign proxy, which crosses the network to the partition holding the requested data and returns the current value. PState data is not the source of truth in an event-sourced system — the depots that produced the events are — but a PState is the materialized view of that truth, kept up to date by the topologies that consume events.

A stream topology is a Rama computation layer that processes events one at a time. For each event, the topology reads state from one or more PStates, transforms the event, writes any resulting changes to PStates, and commits. The next event is not picked up until the commit for the current event completes. This one-event-one-commit model provides low latency — the time between an event arriving and its effects becoming visible in a PState is typically a few milliseconds — and it provides exactly-once processing semantics within a partition. Stream topologies are the right choice when events can be handled independently and when responsiveness to individual events matters.

A microbatch topology is a Rama computation layer that processes events in time-windowed batches rather than one at a time. The topology accumulates events arriving within a configurable time window and processes the entire batch together as a single atomic unit, committing all resulting PState changes at once. The time window introduces some latency relative to stream processing, but it enables coordination that is not possible event by event: a microbatch topology can inspect the aggregate of many events, make decisions that depend on the relationship between events in the batch, and commit all consequences together so that either every change in the batch is visible or none of them are. Microbatch topologies are the right choice when a correct answer requires reasoning about many events together rather than each event in isolation.

A query topology is a synchronous, request-and-reply mechanism for reading PState data. You define a query topology as a named procedure that accepts arguments, performs reads against one or more PStates, and returns a result. A caller invokes a query topology by name, passing the required arguments, and blocks until a result is returned. Internally, Rama routes the invocation to the task that owns the relevant partition of the data being read, executes the read logic locally on that task, and returns the result to the caller. From the caller's perspective, a query topology behaves exactly like a function call: synchronous, typed, and transparent about whether the data was local or remote. Query topologies are how Agent-o-rama exposes execution traces, invocation lists, telemetry statistics, and other structured data to the web UI and client libraries.

A task is Rama's unit of computation: a thread or thread pool running on a specific machine in the cluster, responsible for owning a specific set of partitions from both depots and PStates. When a module is configured to run with thirty-two tasks, the depots and PStates of that module are each divided into thirty-two partitions, and each partition is assigned to exactly one task. The task that owns a partition is the only place where events in that partition are processed and where state in that partition is read and written by topology logic. The number of tasks determines both the degree of parallelism the system achieves and the number of machines the work can be spread across.

Partitioning is the mechanism by which depot events and PState data are divided across tasks. In a depot, partitioning determines which task a given event is routed to. In a PState, partitioning determines which task stores and services reads for a given entry. Both use a partitioner function: a function that takes a key — either the key extracted from an event or the key of a PState entry — and returns the task index that should own it. Partitioner functions can be standard hash functions, or they can be custom. Agent-o-rama defines custom partitioners on its core depots so that events can carry an explicit target task identifier rather than being placed by key hash, which is what makes the co-location strategy possible.

Co-location is the design principle that places an execution's state on the same task as the events that drive that execution. When an agent execution is assigned to task seventeen, its entries in the root PState and the node PState are stored on task seventeen, and every event related to that execution — NodeComplete events, streaming chunks, human input responses — is routed to task seventeen via the custom depot partitioner. The result is that when the stream topology on task seventeen processes any event for that execution, every read and write it performs against those PStates is a task-local operation: no network hop, no serialization cost, just direct access to data structures in memory. Co-location does not eliminate all network traffic in the system — fan-out to child nodes genuinely distributes work across tasks — but it ensures that the hot path of execution, the sequence of reads and writes that happens on every node completion, never requires crossing a machine boundary.

A foreign proxy is the mechanism by which a topology or query topology reads a PState partition that lives on a different task. When the reading code is executing on task three but the PState entry it needs is on task nineteen, Rama handles the cross-task read transparently: it serializes the request, sends it over the network to task nineteen, waits for the response, deserializes it, and returns the value to the reading code. From the code's perspective, the API is the same as a local read. From a performance perspective, a foreign proxy read carries network latency and serialization cost. This is why co-location is designed to minimize the number of foreign proxy reads on the critical execution path. Foreign proxy reads are used deliberately in contexts where they are infrequent — reading the shared PState for config lookups, querying a remote PState from a query topology — but are avoided in the per-event hot path.


## Appendix B: The Full Depot Inventory

The main agent depot is the central depot of the system, and each agent type in Agent-o-rama has its own instance of it. It is partitioned using a custom partitioner that reads a target task identifier directly from the event: if the event carries an explicit target task, it is routed there; if not, it is sent to a randomly selected task. This custom partitioner is the foundation of co-location. Five event types flow through the main agent depot. The first is AgentInitiate, which carries the invocation arguments, execution metadata, the identity of the caller, and optional overrides for the target task and agent identifier. The second is NodeComplete, which carries the invoke-id and retry number of the node that finished, the full list of emits the node declared, its result if one was produced, the accumulated list of nested operations it performed during execution, and any streaming output. The third is NodeFailure, which carries the invoke-id and exception information when a node raises an unhandled error. The fourth is RetryAgentInvoke, which is a synthetic event generated by the stall detector and carries the agent task identifier, the agent identifier, and the expected retry generation number, used to restart a stuck execution. The fifth is ForkAgentInvoke, which carries the original execution's identifiers and a map from existing node invoke-ids to new argument lists, used to spawn a derived execution that replays only the affected portions of the execution graph.

The streaming depot carries NodeStreamingResult events and is partitioned by agent task identifier, routing every streaming event for a given execution to the same task that owns the execution's state. Each event carries a streaming chunk, the agent task identifier, the agent identifier, the node name, the invoke-id of the specific node invocation that produced the chunk, a monotonically increasing index number that allows chunks to be reassembled in order even if they arrive slightly out of sequence, and the retry generation number. The retry number is essential here for the same reason it is essential in the main depot: if an execution is retried, streaming chunks from the failed attempt must not be incorporated into the new attempt's buffer. The streaming depot is separate from the main agent depot so that potentially large and frequent streaming payloads do not contend with the NodeComplete events that are critical to execution progress.

The human input depot handles the pause-and-resume lifecycle of executions that require a human response before they can continue. It carries two event types. The first is NodeHumanInputRequest, which is appended when a node pauses to wait for a human, and carries the agent task identifier, agent identifier, node name, the invoke-id of the paused node, the task that node is running on, and the prompt string to be displayed to the human. The second is HumanInput, which is appended when a human provides a response through the web UI or client API, and carries the original request record plus the response string. The partitioning strategy differs between these two event types by design: HumanInputRequest events are partitioned by agent task identifier, because the request needs to be processed by the task that owns the agent execution's root state, while HumanInput response events are partitioned by the task identifier of the waiting node itself, because the response needs to reach the specific task where the paused virtual thread is waiting to be unparked.

The config depot carries ChangeConfig events for per-agent operational settings such as the maximum retry count. These events are partitioned randomly, meaning they are distributed across all tasks that run the stream topology. Because every task needs to apply any configuration change, random distribution is the correct strategy: over time, every task receives and processes every config event, keeping all tasks consistent. Config events are rare — they arrive on human timescales, driven by operators using the web UI — and their random partitioning reflects the fact that they have no co-location requirement.

The check-tick depot emits periodic tick events on a schedule configured at deployment time, typically every several seconds. These ticks have no payload beyond the fact that they exist. Their sole purpose is to wake up the stall-detection microbatch topology, which then scans the active-invokes set for executions that have not recorded progress within the configured stall threshold. The check-tick depot drives the stall detector, not the stream topology.

The GC tick depot emits periodic tick events on a slower schedule than the check-tick depot, typically on the order of minutes. Like the check-tick, a GC tick has no meaningful payload. Its purpose is to wake up the garbage collection microbatch topology, which identifies completed executions that have passed their retention deadline, marks them for deletion in the shared PState in a first phase, and then removes their entries from the root and node PStates in a subsequent pass. The slower cadence reflects the fact that GC can afford to run less frequently than stall detection and that its operations — durable deletions of PState entries — are more expensive per event.

The PState write depot carries PStateWrite events for all mutations to user-defined stores, including key-value stores, document stores, and PState-backed stores defined within the agent module. It is partitioned by key, using a hash partitioner that ensures writes to the same key always route to the same task. Each event carries the store name, the path expression identifying what to write, the value to write, and an agent source context including the agent task identifier, agent identifier, and retry generation number. The indirection through this depot — rather than writing directly to the backing PState — exists to provide retry safety: the stream topology that processes PStateWrite events checks the retry generation before applying the write, and discards any write whose generation number no longer matches the current generation for that execution. This ensures that a write from a failed execution that completed successfully before the failure is not applied again during a retry, preventing double-write corruption.

The analytics tick depot emits periodic tick events that wake up the analytics microbatch topology. This topology evaluates completed invocations against configured rules, extracts metric values, and accumulates them into the telemetry PState. The analytics tick fires on a schedule similar to the check-tick, typically every few seconds, reflecting the expectation that analytics results should remain reasonably current even in deployments with high invocation rates.

The global actions depot carries events that mutate shared, cross-agent configuration: additions and removals of rules, evaluators, human metrics, feedback queue configurations, datasets, and experiment configurations. These events are processed by the analytics microbatch topology rather than the per-agent stream topology, because they affect shared state rather than any individual execution's state. Partitioning is random, for the same reason as config events: global actions need to be applied everywhere, they arrive infrequently, and they have no meaningful co-location requirement.


## Appendix C: The Full PState Inventory

The root PState is the primary execution state store of the system. It is partitioned by task-id: all entries whose home task is task seventeen live on task seventeen, ensuring that the task processing an execution's events is the same task holding that execution's state. The root PState is keyed first by task-id and then by agent-id, the UUID assigned to each invocation. Each entry is a comprehensive execution record containing the invoke-id of the starting node, the original invocation arguments, any metadata provided by the caller at invocation time, the graph version identifying which version of the agent definition governs this execution, the final result once the execution completes, the current retry count, the ack-val used to track aggregation completion via the XOR mechanism, accumulated runtime statistics including latency measurements and token counts, the set of pending human input requests for any nodes currently paused awaiting a human response, a streaming buffer keyed by node name that accumulates streaming chunks in indexed order as they arrive, and a description of all forked child executions spawned during this invocation. The root PState is created and maintained by the stream topology.

The node PState is the execution graph store, holding one entry for every node invocation across all active and recently completed executions. Like the root PState, it is partitioned by task-id, co-locating node entries with the execution they belong to. It is keyed first by task-id and then by invoke-id, the UUID that identifies a specific invocation of a specific node within a specific execution. Each record contains the agent-id of the parent execution, the node's human-readable name, the invoke-id of the immediate parent node in the graph, and the task-id of the task that owns the parent agent's root record. Critically, it contains the emit list: a structured record of every downstream node this invocation emitted to, including the target node name, the target's invoke-id, the target's assigned task-id, and the arguments passed along. It also contains the nested operations list, which is a complete log of every significant operation performed during this node's execution — model calls with inputs and outputs, store reads and writes, tool invocations, human input requests — each with timing and result. Start and finish timestamps bracket the invocation's execution window. For aggregation nodes, the record also contains the accumulated state of the fan-in: the list of inputs received so far from upstream branches, the current partial aggregate value, and whether the aggregation has been fulfilled. The node PState is created and maintained by the stream topology.

The shared state PState holds cluster-wide coordination data that is not scoped to any single execution. It is not partitioned by execution but is instead organized by content type. It contains four principal structures. The history map records all past and current versions of the agent definition, keyed by version number, and is consulted during live module updates to determine what to do with in-flight executions. The active-invokes set is the authoritative list of all agent-ids currently running; executions enter this set when created and leave it when they complete, and it is the starting point for both the stall detector and the garbage collector. The GC-marked set is a staging area for executions that have been flagged for deletion: they have completed and passed their retention deadline, but the actual deletion of their root and node PState entries happens in the subsequent GC pass. The metadata index is an inverted map from metadata values to sets of agent-ids, enabling efficient lookup of executions by their metadata labels without scanning the entire root PState. The shared state PState is maintained jointly by the stream topology and the microbatch topologies.

The valid-invokes PState maps each agent-id to the current retry generation number for that execution. It is partitioned and co-located with the other execution PStates. The stream topology consults this PState as the very first step of processing any event: if the event's embedded retry generation number does not match the current generation stored here, the event is discarded. This fencing mechanism is what prevents events from stale, previously failed execution attempts from contaminating the state of a current retry. The valid-invokes PState is also the place where the stall detector records a new generation number when it decides to retry a stuck execution. It is written by the stall-detection microbatch topology when a stall is detected and read by the stream topology on every incoming event.

The telemetry PState holds the statistical summaries used by the analytics system to answer questions about execution performance over time. It is keyed by a three-part composite: agent name, metric identifier, and rule name. Together, these three parts identify a specific metric being tracked for a specific kind of execution under a specific analytics rule. The value stored at each key is a NumberStats structure built on top of a T-Digest sketch. A T-Digest is a compact probabilistic data structure that approximates the percentile distribution of a stream of numerical values. Rather than storing each individual measurement, it maintains a set of weighted centroids that together describe the shape of the value distribution, using memory measured in kilobytes regardless of how many millions of values have been accumulated. From a T-Digest, the system can compute approximate percentiles — the median, the ninety-fifth percentile, the ninety-ninth percentile — with bounded error and in constant time. The telemetry PState is written by the analytics microbatch topology and read by query topologies servicing the monitoring UI.

The cursor PState maps each combination of rule-id and task to the invoke-id of the last invocation processed by the analytics topology for that rule on that task. Each task in the module maintains its own cursor independently. When the analytics topology runs, it reads the root PState forward from the cursor position, processes each unprocessed invocation it finds, and advances the cursor to the invoke-id of the last invocation it processed before committing. The cursor ensures that each invocation is evaluated against each analytics rule exactly once per task, regardless of how many analytics ticks fire, and regardless of whether the topology restarts midway through a batch. The cursor PState is also the mechanism that makes historical backfill straightforward: to re-evaluate historical invocations under a new or modified rule, the cursor for that rule is simply reset to an earlier invoke-id, and the analytics topology advances it forward again from there on the next tick. The cursor PState is written and read exclusively by the analytics microbatch topology.


## Appendix D: The Execution State Machine

An execution begins in the Initiated state. This state is entered when the stream topology processes an AgentInitiate event. The topology creates a new entry in the root PState, assigning it an agent-id, recording the invocation arguments, metadata, and graph version, and initializing the ack-val and retry count. Simultaneously, the topology creates an entry in the node PState for the first node in the agent graph and schedules it by routing a NodeOp message to the appropriate task. The execution is added to the active-invokes set in the shared PState. At this point the execution exists in the system's records and its first node is queued for execution, but no user code has run yet.

From the Initiated state, the execution transitions immediately to the Running state as soon as the first node begins executing on its virtual thread. The Running state is the normal, active condition of an execution that is making progress. One or more nodes are executing, and NodeComplete events are flowing through the stream topology as nodes finish their work. Each NodeComplete causes the stream topology to update the node PState entry for the completed node with its emits, result, nested operations, and timing, then create new node PState entries and schedule new NodeOp messages for any nodes the completed node emitted to. The execution remains in the Running state so long as at least one node is still outstanding — still executing or still queued to execute. During the Running state, the root PState's last-progress timestamp is updated with each NodeComplete, providing the stall detector with evidence that the execution is alive.

A subset of the Running state is the Streaming state, entered when one or more nodes begin producing streaming output by calling the stream-chunk function. Streaming and Running are not mutually exclusive conditions — an execution that is streaming is also running — but the streaming behavior is worth describing as its own phase because it involves a distinct path through the system. When a node calls stream-chunk, the node executor appends a NodeStreamingResult event to the streaming depot rather than to the main agent depot. The stream topology processes this event and appends the chunk to the streaming buffer in the root PState, indexed by node name and chunk index. A client watching for streaming output reads from this buffer at the query topology level. Streaming ends when the node that was producing chunks completes and emits a NodeComplete; after that, the streaming buffer for that node is complete and will not receive further chunks.

The Awaiting Human Input state is entered when a node calls the get-human-input function. The node executor appends a NodeHumanInputRequest event to the human input depot. The stream topology processes this event and adds the request to the human-requests set in the root PState, recording the waiting node's name, invoke-id, and prompt. On the task where the node is running, the virtual thread that is executing that node parks itself — it suspends execution and releases its underlying OS thread, waiting to be unparked by a future response. The execution is still considered running from the perspective of the active-invokes set, but that particular node is not making progress. If the human does not respond before the stall detection threshold, the stall detector will eventually trigger a retry. When a human provides a response, a HumanInput event is appended to the human input depot, routed to the waiting node's task. The stream topology processes this event, removes the corresponding entry from the human-requests set in the root PState, and unparks the waiting virtual thread, which resumes executing with the human's response in hand.

The Retrying state is entered when a RetryAgentInvoke event is processed by the stream topology. This event is generated by the stall-detection microbatch topology when it determines that an execution has not made progress within the configured stall threshold. When the stream topology processes RetryAgentInvoke, it first checks that the retry generation number in the event matches the current generation in the valid-invokes PState — a check that prevents a delayed or duplicate retry signal from restarting an execution that has since recovered on its own. If the check passes, the topology increments the retry generation number in the valid-invokes PState, reinitializes the root PState entry for the new attempt, and schedules the first node again from scratch. Any events from the previous attempt — NodeComplete events that were in flight when the stall was detected, streaming chunks that had not yet been processed — will now arrive at the stream topology carrying the old, superseded generation number and will be discarded silently. The execution resumes from the beginning, with the same agent-id, as though it had just been initiated.

The Complete state is entered when the stream topology processes a NodeComplete event that carries a non-empty result value. A result represents a terminal output from the execution — the node that produced it declared it as the final answer, not merely as input to a downstream node. The stream topology writes the result to the root PState entry, marks the execution as complete, and removes the agent-id from the active-invokes set in the shared PState. The execution record remains in the root and node PStates — clients can still read it, the analytics topology can still process it against its cursor — but the execution is no longer live. The last-progress timestamp is updated one final time.

The GC-Marked state is entered when the garbage collection microbatch topology, running on its own tick schedule, identifies the completed execution as having passed its configured retention deadline. The topology moves the agent-id from the completed pool into the GC-marked set within the shared PState. The root and node PState entries for the execution remain fully intact at this point. The GC-marked set is a staging area, and entries are not deleted in the same pass that marks them. The two-phase approach ensures that any in-flight reads of the execution's data — from a client fetching a trace, from the analytics cursor processing the invocation — complete before the data is removed.

The Deleted state is the final state, entered in the GC pass subsequent to GC-Marking. The garbage collection topology reads the GC-marked set, removes the flagged entries from both the root PState and the node PState, and removes the corresponding entries from the GC-marked set. After this commit completes, all persistent state associated with the execution has been cleaned up. The execution no longer exists in any PState. Its record in the depots — the original events — remains there according to the depot's own retention configuration, but no derived state remains in the system. The storage footprint of that execution has been returned to the pool.


## Appendix E: The Analytics Pipeline, Step by Step

The journey of an invocation through the analytics pipeline begins before the analytics system touches it at all. It begins in the stream topology. When a node declares a final result and the stream topology processes the corresponding NodeComplete event, it writes the result, timing, and statistics to the root PState entry and simultaneously updates the node PState entry for that final node with its nested operations and finish timestamp. Alongside these writes, the stream topology removes the agent-id from the active-invokes set in the shared PState, marking the execution as complete. At this moment, the invocation has a complete and stable record in both the root PState and the node PState. It is no longer changing. It is now readable.

The analytics system does not react to this completion directly. There is no event telling the analytics topology that a specific invocation just finished. Instead, the analytics topology operates on a schedule: it wakes up when a tick fires from the analytics tick depot. When that tick fires, the analytics microbatch topology begins processing. On each task independently and in parallel, the topology reads the root PState forward from the position of the cursor — the invoke-id of the last invocation that was processed on that task for that rule. Everything recorded in the root PState after the cursor position represents invocations that have completed since the last analytics tick and have not yet been evaluated.

The topology works through these unprocessed invocations one by one within the batch. For each invocation, it begins by applying the rule's scope filter. A rule may be configured to apply to all agent types in the module, or it may be scoped to a specific agent by name. If this invocation belongs to an agent that the rule does not cover, the invocation is skipped immediately and the cursor advances past it. If the scope check passes, the topology checks the invocation's completion status: did it succeed, or did it error? Some rules are defined to evaluate only successful executions; others target only failures; others apply to both. A mismatch between the invocation's status and the rule's status scope causes the invocation to be skipped.

For invocations that pass the scope and status filters, the topology next evaluates the rule's sampling rate. If the rule is configured to evaluate only a fraction of matching invocations — say, one in ten — the topology applies a deterministic sampling function to the invocation's invoke-id to decide whether this particular invocation is in or out. This sampling is deterministic rather than random, meaning that the same invocation will always be in-sample or out-of-sample for a given rule, regardless of how many times the cursor is rewound and the batch is re-run. For invocations that are in-sample, the topology proceeds to evaluate the rule's conditions: structured filters on the invocation's input arguments, output value, metadata fields, and execution statistics. An invocation must satisfy all configured conditions to be considered a match. If any condition fails, the invocation is skipped.

For an invocation that passes all filters and conditions, the topology dispatches it to the rule's action function. The action receives the full context of the invocation: the input arguments passed to the agent, the output value it returned, the metadata it carried, the timing breakdown showing how long each node took, and any run-level information indicating which experiment configuration was active. The action does whatever it is configured to do: calling an LLM judge to evaluate output quality and storing the resulting score, adding the invocation to a dataset for later fine-tuning or evaluation, calling a webhook to notify an external system, or executing arbitrary custom logic registered by the developer. The analytics topology does not constrain what actions can do — it guarantees only that matching invocations reach the action exactly in the order they completed.

At the same time as rule evaluation, and in the same pass over the unprocessed invocations, the topology performs telemetry aggregation. For each invocation, it evaluates any metric definitions associated with the rule. A metric is defined by a value function: a function that accepts the invocation record and extracts a numerical value. Common metric value functions extract total wall-clock latency from invocation creation to completion, token counts summed across all model calls in the execution, binary success or failure indicators, or evaluator scores if an LLM judge has already run against this invocation. Each extracted value is fed into the T-Digest sketch in the telemetry PState keyed by the combination of agent name, metric identifier, and rule name. The T-Digest absorbs the new value by merging it into its compressed centroid representation, updating the sketch's approximation of the value distribution without storing the individual data point. The memory cost of this update is constant regardless of how many millions of previous values the sketch already represents.

After processing all invocations in the current batch — up to the configured maximum batch size — the topology commits. This commit is atomic. The cursor for each rule on each task advances to the invoke-id of the last invocation that was processed, the updated T-Digest sketches are written to the telemetry PState, any state produced by action functions is committed, and all of this happens together in a single microbatch commit. Either every change in the batch is durable and visible, or none of them are. If the topology fails mid-batch before committing — if a machine crashes, if the process is interrupted — Rama will restart the topology and rerun the batch from the cursor position it last committed to. Some invocations may be processed twice in this scenario, and the T-Digest may receive a value twice, but the error introduced by an occasional duplicate is negligible for statistical purposes and vastly simpler than the alternative of a true exactly-once guarantee.

After the commit, the cursor sits at a new, advanced position. Any invocations processed in this batch will not be processed again on the next analytics tick. They have been evaluated. Their metric values have been incorporated. Their cursor position has been passed. The next tick will advance the cursor further, processing whatever invocations completed between now and then.

The final leg of the pipeline is the query. The telemetry PState accumulates T-Digest sketches continuously, updated on every analytics tick, but that data is only useful when something reads it. When the monitoring UI requests analytics data — asking for the p50, p90, and p99 latency of a specific agent under a specific rule over a specific time window — it calls a query topology. The query topology is a synchronous, request-reply mechanism that runs on the task owning the relevant partition of the telemetry PState. The topology reads the T-Digest sketch for the requested combination of agent name, metric identifier, and rule name, and then evaluates the sketch to compute the requested percentiles. The T-Digest computes approximate percentiles by interpolating over its centroid representation, returning a result in constant time regardless of how many individual measurements have been accumulated. These approximate percentile values are returned to the query topology caller and from there to the UI, where they appear as the latency distribution charts in the analytics view.

The end-to-end path from NodeComplete to chart value touches the stream topology, the root PState, the node PState, the shared PState, the analytics tick depot, the analytics microbatch topology, the cursor PState, the telemetry PState, and the query topology in sequence. Each component has a single, well-defined responsibility. The stream topology records what happened. The analytics topology evaluates what it means. The cursor ensures each invocation is evaluated exactly once per rule. The T-Digest summarizes the distribution compactly. The query topology exposes the summary on demand. The pipeline is not a monolith but a chain of specialized components, each doing one thing, together turning the raw event of a completed execution into an observable data point in the monitoring system.
