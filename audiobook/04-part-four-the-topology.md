# Part Four: The Topology — How Events Become State

## Chapter 9: The Stream Topology — The Main Execution Engine

If you had to identify the single component responsible for turning an agent invocation into a running computation, it would be the stream topology. Everything else — the depots, the PStates, the node executor, the partitioner — is in service of what the stream topology does. It consumes events from the main agent depot and applies them as state transitions to the PStates. It is, in the most literal sense, the engine.

The choice of a stream topology rather than a batch topology is not incidental. In Rama, a stream topology processes events one at a time and commits after each one. An event arrives, the topology processes it, its effects become visible in the PStates, and only then does the topology advance to the next event. The consequence of this design is low latency. The time between an event arriving at the depot and its effects being visible in PStates is measured in milliseconds — not seconds, not the delay you would accumulate waiting for a batch to fill. For an interactive system where clients are waiting on results and downstream nodes are queued waiting for upstream completions, that latency difference is the difference between a system that feels responsive and one that does not.

The first thing the stream topology does when it receives any event is check whether that event belongs to the current retry generation. This check is not a minor housekeeping detail — it is the foundation of the system's retry semantics. Every execution has an associated retry number, and the valid-invokes PState tracks which retry number is current for each execution. When an event arrives carrying a retry number lower than the current value, the topology drops it silently and moves on. This is how the system achieves idempotent retries: an old NodeComplete from a previous attempt cannot affect the state of a new attempt, because the filter prevents it from reaching the state-writing logic. The system does not need to explicitly cancel in-flight nodes from old retries; it simply stops accepting their output. The events may still arrive, they just stop mattering.

When an AgentInitiate event passes the filter — which it always does, since it initiates a new execution with a fresh retry number — the topology's work is straightforward but consequential. It creates an entry in the root PState for this execution. That entry receives an agent-id, the arguments and metadata provided by the caller, a record of which graph version governs this execution, and an initial ack-val. This last item, the ack-val, will come back in Chapter 12. For now, it is enough to know it is initialized here. Alongside the root PState entry, the topology creates an entry in the node PState for the first node in the agent graph — the entry node. This entry receives an invoke-id, records the node's name and which task it is targeted to run on, and marks the node as pending. Finally, the topology schedules the first node for execution by constructing a NodeOp message and routing it to the appropriate task. At this point the topology is done with this event. It commits and advances.

NodeComplete events are the most complex case the topology handles, and understanding them is the key to understanding how the execution graph unfolds. When a NodeComplete event arrives and passes the filter, the topology first updates the node PState entry corresponding to this completion: it records the emits the node declared, any nested operations the node performed during its execution, the result if one was declared, and timing information. Then it works through the consequences.

For each emit declared in the NodeComplete, the topology creates a new entry in the node PState for the downstream child node — assigning it an invoke-id, recording which node it targets and which task will run it — and schedules it by routing a new NodeOp message. If the NodeComplete included a final result, the topology marks the root PState entry as complete and removes the execution from the active invokes set. In either case, it updates running statistics in the root entry: timing information, counts, whatever the monitoring and analytics layer needs.

This matters because of what it reveals about the system's structure. The stream topology is stateless logic applied to stateful data. Read that again, because it is the key to understanding why this architecture is reliable. The topology itself contains no mutable variables. It holds no running counts, no pending maps, no in-memory structures that can be lost if a machine fails. It reads events from a depot, reads and writes PStates, and commits. If the topology crashes mid-processing, Rama restarts it from the last committed position. The events in the depot are still there. The PStates reflect exactly the state as of the last successful commit. The topology picks up where it left off. This is what it means to build on event sourcing: the log is the ground truth, the state is derived from it, and the processing logic is free to be stateless because the log never lies.

## Chapter 10: How a Node Actually Runs

The stream topology schedules a node by constructing a NodeOp record. This record contains the node's name, the invoke-id that identifies this particular execution of that node, the arguments it was called with, and the agent context — which includes references back to the execution it belongs to and the graph version it is running under. The topology routes this NodeOp to the task identified as the target for this execution. Once the message is routed and the topology commits, the topology's job for this event is done.

On the target task, the NodeOp is picked up by the node executor. The executor is not a stream topology or a batch topology in the Rama sense — it is a component that sits alongside those topologies on the task and manages the actual execution of user code. It maintains a pool of virtual threads, and when a NodeOp arrives, it dispatches the corresponding execution onto one of them.

Before the user's function can run, the executor does one more piece of construction. It creates an AgentNode implementation and hands it to the function as its execution context. AgentNode is the interface through which the node function interacts with the outside world: it is how the function makes model calls, reads and writes stores, emits to downstream nodes, and requests human input. The executor also initializes a thread-local list that will accumulate NestedOp records — a log of every significant operation the node performs during its execution.

The user's function then runs to completion in its virtual thread. This is where the framework largely disappears from the programmer's perspective. Inside the virtual thread, the code looks and behaves like ordinary blocking code. You call a method to invoke a language model, and you wait. The thread parks on the blocking call while the model responds, and when the response arrives, execution resumes with the result in hand. You call a method to read from a store, and you wait. You call a subagent and receive its result when it finishes. From the programmer's perspective, this is the simplest possible model: sequential code, one thing after another, no callbacks or futures to manage.

While this is happening, the AgentNode implementation is silently recording. Every model call, every store operation, every tool invocation, every human input request — each one is captured as a NestedOp entry appended to that thread-local list. This recording is not optional and not something the programmer explicitly controls. It happens automatically, at the interface boundary between user code and the framework's capabilities.

When the function returns — whether because it called emit to pass a value downstream, or called result to declare a final output for the execution, or simply returned normally — the executor collects the pieces. It gathers the emits the function declared, the result if any, and the accumulated list of nested ops. It packages these into a NodeComplete event and appends that event to the main agent depot. The executor's work is done. It releases the virtual thread.

This is the key insight of the execution model: the node function never writes to any PState directly. It does not touch execution records. It does not modify the node graph. It produces one artifact — a NodeComplete event — and delivers that artifact to the depot. Everything downstream, all the state changes that represent the consequence of this node having run, flows from the stream topology processing that event. The node function is a producer. The topology is the writer.

To understand why virtual threads matter here, consider the alternative. A traditional thread pool has a fixed number of threads, and threads are operating-system resources — expensive to create, expensive to maintain, limited in number. If you have a thousand concurrent agent executions, each waiting in a blocking model call, you need a thousand threads ready to park on those calls. On most systems, a thousand OS threads is a meaningful resource commitment, and at ten thousand it becomes a serious problem. Virtual threads, introduced as a stable feature in Java 21, change the arithmetic. They are threads managed by the JVM rather than the operating system. When a virtual thread parks on a blocking operation, the JVM unmounts it from its underlying OS thread and makes that OS thread available for other work. The virtual thread resumes on whatever OS thread is available when the blocking call completes. The cost of a parked virtual thread is a small amount of heap memory, not a reserved OS thread. This means the system can sustain thousands of concurrent node executions, each waiting on a network call to a language model, without exhausting any thread pool. The concurrency scales with heap memory, not with operating system limits on threads. For a system whose primary bottleneck is waiting on external model providers, this is exactly the right property.

## Chapter 11: Partitioning and Co-location — Why It's Fast

Performance in a distributed system does not come from raw computation speed. It comes from reducing the fraction of time spent waiting for data to travel across a network. The design of Agent-o-rama's partitioning strategy is built around one central commitment: when a task is doing work on behalf of an execution, the data that work requires should already be on that task. This is the principle of co-location, and it shapes every routing decision in the system.

When an agent execution begins, it is assigned to a specific task in the Rama cluster. This is the home task for that execution, and the identifier for this assignment is the agent-task-id. The assignment is not random in the sense of being arbitrary — it is stable for the lifetime of that execution. Every subsequent event related to that execution will be routed to the agent-task-id.

The routing mechanism is the custom depot partitioner. In Rama, a partitioner is a function that takes an event and returns the task that should receive it. Agent-o-rama's partitioner inspects each event and reads the routing key directly from the event structure. For a NodeComplete event, the routing key is the agent-task-id embedded in the event. For a streaming chunk, it is the agent-task-id of the execution that generated it. For a human input response, it is the agent-task-id of the execution that is waiting on it. The partitioner never computes a task from scratch — it reads a task assignment that was made upfront and stored in the event. This makes routing deterministic and free of coordination.

Now consider the PStates. The root PState and the node PState are both partitioned by task-id. This is the other half of the co-location strategy. Because the PState data for a given execution lives on the same task as the events for that execution, the stream topology running on that task can read and write PState without a network round-trip. When a NodeComplete arrives at the home task, the topology looks up the corresponding node PState entry — which is local — writes the updated fields — local — creates new node entries — local — and commits. No network hops. This is fast not because any individual operation is particularly optimized, but because the operations are composed from pieces that are all present in the same place.

The more interesting case is what happens when a node emits. When the stream topology processes a NodeComplete that contains emits, it needs to create entries for the child nodes and schedule them. Each child node gets a new invoke-id. Each child node also gets a target-task-id, and the choice of target-task-id is where the system's fan-out behavior comes from.

For regular nodes — nodes that process independently and do not need to share accumulation state with siblings — the target task is chosen at random from the cluster. If a node emits ten times, ten child nodes are created, potentially each assigned to a different task. Each of those ten executions runs on its assigned task, parks a virtual thread on a model call, and eventually produces a NodeComplete that routes back to its own home task for processing. The work is distributed across the cluster without any single task becoming a bottleneck.

For aggregation nodes — nodes whose purpose is to combine results from multiple upstream siblings — the story is different. Aggregation nodes that are accumulating state must stay co-located with that state. All results flowing into an aggregation node are routed to the same agg task, the task that owns the accumulation PState for that aggregation. This means that no matter which tasks the parallel child nodes ran on, their results converge on the agg task. Think of it this way: the fan-out spreads work across the cluster, and the fan-in pulls results back to a single point where they can be combined. That convergence point is determined at the start of the aggregation, not dynamically as results arrive.

Store writes follow the same logic. The PState backing a user-defined store is partitioned by key. The write depot routes each write operation to the task that owns that key's partition. The co-location here is not between an execution and its store, but between a store key and its data. Writes to the same key always land on the same task, which means the task processing those writes can update its local PState without coordination.

The design philosophy that ties all of this together is worth making explicit. The goal is not to minimize the number of tasks involved in a computation. A complex fan-out will genuinely involve many tasks — that is correct behavior, because that distribution is what provides parallelism. The goal is to ensure that when a task is involved, it has everything it needs locally. The home task for an execution has the execution's PState. The agg task has the aggregation's state. The store task has the key's data. Each task operates on local data. The network traffic in the system is dominated by routing events to their destinations, not by fetching data from remote tasks to process an event. That asymmetry — routing is network traffic, processing is local — is the source of the system's performance.

## Chapter 12: The XOR Ack-Val — How Aggregation Completion Is Detected

Consider the problem that aggregation solves, stated precisely. A node emits some number of times to a set of parallel child nodes. Each child node runs independently, possibly on different tasks, and each eventually produces a result. Those results must be collected by an aggregation end node, which should fire exactly once when all children have reported back. The difficulty is not in collecting results — that is straightforward — but in knowing when the collection is complete.

The number of children is not known before the fan-out begins. It depends on how many times the start node emits, which depends on the start node's runtime behavior, which depends on its inputs. You cannot tell the aggregation end node to wait for five children if you do not know it will be five until the start node has finished running. You might think to use a counter: increment it each time a child is created, decrement it each time a child completes, and fire the end node when the counter reaches zero. This works logically, but it has a structural problem. A counter that must be incremented and decremented from multiple tasks is a shared mutable variable with contention. Every increment and decrement requires coordination with wherever the counter lives. In a distributed system with a large fan-out, that coordination point becomes a serialization bottleneck. All the parallelism you gained by distributing the child nodes across the cluster is potentially undone by the queue of tasks waiting to update a counter.

Agent-o-rama uses a different mechanism, one that does not require a single coordination point and does not require knowing the final count upfront. It is called the ack-val, and it is initialized in the root PState when an aggregation begins. The ack-val starts as a large random number — think of it as half of a random UUID, large enough that collisions are not a practical concern.

Each time the start node emits to a child, two things happen. A new random number is generated. That number is XORed into the ack-val. The ack-val is now the original value XOR'd with this new contribution. When the child node eventually completes and reports back to the aggregation context, the same number — its contribution — is XORed back out. The ack-val returns to what it was before this child was added.

To understand why this works, consider what happens when all children have reported back. Each contribution was XORed in when the child was created, and XORed out when the child completed. The net effect is zero: the ack-val is exactly equal to its initial value. The stream topology monitors this condition. When it processes a child's completion and finds that the ack-val has returned to its starting value, it knows all children have reported. It fires the aggregation end node.

The mathematical properties that make this work are worth understanding, because they are the properties that make XOR the right operation for this use case rather than, say, addition. XOR is commutative: the order in which contributions are applied does not matter. Whether child A completes before child B or after, the effect of XORing both their contributions is the same. This means the ack-val does not accumulate error from out-of-order arrivals. XOR is also self-inverse: applying the same value twice cancels out to zero. This means the XOR-in and XOR-out operations are symmetric — the same operation that adds a contribution removes it. And because each contribution is a large random number, the probability that two different children's contributions cancel each other out before their respective completions is negligible. The ack-val only returns to its initial value when every contribution that was added has been removed.

The practical implication is significant. The system never needs to know how many children will be created before it starts creating them. Each emit atomically updates the ack-val by XORing in a fresh contribution. Each child completion atomically XORs out its contribution. The agg task monitors the ack-val. That is the entire mechanism. There is no counter to serialize updates to, no barrier waiting for a predetermined count, no coordination step between the task running the start node and the task watching the ack-val.

Nested aggregation works by the same mechanism, applied at each level independently. Each level of nesting maintains its own ack-val in its own node PState entry. The outer aggregation's ack-val is updated not when individual inner children complete, but when the inner aggregation's end node fires — which itself fires only when the inner ack-val has returned to its initial value. The outer aggregation is not waiting for inner leaves; it is waiting for inner end nodes. Each inner end node is itself waiting for its own children via its own ack-val. The synchronization is nested correctly without any explicit coordination between levels.

There is a deeper observation here about design constraints and the choices they force. The requirement that the system should not have a centralized coordination bottleneck is a hard constraint, not a soft preference. Meeting it requires finding operations that are inherently distributed — operations where each participant can contribute independently and the combination has a detectable final state. Most operations do not have this property. Addition does not: while you can add contributions independently, detecting whether the sum has reached a target requires knowing the target in advance. Comparison does not: you cannot meaningfully compare partial results without knowing what the full set looks like. XOR does: each contribution cancels itself out when removed, and the identity state — all contributions removed — is detectable without any knowledge of how many contributions there were. The cleverness is not in the implementation. The cleverness is in recognizing that this problem's shape exactly matches XOR's properties, and in designing the rest of the system to make that match possible.

When you encounter this kind of fit between a mathematical operation and an engineering problem, it is usually a sign that someone thought carefully about the structure of the problem before reaching for a solution. The ack-val mechanism is one of those signs.
