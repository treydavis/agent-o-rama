# Agent-o-rama: How It Really Works

## Preface

This book is not a tutorial.

There are already excellent resources for learning how to use Agent-o-rama: a quickstart guide, full documentation, Javadoc, Clojuredoc, a documentation chatbot, and a collection of example projects. If you want to build an agent, those are the right places to start. This book has a different purpose. It is an explanation of how Agent-o-rama works on the inside — what actually happens in the system when you call invoke on a client, when a node emits to its neighbor, when a fan-out of ten parallel branches eventually collapses back into a single result, or when a streaming chunk reaches a registered callback in a remote client.

The goal is to give you a mental model precise enough to be genuinely useful. Not the vague sense that "it uses some kind of event system," but a working understanding of which data structures hold what, which components write to them, in what order, and why the sequence was designed that way. By the end of this book, Agent-o-rama should feel less like a framework you invoke and more like a system you understand — a set of deliberate design choices built on top of a distributed computing platform, each choice traceable to a concrete requirement.

Understanding implementation makes you a better practitioner in ways that documentation alone cannot. When you know that NodeComplete events are the unit of state change, you understand what it means for an argument list to be large. When you know that streaming chunks travel through a separate depot from the main execution flow, you understand why high-volume streaming does not starve other agents competing for throughput. When you know how the XOR acknowledgment mechanism detects aggregation completion, you stop thinking of fan-out-and-join as magic and start thinking of it as arithmetic. And when something goes wrong in production — a stalled execution, an unexpected retry, a streaming buffer that seems behind — you will have a vocabulary for reasoning about the failure rather than waiting for someone else to explain it.

The background this book assumes is modest but specific. You should understand what an append-only log is: a data structure to which records are appended in order, never modified in place, and readable from any position. You should have a working mental picture of a distributed indexed data structure: something like a large hash map that is partitioned across many machines, where a key hashes to a specific partition and that partition lives on a specific machine. And you should have a rough idea of what it means to run code on a distributed cluster: that there are multiple machines, that work is assigned to specific machines, and that communicating between machines costs more than operating on data that is already local. You do not need prior experience with Rama, the distributed computing platform on which Agent-o-rama is built. The book introduces Rama's abstractions from the ground up, using the plain-language vocabulary that makes them approachable.

What this book does not assume is familiarity with Agent-o-rama's source code. The internal implementation is described in conceptual terms, through the lens of what each component is responsible for and how it interacts with the others. Where the system uses specific names — NodeComplete, AgentInitiate, the root PState, the XOR ack-val — those names are used here too, because using the system's own vocabulary is the most direct path to a model that matches what the system actually does.

The arc of the book follows the natural layering of the system. Part One introduces Rama's core abstractions and the architectural pattern — event sourcing — that shapes everything above it. Part Two catalogs the depots that form the input layer of the system: where events originate, how they are partitioned, and why certain concerns are separated into their own depots. Part Three examines the PStates: the persistent state of the execution system, how they are structured, and what each piece of data represents. Part Four traces the stream topology that turns depot events into PState updates — the main execution engine. Parts Five and Six cover the specialized depots and the microbatch topologies that handle streaming, human input, retry detection, analytics, and garbage collection. Parts Seven and Eight address advanced mechanics and then step back to take a complete view, walking through a single agent invocation from start to finish and examining the tradeoffs embedded in the design.

The tone throughout is serious and technical. This is a book for practitioners who want to think clearly about a system they depend on. Warmth does not mean imprecision. Where the explanation requires careful attention — particularly around the XOR acknowledgment mechanism, the partitioning strategy, and the cursor-based analytics pipeline — the writing slows down and works through the ideas step by step. The goal is not to impress you with the system's cleverness. The goal is to make the system legible.

One final note before we begin. Agent-o-rama is built entirely on top of Rama, and it is genuinely inseparable from Rama's primitives. The co-location strategy depends on Rama's partitioning model. The retry semantics depend on Rama's exactly-once processing guarantees. The live-query mechanism that delivers a result to a waiting client depends on Rama's foreign proxy system. Understanding Agent-o-rama's internals therefore requires understanding Rama, and so Part One spends two full chapters on exactly that. If you are already deeply familiar with Rama, you may find those chapters move quickly. If Rama is new to you, they are essential. Either way, everything that follows builds on them.

Let us begin.

# Part One: The Foundation — What Rama Provides

## Chapter 1: Rama in Plain Language

Before we can understand how Agent-o-rama works, we need to understand the platform it is built on. Rama is a distributed computing platform — meaning it is a system for building applications where both the state your application maintains and the computation that operates on that state are spread across many machines, with the platform taking responsibility for the hard problems that come with that distribution: durability, fault recovery, partitioning, and consistency. If you have built systems that combine something like Kafka for event streaming, a distributed key-value store for persistent state, and a stream processing framework for computation, you already have an intuition for what Rama provides. The difference is that Rama unifies all of those concerns into a single coherent model, with tight integration between the pieces and stronger guarantees at the boundaries between them.

To understand Rama, you need to understand three abstractions. These are not implementation details — they are the vocabulary through which you reason about everything that Rama does and everything that Agent-o-rama does on top of it.

The first abstraction is the depot. A depot is an append-only, partitioned, durably stored event log. Think of it as similar in spirit to a Kafka topic, but with deeper integration into the rest of the platform. You interact with a depot by appending events to it. Once an event is appended, it is stored durably and replicated according to the configured replication factor. Events in a depot are ordered within each partition. Critically, a depot is not just passive storage — it is the trigger for computation. Topologies, which we will discuss in a moment, subscribe to depots and process events as they arrive. This tight coupling between log and computation is what distinguishes a Rama depot from a message broker you have bolted onto a processing framework as a separate operational concern.

The second abstraction is the PState. PState stands for partitioned state, and a PState is a distributed, indexed data structure — the persistent state layer of your application. The best mental image is a very large nested map: you can store any structure of maps and lists and values at any path, and all of it is partitioned across the cluster, replicated for durability, and kept up to date as topologies write to it. You can read a PState from anywhere in the cluster through a mechanism called a foreign proxy, which reads across the network and returns the current value at a given path. You can also define reactive subscriptions on a PState so that when a value changes, something is notified. PStates are strongly consistent within a partition: two writes to the same partition are serialized, and readers on the same partition see a consistent view. This matters enormously for the kinds of guarantees Agent-o-rama provides.

The third abstraction is the topology. A topology is the computation layer of a Rama module. It is a dataflow definition — you describe how events flowing from a depot are transformed and what effects they have on PStates. Topologies come in two flavors, and the distinction between them is one of the most important design decisions in the Rama model.

Stream topologies process events one at a time. An event arrives at the depot, the topology picks it up, processes it, writes any resulting changes to PStates, and commits. The latency is low — typically measured in single-digit milliseconds — because there is no waiting for other events. Stream topologies are the right choice when you need fast responses to individual events.

Microbatch topologies process events in time-windowed batches. Instead of committing after each event, a microbatch topology accumulates events over a configurable time window and then processes the entire batch together as a single atomic unit. This trades latency for coordination power: within a single batch commit, a microbatch topology can look at the aggregate state of many events, make coordinated decisions across them, and commit all resulting state changes atomically. Microbatch topologies are the right choice when you need to reason about multiple events together — when the question you are asking cannot be answered event by event.

Agent-o-rama uses both flavors, and the choice of which to use for which subsystem is a deliberate architectural decision that we will return to in depth.

Now we need to understand partitioning, because it is central to everything Agent-o-rama does to achieve performance. Both depots and PStates are partitioned. This means that the data in each of them is divided into segments — partitions — and each partition is assigned to a specific task. A task is Rama's term for a unit of computation: a thread (or thread pool) running on a specific machine, responsible for a specific set of partitions. When you configure a module to run with thirty-two tasks, you are saying that the depots and PStates in that module will each be divided into thirty-two partitions, and the work of processing events and maintaining state will be spread across those thirty-two tasks, which in turn can be spread across as many machines as you have in your cluster.

This matters because of a concept called co-location. If a piece of data in a PState lives on task seventeen, and a topology is processing an event that needs to read or write that data, and the topology is currently running on task seventeen, then the read or write is entirely local. No serialization. No network call. Just direct access to the data structure in memory. This is a task-local operation, and it is orders of magnitude cheaper than a read that requires crossing a network boundary to another machine.

To understand why this matters for agents, consider what happens during a typical agent execution. The topology must look up the agent's execution record to see what state it is in. It must update that record when a node completes. It must create new records for child nodes. It must write timing data, token counts, and nested operation logs. All of this happens for every single node that runs. If each of those operations required a network round-trip to a different machine, the overhead would accumulate quickly. By co-locating the execution state with the task that processes the corresponding depot events, Agent-o-rama ensures that this hot path — the sequence of reads and writes that happens on every node completion — stays entirely within a single task's memory.

The partitioning scheme is not automatic. You must design it deliberately. Rama provides a mechanism to attach a custom partitioner to a depot: a function that takes an incoming event and returns which partition it should go to. Agent-o-rama's main depot uses a custom partitioner that reads a target task identifier from the event itself. This is how the system ensures that all events for a given agent execution end up on the same task. We will examine this mechanism in detail when we cover the depot architecture.

There is one more Rama concept that plays an important role: the query topology. A query topology is a synchronous, request-reply mechanism. You define a query topology as a named procedure that accepts arguments, reads from one or more PStates, and returns a result. A client invokes a query topology by name, passing arguments, and receives back a result. Internally, Rama routes the invocation to the right task for the data being queried, executes the read logic, and returns the result synchronously. From the caller's perspective, it behaves exactly like a function call. This is how the Agent-o-rama web UI and client library retrieve traces, invocation lists, experiment results, and other data from the live PStates. The query topology layer is what makes synchronous reads possible on top of an otherwise asynchronous, event-driven architecture.

With these three abstractions in hand — depots, PStates, and topologies — and the supporting concepts of tasks, co-location, and query topologies, you have the vocabulary you need to understand everything that follows. The system is built from these primitives, and its design reflects their properties in every layer.

## Chapter 2: The Event-Sourcing Perspective

The architectural pattern underlying all of Agent-o-rama's execution machinery is event sourcing. Understanding this pattern deeply is not optional background — it is the key that unlocks the rest of the book. Every design decision in the system either follows from event sourcing or exists to extend event sourcing into areas where the naive approach would create problems.

Event sourcing is a way of designing systems where state is not mutated directly. Instead, every change that needs to happen is first recorded as an event in an immutable log. A separate process — in Rama's model, a topology — consumes that log and derives the current state of the system from it. The log is the source of truth. The state you can read out of a PState is not primary storage; it is a materialized view, a projection derived from the events. If you lost all your PStates but kept your depots, you could replay the depot from the beginning and reconstruct the same PState state you had before.

This might sound like an indirect way to manage state, and it is. The indirection is the point. To understand why, consider the alternative: a system that updates its state directly when something happens. A node completes its work, and the system immediately writes the result to a database. This is simpler to reason about locally, but it creates serious problems in a distributed system. What if the write fails partway through? You have partial state and no record of what was intended. What if the node fails and retries? How does the retry know which writes already happened? What if two replicas of the system are both trying to update the same record at the same time? Without the log as an intermediary, you must answer these questions through coordination mechanisms — locks, two-phase commits, idempotency tokens — each of which adds complexity and failure modes.

With event sourcing, these problems are solved structurally. The event is durable before the state change happens. If the topology that processes the event fails midway through updating a PState, Rama will replay the event onto another instance of the topology. The topology will run the update again, and because PState writes in Rama are deterministic given the same input, the result will be the same as if the first attempt had succeeded. Retries are not a special case to be handled with extra logic — they are the normal operation of a system that derives its state from a log.

The implication for ordering is equally significant. Within a single partition, events are processed in the order they arrive. If event A is appended before event B on the same partition, the topology will process A before B, and the state produced by processing A will be visible to the processing of B. This total ordering within a partition is a foundational guarantee. It means you can reason about what state exists when an event is being processed, because you know exactly which prior events have already been handled.

Fault recovery in this model is automatic. If a machine goes down mid-execution, Rama identifies which partition that machine owned, reassigns those partitions to other machines, and replays the unprocessed events from the depot onto the new machines. No data is lost because the events were already durable in the depot before any computation began. No custom recovery logic is needed because the topology is designed to be a pure function from events to state changes. The recovery is transparent.

Now apply this to Agent-o-rama specifically. When a node function completes its work — it has called a language model, received a response, and decided to emit to the next node — what happens? The node does not write the result to any PState directly. It does not update the agent's execution record. It does not create the next node's entry in the node state. It does none of these things. Instead, the node executor collects everything the node produced — its emits, its result if it declared one, the log of nested operations it accumulated while running — and packages all of that into a single event called NodeComplete. That event is appended to the main agent depot. Then the stream topology processes the NodeComplete event, and the topology is the thing that performs all the PState updates.

This separation is precise and intentional. The node function is a pure producer of intent — it describes what happened and what should happen next. The topology is the sole writer of state. Nothing else in the system is permitted to write directly to the PStates that the topology owns.

To understand why this matters practically, consider what happens when a node fails. Perhaps the language model API timed out. Perhaps the virtual thread was interrupted. Perhaps the machine it was running on went down. In any of these cases, no NodeComplete event was successfully appended to the depot. The depot contains only events for things that actually completed. If the retry logic decides to run the node again, the new attempt runs from scratch, produces a new NodeComplete event, and the topology processes that new event. The failed attempt left no partial state because it never wrote any state. It simply produced no event. This is the retry safety that event sourcing provides, and it is the foundation of Agent-o-rama's reliability guarantees.

The same property makes the stall detection system possible. The stall detector is a periodic process that examines running executions and identifies ones that have not made progress recently. Progress is defined as a NodeComplete event being processed. If no NodeComplete has been processed for a given execution within a configured window, the stall detector concludes that the execution is stuck — perhaps its node is running on a machine that became unresponsive, or perhaps some other failure has left it in a state it cannot exit from on its own. The stall detector then synthesizes a retry event and injects it into the depot. Because the entire history of the execution is in the log, and because the PState reflects exactly the events that have been processed, the execution can be restarted cleanly. The stall detector does not need to know the internal state of the node that was running. It just needs to know that no progress event arrived. The log is the truth, and the log is complete.

The fork-and-replay feature in the web UI follows the same logic. When you take a completed execution and say "run it again with these different arguments," the system does not need to invoke any special replay mechanism. It looks at the event log and the materialized state in the PStates, determines which parts of the execution graph are upstream of the change you made, and constructs a new execution that replays the unchanged parts from cached state while re-running the affected parts fresh. All of this is possible because the execution history is a precise, immutable record of what happened, stored in the depots and materialized in the PStates.

There is a cost to event sourcing that is worth naming. Write amplification: every state change requires two writes, one to the depot as an event and one to the PState as a materialized update. In a system that handles millions of node completions per hour, this doubles the number of storage writes compared to a direct-mutation design. Agent-o-rama accepts this cost because the benefits — retries, recovery, stall detection, fork-and-replay, cursor-based analytics — all depend on it. The decision is not made carelessly; it reflects a deliberate judgment about what a production agent system needs to be reliable.

The event-sourcing perspective also shapes how you should think about the PStates. A PState is not a database in the traditional sense. It does not define what is true. The depots define what is true. The PStates are derived views of that truth, optimized for efficient query access. If you ever want to ask "why does this execution record look the way it does," the answer is always in the depot: find the NodeComplete events that correspond to that execution, read them in order, and you have the complete causal history.

This is the mental model you should carry into every chapter that follows. When we talk about a topology updating a PState, remember that the topology is consuming an event that is already durable in the depot. When we talk about retry safety, remember that retries work because the node never wrote state directly. When we talk about the stall detector or the analytics cursor or the garbage collector, remember that each of these systems operates on the same event log and the same materialized state, and their correctness depends on that log being the authoritative record of what happened.

Event sourcing is not a trend Agent-o-rama adopted for aesthetic reasons. It is the structural foundation that makes the system's reliability properties possible. Everything else we will discuss in this book is built on top of it.

# Part Two: The Depot Architecture

## Chapter 3: The Main Agent Depot

Every agent defined in Agent-o-rama has its own dedicated depot. Not a shared channel, not a topic where all agents compete for attention — a depot belonging entirely to that agent, carrying every event that drives its execution from first invocation to final result. Think of it as the central nervous system of that agent's runtime life. Every heartbeat of an agent execution passes through this depot: the initial call, the news of each completed node, the signals to retry, the commands to fork. If you want to understand what has happened and is currently happening to an agent execution, this depot is where the record lives.

The depot does not use a standard hash partitioner. Instead, the Agent-o-rama team defined a custom partitioner that shapes how events are routed across the cluster. The logic is deliberate: if an event carries an explicit target task identifier, the partitioner sends that event directly to that task. If no task identifier is present, the event goes to a randomly selected task. This two-path routing is not an accident — it is the mechanism that makes co-location possible.

To understand why co-location matters, consider what happens at the start of an execution. An AgentInitiate event arrives at the depot without a target task identifier, so the partitioner selects a task at random. Let's say that task is task seventeen. The stream topology running on task seventeen processes the event and creates the execution's root records in its local PStates. From this point forward, every subsequent event that belongs to this execution will carry task seventeen as its target. Node completions carry it. Failure notifications carry it. Retry signals carry it. This embedded task identifier is what keeps the entire execution co-located — every event routes back to the same task, which means every read and write during the hot path of execution touches state that lives on that same task, without any network hop. The custom partitioner is the implementation of that guarantee.

The main agent depot carries five principal event types, and understanding each one is essential to understanding how execution actually works.

The first is AgentInitiate. This is the event that starts everything. When a client calls an agent, it appends an AgentInitiate to this depot. The event carries the invocation arguments, the execution metadata, the source identity of the caller, and optionally a forced task identifier or a forced agent identifier — both of which are used by the system when it needs precise control over placement, as in forking or in testing scenarios. Absent those forced values, the partitioner selects a task at random. The stream topology processes AgentInitiate by creating the root execution record, assigning a unique agent identifier, and scheduling the first node for execution.

The second event type is NodeComplete. This is the most frequent event in the system — every time a node finishes executing, a NodeComplete is what carries the news. The event contains the unique invoke identifier of the node that finished, the task it ran on, the retry number of the execution it belongs to, and the return value of the node function itself. It also carries the full list of emits the node declared: each emit specifies the target node name, the task that target node should run on, a freshly generated invoke identifier for the child, and the arguments to pass along. On top of that, NodeComplete carries any streaming information the node produced, and the complete list of nested operations recorded during execution — every model call, every store read, every tool invocation, every subagent call, each one captured as a structured entry with timing and outcome. The stream topology unpacks all of this and uses it to update the execution's state: recording what happened, creating new entries for the child nodes declared by the emits, and routing those child nodes off to their target tasks for execution.

The third event type is NodeFailure. When a node raises an exception, rather than completing, the node executor packages the exception and context into a NodeFailure event and appends it to the depot. The stream topology processes this by triggering the retry machinery: checking how many retries have occurred, deciding whether to retry the node or to escalate to an agent-level retry, and taking the appropriate action.

The fourth event type is RetryAgentInvoke. This is a synthetic event — it is not produced by a node, but by the stall detection system. The stall detector fires periodically and scans active executions looking for any that appear stuck: executions that have been running for longer than the configured threshold without producing a NodeComplete. When it finds one, it appends a RetryAgentInvoke to the main agent depot. This event carries the agent task identifier, the agent identifier, and the expected retry number. When the stream topology processes it, the execution is reset: the root PState entry is reinitialized, the retry count increments, and the first node is scheduled again from scratch. The retry number embedded in the event also serves as a fencing mechanism — any events from the previous stalled execution that are still in flight in the depot will arrive with the old retry number, and the stream topology's first step on every event is to verify the retry number is still current.

The fifth event type is ForkAgentInvoke. This event starts a new forked execution derived from an existing one. It carries the original execution's agent task identifier and agent identifier, along with a map from the original execution's node invoke identifiers to new argument lists. The fork feature is how the web UI's fork-and-replay capability works: you take a completed execution, modify some inputs, and replay it — the system creates a new execution that reuses cached results for the unchanged portions of the graph and re-executes only the affected parts. ForkAgentInvoke is also the mechanism behind experiments that compare different argument configurations against the same agent definition.

There is something important to understand about the role this depot plays beyond mere transport. A transport mechanism carries data from one place to another and then forgets it. This depot is not that. Because it is a Rama depot — an append-only log with durable storage — the record of every event is preserved. The fact that events are durable and ordered is what gives the execution model its reliability guarantees. When a machine fails mid-execution, Rama's fault recovery mechanism replays unprocessed events from the log onto a replacement machine. The execution does not need to know this happened; it simply continues processing events from where it left off. When the stall detector needs to assess whether an execution is stuck, it can consult the state derived from the event log. When a fork needs to replay a previous execution's graph, the node PState populated by NodeComplete events is the record it reads from. The depot is not a channel — it is the source of truth for what happened and when.

## Chapter 4: The Supporting Depots

The main agent depot handles execution. But execution is not the only concern an agent system has to manage. Streaming output, human input, configuration changes, garbage collection, analytics, global shared state, and safe writes to user-defined stores — each of these is a distinct concern, and each has its own depot. Understanding the supporting depots means understanding how Agent-o-rama divides its responsibilities and why each division was drawn where it was.

The streaming depot carries NodeStreamingResult events. Each event contains a chunk of data, the agent task identifier, the agent identifier, the node name, the invoke identifier of the specific node invocation that produced the chunk, a monotonically increasing index number, and the retry number. The retry number matters here for the same reason it matters in the main depot — if a node fails and restarts, streaming chunks from the failed attempt need to be discardable. The index number is what allows chunks to be reassembled in the correct order even if they arrive slightly out of sequence. The partitioning strategy for the streaming depot routes events by agent task identifier, which means streaming data always lands on the same task as the agent execution that produced it. This co-location is intentional: the stream topology handler for streaming events updates the root PState's streaming buffer, and having the streaming data arrive on the task that owns the root PState keeps that write task-local. The more architecturally significant decision, though, is the existence of a separate streaming depot at all. Streaming chunks can be large, and they arrive frequently. If they traveled through the main agent depot, they would share space and processing time with the NodeComplete events that are critical to execution progress. Isolating streaming to its own depot keeps the hot path of execution clear and uncontested.

The human input depot carries two event types that work in tandem. When a node pauses to wait for human input, a NodeHumanInputRequest event is appended to this depot, carrying the agent task identifier, the agent identifier, the node name, the specific invoke identifier of the waiting node, the task that node is running on, and the prompt string the human needs to answer. When a human provides a response — through the web UI or through the client API — a HumanInput event is appended to the same depot, carrying the original request record and the response string. The partitioner for this depot routes NodeHumanInputRequest events by agent task identifier and routes HumanInput events by the task identifier of the node that originally requested the input. This distinction reflects what co-location means for each type: the request must arrive where the agent execution lives, but the response must arrive where the waiting node lives, which may be a different task if the execution has spread across the cluster.

The config depot carries ChangeConfig events for per-agent settings. The most prominent example is the maximum retry count, which operators can adjust through the web UI without redeploying the module. Config changes are rare — they happen on human timescales, not execution timescales — and they do not need to be co-located with any particular execution. So the config depot uses random partitioning. Every task that processes the stream topology will receive and apply config updates, keeping all tasks consistent over time, without any requirement that a config event land on a specific task.

There are two time-driven depots, each firing on a schedule. The check-tick depot fires periodically — by default every several seconds — and drives the stall detection system. When a tick fires, the stall-detection microbatch topology wakes up and scans the set of active agent executions, checking each one for signs of progress. The GC tick depot fires on a slower schedule and drives garbage collection of completed executions. Completed executions remain in the PStates until the GC mechanism cleans them up according to the configured retention policy. The two separate tick depots reflect the fact that these two concerns operate at different time granularities and have different cost profiles: stall detection needs to fire frequently enough to catch stuck executions before they hold resources for too long, while garbage collection can afford to run less often.

The PState write depot handles all writes to user-defined stores: key-value stores, document stores, and PState stores. When a node running inside a topology writes to a store, that write does not go directly to the backing PState. Instead, it is recorded as a PStateWrite event and appended to this depot. Each event carries the store name, the path expression describing what to write, the value to write, and the agent source context — which includes the agent task identifier, agent identifier, and retry number. The partitioner routes writes by key, using a hash partitioner that sends each write to the task owning the relevant partition of the backing PState. This indirection exists to provide retry safety. Because the write is an event in a depot, the stream topology that processes it can check the retry number before applying the write. If the agent has since been retried and the write is from a now-stale execution, the topology simply discards it. Without this indirection, a write from a failed execution that happened to complete successfully before the failure occurred could be applied again during the retry, potentially creating inconsistent state. The depot ensures the write happens exactly once, attributable to exactly the right execution generation.

The analytics tick depot fires periodically and wakes up the analytics microbatch topology, which is responsible for rule evaluation and telemetry aggregation. When the tick fires, the analytics topology scans recently completed invocations from a cursor position, evaluates configured rules against them, applies actions for matching runs, and accumulates metric values into the telemetry PState.

The global actions depot carries mutations to shared global state — the additions and removals of rules, evaluators, human metrics, feedback queue configurations, datasets, experiment configurations, and similar cross-cutting concerns. These events are processed by the analytics microbatch topology rather than by the per-agent stream topology, because they affect global state that all agents share rather than the state of any individual execution. Random partitioning is used here, consistent with the same reasoning applied to the config depot: global actions are infrequent and do not need to be co-located with any specific task's execution state.

Taken together, these depots form a deliberate division of concerns. The main agent depot owns the execution lifecycle. The streaming depot owns output delivery. The human input depot owns the pause-and-resume lifecycle of human interaction. The config depot owns operator settings. The tick depots own time-driven maintenance. The PState write depot owns safe mutation of user-defined state. The global actions depot owns mutations to the module's shared configuration. Each depot has its own partitioning strategy, and each strategy reflects what co-location means for that specific class of events. Where events need to land on the same task as an execution, the partitioner carries a task identifier. Where events are global or infrequent, the partitioner uses random distribution. The sum of these choices is a system where the hot path of agent execution is isolated, protected, and fast, while auxiliary concerns run on separate rails without interfering.

# Part Three: The PState Architecture

## Chapter 5: The Root PState — Where Agent Executions Live

Every agent invocation that enters the system eventually finds a home in the root PState. This is the primary state store of the execution engine — a large, partitioned map whose keys are agent-ids, each a UUID generated at the moment of invocation, and whose values are records that capture everything meaningful about a running or completed execution. If you want to know whether an agent finished, the root PState has the answer. If you want to know what it returned, the root PState has that too. If you are watching a streaming response arrive chunk by chunk, the buffer accumulating those chunks lives in the root PState. It is, as the name suggests, the root of the system's observable state.

To understand how this PState is organized, you need to understand how it is partitioned. In Rama, every PState is divided across the tasks that make up a topology, and each entry in the PState lives on exactly one task. The partitioning key for the root PState is not the agent-id itself — it is the task-id, a number assigned at invocation time that determines which task owns that execution. All entries whose task-id equals seventeen live on task seventeen. This means that when the execution engine is doing work on behalf of an agent assigned to task seventeen, all the state reads and writes for that execution are local — no network hop required. This co-location between computation and state is one of the central performance properties of the system, and the root PState's partitioning scheme is what makes it possible.

What does a root record actually contain? The first field worth understanding is the invoke-id of the starting node. Every node execution in Agent-o-rama is identified by its own UUID, called an invoke-id, and the root record holds the invoke-id of the very first node in the graph — the entry point from which the entire execution tree fans out. This is the handle the system uses when it needs to traverse the execution from the beginning. Think of it as the address of the first page of a book whose subsequent pages may be scattered across the cluster.

The root record also holds the original invocation arguments and any metadata passed at invocation time. These are the inputs the caller provided when they asked the system to run this agent. Alongside them sits the graph version: a number identifying which version of the agent definition this execution is running against. Agent-o-rama supports live updates — the graph of nodes that defines an agent can change while executions are in flight — and the graph version is how the system tracks which code a given execution belongs to. This matters because when an update arrives, the system has to decide what to do with executions that are already running: should they continue on the old version, restart on the new one, or be dropped? The graph version in the root record is the basis for making that decision consistently.

Once an execution completes, the root record is updated with the final result. Until then, that field is empty, and the emptiness itself is meaningful — it signals that the execution is still in progress. Alongside the result sits the current retry count, incremented each time the system determines that an execution needs to run again. These two fields together let an observer determine not just what happened but how many attempts it took to get there.

The ack-val is a field that may seem opaque at first. It is a number used to coordinate across parallel execution branches — a mechanism whose full significance will not become clear until the discussion of fan-out and join in a later chapter. For now, it is enough to know that the root record carries it and that the system writes to it as execution branches spawn and complete.

Aggregated statistics accumulate in the root record throughout an execution's lifetime. These include latency measurements, token counts from model calls, and a tally of node executions. They are updated incrementally as the execution proceeds rather than computed at the end, which means a query for statistics on a running execution returns a partial but accurate picture of what has happened so far.

Two more fields reflect the interactive capabilities of the system. The first is the set of pending human input requests — entries representing nodes that have emitted a request for human input and are now paused, waiting for a response before they can continue. Each entry in this set is enough to identify the paused node and reconstruct what was asked. The second is the streaming buffer: a structure keyed by node name that accumulates streaming chunks as they arrive. For each node that has produced streaming output, the buffer holds the complete sequence of chunks received so far, along with an index that maps each chunk back to the specific node invocation that produced it. A client watching a stream does not reach into the live execution flow — it reads from this buffer, which is a stable, indexed record of every chunk the system has received and stored.

Finally, the root record carries a description of all forked executions spawned from this one. When an agent forks a child execution — a separate agent invocation triggered in the course of running the parent — that relationship is recorded in the parent's root entry. This makes it possible to follow the tree of forked executions from any root downward.

The root PState, taken as a whole, is the dashboard of a running execution. Everything an operator, a client, or the system itself needs to assess the state of an invocation is either stored here directly or reachable from a handle stored here. The trace of internal operations, the node-by-node execution graph, the detailed timing — those live elsewhere. But the root PState is always the starting point.

## Chapter 6: The Node PState — The Execution Graph in Memory

If the root PState is the dashboard, the node PState is the engine room. It is a map from invoke-ids to node execution records, and every time the system schedules a node to run, it creates an entry here. The complete execution trace of an agent — not just the final result but the entire history of how that result was produced — is encoded in the graph of entries connected by the emit relationships between them.

The partitioning of the node PState mirrors the root PState: entries are co-located by task-id, so the task that owns an execution also owns the node records for that execution. Reads and writes during execution remain local.

A node record begins with the basics: the agent-id this node belongs to, and the task-id of the task that owns the parent agent's root record. These two fields locate the node in the broader context of the execution tree. The record also stores the node's name — the human-readable label from the agent definition — and its position in the graph, which allows the system to reconstruct the topology of the execution without needing to re-read the agent definition.

The most structurally important field in a node record is the emit list. When a node finishes running, it may emit to one or more downstream nodes. Each emit is not just a notification — it is a structured record carrying the name of the target node, the task-id where that target will execute, the newly generated invoke-id assigned to the child execution, and the arguments being passed. The emit list is therefore the edge list of the execution graph. Starting from the root record's starting invoke-id and following emit lists through the node PState, you can reconstruct the complete tree of node executions. The trace view in Agent-o-rama's user interface does exactly this: it reads the starting invoke-id from the root record, fetches the corresponding node entry, reads its emit list, fetches each child entry, and follows the graph outward until it has assembled the entire execution.

The nested operations list is the other crucial field. Every significant thing a node does during its execution is recorded here as a structured entry: model calls, store reads, store writes, tool calls, human input requests — each appears as a separate entry with its own timing, its own inputs, and its own result. This matters because it means the trace view can show not just that a node ran and produced a result, but the complete internal sequence of operations that led to that result. You can see which model was called, with what prompt, how long it took, how many tokens it consumed, and what it returned. You can see whether a store read returned a hit or a miss, and what value came back. The node record is not a summary — it is a full accounting.

Start and finish timestamps bracket the node's execution, giving the system and any observer the data needed to compute per-node latency. These timestamps are written at execution time, not retroactively, which means the data is always available in the PState without requiring a replay of events.

Aggregation nodes carry additional fields that track the mechanics of the fan-out-and-join pattern. To understand why, consider what an aggregation node does: it waits for multiple upstream branches to complete and collects their outputs before proceeding. While it is waiting, it needs to track the accumulated state it has gathered so far, the list of inputs received, and whether the aggregation is complete. These fields are part of the node record for any node that plays the aggregation role. They are written incrementally as each upstream branch delivers its result, and the system checks them on each delivery to determine whether the aggregation threshold has been met. The full mechanics of how that check works, including the XOR acknowledgment system, are a topic for later. Here, it is enough to know that the node PState holds the accounting information that makes aggregation possible.

The key insight that the node PState embodies is that execution is a data structure. Every invocation is a graph. Every edge in that graph is an emit. Every node is a record. Every internal operation is a nested entry. Nothing that happens during execution is lost to the system — it is transformed into structured, indexed state. This is the event sourcing pattern applied at the level of individual operations. The execution trace is not reconstructed after the fact from logs; it is assembled incrementally, in real time, as execution proceeds. By the time an agent completes, the node PState already contains the complete history of what happened, ready to be read by the trace view, the analytics pipeline, or any other component that needs it.

## Chapter 7: The Shared State PState — Cluster-Wide Coordination

The root and node PStates are partitioned by execution. Each entry in those PStates belongs to a specific task, and the logic that reads and writes those entries runs on the same task. This is the pattern that enables local reads and writes and, by extension, efficient execution. But there is a third PState that breaks from this pattern. It holds state that needs to be visible across the entire topology, not scoped to any particular execution or task. This is the shared state PState, and its role is coordination.

The first structure inside shared state is the history map. This is a record of all past versions of the agent definition, stored by version number. When an agent's graph changes — when a developer deploys an updated version — the new version is added to this map and the old version remains there. This is what enables the live-update modes. When the execution engine needs to decide what to do with a running execution after a new version is deployed, it checks this map to determine whether the execution's recorded graph version is still valid. If the execution is in Continue mode, it consults the history map to verify that the old version remains compatible with the new one. If the execution is in Restart mode, the system uses the history to start a fresh execution on the new version while cleanly terminating the old one. The history map does not grow without bound — old versions are pruned once no running executions reference them — but at any moment it contains the version lineage the system needs to reason about live executions.

The active invokes set is the second structure. It is the set of all agent-ids currently running. This set is the starting point for two different background processes. The stall detector, which runs on a periodic schedule, consults the active invokes set to identify executions that have been running longer than their configured timeout without making progress — executions that appear to be stuck. The garbage collector similarly reads this set when looking for executions that have completed but whose records have not yet been cleaned up. Both processes need to know which executions are live, and the active invokes set is the authoritative answer.

Related to the active set is the garbage collection marker: a separate set of agent-ids that have been flagged for eventual cleanup. When an execution completes, it is removed from the active set and added to the GC marker set. The garbage collector processes this set on its own schedule, cleaning up the root and node PState entries for completed executions, freeing storage. The separation between completion and cleanup is deliberate. It gives the system a window during which a completed execution's data is still accessible for queries, even after the execution has finished running.

The metadata index is the fourth structure in shared state. At invocation time, callers can attach arbitrary metadata to an agent invocation — labels, categories, identifiers meaningful to the application layer. The metadata index is an inverse map from metadata values to the set of agent-ids that carry those values. This makes metadata-based queries efficient. When the analytics system needs to evaluate a rule over all executions with a given metadata tag, it does not scan the entire root PState looking for matching entries. It looks up the tag in the metadata index and receives a set of agent-ids directly. This is the classic database pattern of building an index to avoid a full scan, applied to the distributed state of a running system.

The shared state PState is different in character from the root and node PStates in one important way. Because it is not partitioned by execution, reading from it when you are operating on a task that does not own the relevant partition requires a network hop. A node executing on task nine that needs to check the history map may be asking a different task for that data. The system accepts this cost because the data in shared state is read infrequently relative to the per-execution reads and writes that dominate the execution path. The history map is consulted at update time, not on every node execution. The active invokes set is read by background processes on a schedule, not inline with execution. The metadata index is read during analytics processing, not during the hot path of running a node. The pattern throughout is the same: cluster-wide coordination data is separated into a structure that accepts slightly higher read cost in exchange for the expressiveness and flexibility of being globally visible.

## Chapter 8: Analytics and Telemetry PStates

Telemetry is the system's record of how executions have performed over time, and it lives in a PState managed by the microbatch analytics topology — a separate computation layer that processes completed invocations and accumulates statistical summaries from them.

The key structure in this PState is a three-part composite key. The first part is the agent name: the human-readable identifier for the kind of agent being measured. The second part is the metric identifier: what is being measured, such as end-to-end latency or token consumption for a particular node. The third part is the rule name: an identifier for the analytics rule whose evaluation produced this measurement. Together, these three parts identify an entry in the telemetry PState as precisely as a street address identifies a building. The value stored at each address is a NumberStats structure — a statistical summary built on top of a T-Digest.

The T-Digest deserves explanation, because the choice to use it over simpler alternatives reflects a deliberate tradeoff. The most obvious way to track latency statistics is to keep every measurement: record the latency of every agent invocation, store each value, and compute percentiles on demand by sorting the list. This works well at small scale. At large scale, it becomes prohibitive. An agent that handles ten thousand invocations per hour generates ten thousand latency measurements per hour per agent per metric. Storing all of them, forever, is not practical. Even storing a rolling window is expensive. The T-Digest is a different kind of data structure altogether.

A T-Digest is a sketch. To understand what that means, consider the problem it solves. You want to be able to say that the ninety-ninth percentile latency over the last hour was approximately three point four seconds. You do not need to be exactly right — approximate is acceptable. And you need to use much less memory than the full set of measurements would require. A sketch is a compact data structure that approximates a statistical property with a bounded error guarantee, using a fraction of the memory cost of the raw data. The T-Digest specifically is designed to approximate the percentile distribution of a set of numbers. It maintains a compressed representation of the distribution — a set of weighted centroids that together describe the shape of the distribution — rather than the individual data points. New measurements are merged into this representation incrementally. Percentile queries are answered by interpolating over the centroids. The result is a structure that can track latency distribution across millions of invocations using memory measured in kilobytes rather than megabytes.

This matters because the analytics PState is queried by the monitoring interface and the analytics API. When a developer asks for the ninety-fifth percentile latency of their agent over the last twenty-four hours, the system answers from the T-Digest rather than scanning raw event data. The answer is approximate but the approximation is well-characterized — the T-Digest's error bounds are understood and documented — and it arrives in milliseconds.

The cursor PState is the second analytical data structure worth examining. The analytics system processes invocations by scanning the root and node PStates forward from a saved position. That saved position is the cursor: the invoke-id of the last invocation processed for a given analytics rule. Each time the analytics topology runs its microbatch, it picks up from the cursor, processes all invocations recorded since that position, updates the telemetry PState with the results, and advances the cursor to the new position. The cursor is what ensures that each invocation is processed exactly once. Without it, the system would either re-process invocations it had already counted, inflating statistics, or miss invocations that arrived between batches, undercounting. The cursor makes the exactly-once guarantee mechanical rather than hopeful.

Cursor tracking is separated by task. Each task in the topology maintains its own cursor for each analytics rule. This means that the work of evaluating analytics rules is fully parallel across the cluster: task one is advancing its cursor through the invocations it owns, task two is independently advancing its own cursor, and so on. There is no single point of coordination, no queue of invocations to serialize through a bottleneck. The statistics produced by each task are merged when the telemetry PState is queried, giving a cluster-wide view assembled from per-task components. The separation of cursor tracking is also what makes retroactive backfill possible: to reprocess historical invocations under a new or modified analytics rule, the system resets the cursor to an earlier position and lets the microbatch topology advance it again from there.

Stepping back from the specifics, the PState architecture as a whole reveals three principles that recur throughout Agent-o-rama's design. The first is that everything that changes is recorded before it is applied. The depots hold the authoritative history of events. The PStates hold the current state derived from those events. The relationship between them is always derivable from the event log, which means the PStates are not the source of truth — they are a materialized view of it, rebuilt from the log whenever necessary. The second principle is that everything that needs to be found quickly is indexed. The metadata index in shared state. The cursor in the analytics PState. The emit lists that form the edges of the execution graph in the node PState. None of these are discoveries the system makes at query time — they are maintained incrementally so that the query-time work is a lookup, not a scan. The third principle is that state is co-located with the computation that uses it. The root and node PStates are partitioned to match the task assignment of executions, so that the writes that happen during execution are local. The shared state PState accepts a network cost because it is read on a background schedule, not in the critical path. The analytics cursors are per-task so that analytics processing is parallel. In each case, the partitioning of state is a deliberate choice made in service of performance, and understanding that choice is the key to understanding why the system behaves the way it does.

# Part Four: The Topology — How Events Become State

## Chapter 9: The Stream Topology — The Main Execution Engine

If you had to identify the single component responsible for turning an agent invocation into a running computation, it would be the stream topology. Everything else — the depots, the PStates, the node executor, the partitioner — is in service of what the stream topology does. It consumes events from the main agent depot and applies them as state transitions to the PStates. It is, in the most literal sense, the engine of the entire system. You could describe all the other components and their relationships with reasonable accuracy, but without understanding the stream topology you would still not know how the machine runs. This chapter is where that changes.

To understand why Rama's stream topology is the right tool for this job, you need to hold in mind the two properties that define it: it processes events one at a time, and it commits after each one. An event arrives from the depot, the topology applies it, the effects become visible in the PStates, and only then does the topology advance to the next event. Every event is a discrete transaction with a clear before and after. This is in contrast to a batch topology, which accumulates events over a time window and processes them together. Batch processing is useful for analytics and aggregations where you want to operate on sets of data, and Agent-o-rama uses batch topologies for exactly that in its analytics and garbage collection layers, which are covered later in the book. But for the main execution engine, batching introduces the wrong kind of delay. When a client calls invoke and is waiting for a result, when a downstream node is queued waiting for its upstream sibling to complete, the latency between an event arriving at the depot and its effects becoming visible in PStates is experienced directly. With a stream topology, that latency is milliseconds. With a batch topology, it would be measured by however long a batch window has to wait before it fills. For an interactive system, that distinction is not subtle.

The first thing the stream topology does when it receives any event — before it examines the event type, before it touches any PState — is check whether that event belongs to the current retry generation. This check is not a minor housekeeping detail. It is the foundation of the system's retry semantics, and it is worth understanding deeply.

Every execution has a retry number. When an execution is first created, its retry number is zero. If the execution fails and is retried, the retry number increments. The valid-invokes PState maintains a mapping from execution identifiers to the current retry number for each live execution. When any event arrives carrying a retry number, the stream topology looks up the current retry number for that execution and compares. If the event's retry number is lower than the stored current value, the event is dropped silently. The topology commits, and it advances to the next event. Nothing else happens.

This simple comparison achieves something that would otherwise require explicit cancellation logic: idempotent retries in a distributed system where in-flight work cannot be forcibly stopped. Consider what happens when an execution fails and a new retry is initiated. There may be node executor threads on various tasks that are still running nodes from the previous attempt. They will eventually produce NodeComplete events and append them to the depot. Without the retry filter, those stale completions would reach the stream topology and corrupt the state of the new attempt. With the filter, they cannot. They arrive, the topology checks their retry number against the current value, finds it lower, and drops them. The new attempt proceeds undisturbed. The system does not need to track down and cancel those in-flight threads. It simply stops accepting their output. The execution boundary is enforced at the state-writing layer, not at the work-dispatching layer, which is the only place where enforcement is both reliable and cheap.

When an AgentInitiate event passes the retry filter — which it always does, since it initiates a new execution with a fresh retry number beginning at zero — the topology's work is straightforward but consequential. The first task is to create an entry in the root PState for this execution. That entry receives an agent-id generated by the system, the full argument list and metadata that arrived in the AgentInitiate event, a record of which graph version governs this execution, and an initial ack-val. The agent-id is how this execution will be referenced everywhere in the system. The graph version record is how the topology knows which node graph to traverse. The ack-val serves the aggregation detection mechanism described in Chapter 12; for now, it is enough to know it is initialized here, and that its initial value is significant.

Alongside the root PState entry, the topology creates an entry in the node PState for the first node in the agent graph — the entry node. Every graph has exactly one entry node, the designated starting point. The node PState entry receives an invoke-id — a unique identifier for this particular invocation of this node in this execution — records the node's name and which task it is targeted to run on, and marks the node as pending. The target task assignment at this stage is determined by the partitioner, and the assignment is permanent: this node will run on exactly this task.

Finally, the topology schedules the first node for execution by constructing a NodeOp message — the scheduling artifact that the node executor recognizes — and routing it to the task that was recorded as the target. At this point the topology is done with this event. It commits and advances to the next one.

NodeComplete events are the most complex case the topology handles, and understanding them is the key to understanding how the execution graph unfolds over time. When a NodeComplete arrives and passes the retry filter, the topology performs a sequence of operations that both closes out the completing node and opens up whatever comes next.

The first operation is to update the node PState entry corresponding to this completion. The entry was created when the node was scheduled; now it is being closed. The topology writes the emits the node declared, the list of nested operations the node performed during its execution, the result if one was declared, and timing information. This is the archival record of what the node did. It persists in the PState and is the basis for the nested operation history that clients and operators can query.

Then the topology works through the consequences of those emits. For each emit declared in the NodeComplete — and there may be zero, one, or many — the topology creates a new entry in the node PState for the downstream child node. Each child gets an invoke-id, a record of its target node name, and an assignment to a task. Each is marked pending. Then the topology routes a NodeOp message to each child's target task. This is how the execution graph grows: one NodeComplete fans out into multiple new NodeOps, each of which will eventually produce its own NodeComplete, each of which the topology will process in turn. The entire graph traversal is implicit in this loop.

If the NodeComplete included a final result — the signal that this execution is complete — the topology marks the root PState entry as complete, records the result, and removes the execution from the active invokes set. It also updates running statistics in the root entry: execution time, node counts, and whatever the analytics layer will later read through its cursor-based pipeline.

Step back and consider what this design reveals about the system's structure. The stream topology is stateless logic applied to stateful data. This phrase is worth dwelling on. The topology itself contains no mutable variables. It holds no running counts, no pending maps, no in-memory bookkeeping that would be lost if a machine crashed. Everything the topology knows about the state of an execution is in the PStates. Everything the topology has yet to do is represented by events in the depot. If the topology crashes mid-processing, Rama restarts it from the last committed position. The events are still in the depot. The PStates reflect exactly the state as of the last successful commit. The topology resumes processing as though nothing happened. This is the core guarantee of event sourcing: the log is the ground truth, the state is derived from it, and the processing logic can afford to be stateless because the log never forgets. The stream topology is stateless not as an oversight or a limitation, but as a deliberate design choice that makes the system resilient without any explicit recovery logic.

## Chapter 10: How a Node Actually Runs

The stream topology schedules a node by constructing a NodeOp record. This record contains the node's name, the invoke-id that identifies this particular execution of that node within this particular agent run, the arguments it was called with, and the agent context — a bundle that includes references back to the execution it belongs to, the graph version it is running under, and the target task for any aggregation results. The topology routes this NodeOp to the task identified as the target for this node. Once the routing is done and the topology commits, the topology's responsibility for this node is complete until a NodeComplete arrives. The question of what happens between routing and NodeComplete is the subject of this chapter.

On the target task, the NodeOp is picked up by the node executor. It is important to understand what the node executor is and is not. It is not a stream topology or a batch topology in the Rama sense. Those are frameworks that process depot events and write to PStates. The node executor is a different kind of component — it sits alongside the topologies on the task and manages the actual execution of user-written node functions. It maintains a pool of virtual threads, and when a NodeOp arrives, it dispatches the corresponding execution onto one of them. While the topologies handle Rama's event-processing lifecycle, the node executor handles the lifecycle of running code inside those events.

Before the user's function can run, the executor does one more piece of assembly. It creates a concrete implementation of the AgentNode interface and prepares it for the specific invocation at hand. AgentNode is the object the node function receives as its execution context. It is the user code's window into the framework's capabilities: through it, the function makes model calls, reads and writes user-defined stores, emits to downstream nodes, declares a result, and requests human input. The user's function never imports a Rama API directly. It uses AgentNode, and AgentNode handles the translation between what the user requests and what the framework does. This indirection is not bureaucracy — it is the mechanism by which all of the node function's operations can be observed, recorded, and later reconstructed.

The executor also initializes a thread-local list before the function runs. This list will accumulate NestedOp records throughout the function's execution. A NestedOp is the system's representation of a single significant action: a model call, a store read, a store write, a tool invocation, a human input request. Every time the user's function performs any of these actions through the AgentNode interface, the implementation appends a NestedOp to the thread-local list. This happens automatically, beneath the level of the user's code. The user does not call any recording API. The recording is a side effect of using AgentNode, not a separate step.

The user's function then runs to completion in its virtual thread, and this is where the framework largely disappears from the programmer's perspective. Inside the virtual thread, the code looks and behaves like ordinary blocking code. To call a language model, you invoke a method on the AgentNode and wait for the response. The thread parks on the blocking call, the JVM suspends it, and execution resumes when the model's response arrives. To read from a store, you call a method and wait. To invoke a subagent — triggering a separate agent execution that will run its own full graph — you call a method and wait for the nested execution to complete and return a result. The programming model is sequential: one thing, then the next, results in hand before the next step begins.

This sequentiality is a significant design choice. Agent logic is often expressed most naturally as a sequence of steps with dependencies: call the model to decide what to do, use the result to determine what to look up, look it up, call the model again with the result, decide whether to continue or terminate. Writing that logic with callbacks or composing futures requires the programmer to express the dependency structure explicitly, which adds ceremony and indirection. Writing it as sequential blocking code means writing it exactly as you would write prose describing the algorithm. The cognitive overhead is minimal. The logic is direct.

While the function runs and waits and runs again, the NestedOp list grows. Each model call appends a record with the model, the prompt, the response, and the timing. Each store operation appends a record with the key and value. Each subagent invocation appends a record with the subagent's identity and the returned result. By the time the function completes, the thread-local list is a complete audit trail of everything the node did during its execution.

When the function returns — whether because it called emit to pass a value to a downstream node, called result to declare the execution's final output, or simply returned normally from the function body — the executor moves into collection mode. It gathers the emits the function declared during its run, the result if any was declared, and the complete list of nested ops. It packages these into a NodeComplete event. The NodeComplete event is then appended to the main agent depot, where the stream topology on the home task will process it.

The executor releases the virtual thread. The thread returns to the pool, available for another NodeOp. The node executor's involvement with this particular invocation is over.

Notice what this lifecycle implies about error handling. If the node function throws an uncaught exception rather than returning normally, the executor catches it. An exception is not a NodeComplete; it is a signal that the node failed. The executor packages the failure information and appends a NodeFailure event to the main agent depot instead of a NodeComplete. The stream topology processes NodeFailure events through its own branch of logic, which may trigger the retry machinery or record the failure in the root PState as a terminal error, depending on the execution's retry policy. From the topology's perspective, NodeFailure is just another event type to handle. From the node executor's perspective, the handling is symmetric: either the function completes and produces a NodeComplete, or it fails and produces a NodeFailure. Either way, the outcome is an event in the depot, not a side effect on local state.

The key insight here — and it is worth stating explicitly because it is easy to overlook — is that the node function never writes to any PState directly. It does not update execution records. It does not modify the node graph. It does not touch the aggregation state. The only artifact it produces is a NodeComplete event delivered to the depot. All of the state changes that represent the consequence of this node having run flow from the stream topology processing that event. The node function is a producer of events. The stream topology is the exclusive writer of state. This separation is not just clean architecture; it is the property that makes the retry filter work correctly. Since the node function has no direct access to state, the only way a node execution can affect state is through its NodeComplete event, and the retry filter can therefore completely neutralize any stale execution by dropping its NodeComplete.

To understand why virtual threads matter here, consider the alternative. A traditional thread pool has a fixed maximum size, and those threads are operating-system resources. Creating an OS thread takes time and memory; maintaining one that is parked on a blocking network call consumes a kernel structure and a stack. If you have a thousand concurrent agent executions, each parked on a blocking call to an external language model provider, you need a thousand threads ready to resume when those calls return. On most systems, a thousand OS threads is manageable. At ten thousand, you are consuming meaningful system resources. At a hundred thousand — which is not an unreasonable number for a busy cluster — you are in serious trouble.

Virtual threads, introduced as a stable feature in Java 21, change this arithmetic entirely. They are managed by the JVM rather than by the operating system. When a virtual thread parks on a blocking operation — waiting for a network response, waiting for an IO call — the JVM unmounts it from its underlying carrier OS thread. The carrier thread is immediately available for other work. The virtual thread exists as a small heap object, retaining its stack and program counter, waiting for its blocking call to complete. When the network response arrives, the JVM mounts the virtual thread back onto a carrier thread and resumes execution. The cost of a million parked virtual threads is measured in heap memory, not in OS thread handles. For a system whose primary bottleneck is waiting on external model providers — each model call taking hundreds of milliseconds of real time — virtual threads are not an optimization. They are what makes the concurrency model possible at the scale Agent-o-rama is designed for.

There is also a subtler benefit that virtual threads provide beyond raw concurrency numbers. Because each node execution runs in its own dedicated virtual thread from start to finish, there are no thread-switching artifacts to reason about. The call stack visible to the node function is consistent for the entire duration of the execution. Thread-local storage works exactly as it does in single-threaded code. The NestedOp list accumulated by the AgentNode implementation, which is stored in a thread-local variable, is always the list for exactly this invocation, not a shared structure that requires synchronization. The virtual thread isolation makes the recording mechanism simple to implement and impossible to corrupt across concurrent invocations. This is another example of the same theme found throughout the system's design: choose the abstraction whose natural properties make correctness straightforward rather than something you have to enforce explicitly.

## Chapter 11: Partitioning and Co-location — Why It's Fast

Performance in a distributed system is not primarily about raw computation speed. Modern hardware computes quickly. What kills distributed system performance is latency: the time spent waiting for data to travel across a network, waiting for a remote read to return, waiting for a coordination message to complete a round-trip. The design of Agent-o-rama's partitioning strategy is built around a single central commitment — when a task is doing work on behalf of an execution, the data that work requires should already be on that task. This is the principle of co-location, and it shapes every routing and placement decision in the system.

When an agent execution begins and the stream topology processes the AgentInitiate event, the execution is assigned to a specific task in the Rama cluster. This assignment is the execution's home: the task where its PState data lives, the task where its events will be processed, the task where any coordination that requires knowing the execution's state will take place. The identifier capturing this assignment is the agent-task-id. It is generated once, recorded in the root PState entry, and embedded in every subsequent event related to this execution.

The agent-task-id functions as a routing directive. Every event type in the main agent depot — NodeComplete, streaming progress updates, human input responses, tick events — carries a routing key that identifies which execution it belongs to, and the custom depot partitioner uses that key to direct the event to the home task. The partitioner's logic is deliberately simple: read the routing key from the event, look up the corresponding task assignment, route there. It does not compute a task by hashing the key. It does not consult a registry. The assignment was made upfront and stored in the event; the partitioner just reads it. This makes routing deterministic, cheap, and free of coordination. Any task in the cluster can route any event correctly by reading the agent-task-id embedded in it.

Consider why this matters for the stream topology. When a NodeComplete arrives at the home task, the stream topology needs to look up the node PState entry for the completing node, update it, create new entries for child nodes, and potentially update the root PState entry. Each of these reads and writes must touch the correct partition of the PState. Because the root PState and node PState are partitioned by task-id, and because the home task's task-id was used to partition this execution's PState data, those partitions are local to the home task. The topology reads local data, writes local data, commits. No network round-trips. The entire processing of a NodeComplete event, from arrival to commit, involves only local operations on the task where it lands.

This is the mechanism by which the system achieves its millisecond event-processing latency. It is not that the individual operations are unusually fast. It is that they are composed entirely from local operations: local PState reads, local PState writes, local depot appends that route outbound events. The network is used to deliver events to the right tasks, but once an event has arrived, its processing is local.

The more interesting design question is what happens when a node emits. A NodeComplete event can carry multiple emits, each directing the execution graph to continue along a different branch. Each emit creates a new child node invocation. Each child node invocation must be assigned to a task. The choice of task assignment for child nodes is where the system's distributed parallelism comes from, and the rules are different for different kinds of nodes.

For regular nodes — nodes whose work is independent and self-contained, nodes that do not need to coordinate with their siblings during execution — the task assignment is chosen at random from the cluster. If a node emits ten times, ten child nodes are created, and each may be assigned to a different task. The ten child executions run in parallel on their respective tasks, each parking a virtual thread on a blocking model call, each eventually producing a NodeComplete that routes to its own home task for state processing. The cluster's computational resources are being used in proportion to the number of concurrent invocations, without any single task becoming a bottleneck for the fan-out.

For aggregation nodes — nodes whose purpose is to accumulate and combine results from multiple upstream siblings — the assignment rule is different. All children that feed into the same aggregation must route their completions to the same agg task, the task that owns the accumulation state for that aggregation. The agg task is assigned when the aggregation starts, and it is recorded so that every completing child knows where to send its result. Think of it this way: the fan-out spreads independent work across the cluster, and the fan-in pulls the results back to a single convergence point where they can be combined into a coherent whole. The convergence point is fixed at the start of the aggregation, not discovered dynamically as results arrive.

The interplay between these two rules creates the system's characteristic execution shape. A computation that fans out to many independent children and then aggregates them will distribute its work widely across the cluster during the fan-out phase, then funnel results to a single task during the aggregation phase. That single task becomes the bottleneck during aggregation, but only during aggregation — once it has processed all the incoming results and fired the aggregation end node, it is free for other work. The aggregation bottleneck is transient, bounded by the number of children completing, and does not propagate to the rest of the system.

Store writes follow a different co-location logic. User-defined stores are backed by PStates, and those PStates are partitioned by store key. When user code performs a store write through the AgentNode interface, the write is not processed immediately on the node executor's task. Instead, it is routed to the write depot, which uses the store key to direct the write to whichever task owns that key's partition. This means writes to the same key always land on the same task, and that task can update its local PState without any cross-task coordination. Two concurrent writes to the same key may need to be serialized — Rama handles this — but they do not need to coordinate with any task except the one that owns the key's partition.

The shared state PState, which holds cluster-wide coordination data, follows the same key-partitioned logic. Any agent execution that needs to read or update shared state routes that operation to the task owning the relevant key. Because the shared state PState is consistent and durable — backed by Rama's same event sourcing guarantees as everything else — reads and writes to it are reliable without requiring the kind of distributed locking you would need if shared state lived in a conventional cache or in-memory data structure. This is a place where the event sourcing foundation pays dividends beyond the main execution path: the same properties that make the root and node PStates reliable make the shared state PState reliable, and the same co-location strategy that keeps execution processing fast keeps shared state reads fast when the data is already on the right task.

It is also worth noting what happens when a node reads from a store rather than writing to it. A store read goes through the read path, which may or may not be task-local depending on whether the reading execution happens to be on the same task as the key's partition. In the common case, reads are not co-located with the execution — they go wherever the key lives. This is an intentional tradeoff. Reads are typically less latency-sensitive than the state updates that drive the execution forward, and the consistency guarantees of reading from a PState are worth the occasional network hop. Writes, by contrast, must be serialized correctly, which is why they travel through the write depot and land exclusively on the task that owns the key.

The design philosophy that ties all of this together is worth making explicit. The goal is not to minimize the number of tasks involved in a computation. A complex fan-out with an aggregation step will genuinely involve many tasks — that is correct behavior, that distribution is the source of the system's parallelism. The goal is to ensure that when a task is involved, it has everything it needs locally. The home task for an execution has the execution's PState. The agg task has the aggregation's accumulation state. The store task has the key's data. Each task operates on data that is already present. The network traffic in the system is dominated by routing events to their destinations, not by fetching data from remote tasks to process an event once it has arrived. That asymmetry — routing is the network cost, processing is local — is the source of the system's performance characteristics, and it is entirely a consequence of deliberate placement decisions made when assignments are first created.

## Chapter 12: The XOR Ack-Val — How Aggregation Completion Is Detected

Consider the problem that aggregation poses, stated precisely. An agent graph contains a fan-out pattern: a start node emits some number of times to a set of parallel child nodes, and an aggregation end node should fire exactly once when all of those children have completed. The aggregation end node might compute a summary, a ranking, a combined answer, or simply a signal that the parallel work is done. The requirement is that it fires exactly once, not before all children are done, and not more than once after they are.

The difficulty is not in collecting the results. Each child produces a NodeComplete event, and those events can be processed as they arrive. The difficulty is in knowing when the collection is complete. And the thing that makes it difficult is that the number of children is not known before the fan-out begins. It depends on how many times the start node emits, which depends on the start node's runtime behavior, which depends on its inputs, which may include the result of a model call that has not yet happened. You cannot know in advance whether the fan-out will produce three children or thirty.

One natural approach is to use a counter. Initialize it to zero, increment it each time a child is created, decrement it each time a child completes, and fire the end node when the counter reaches zero. This is logically correct. The problem is structural. The counter is a shared mutable value that must be updated from multiple tasks. Children are created by the home task and may complete on different tasks, any of which needs to decrement the counter when it processes a child's NodeComplete event. A counter that must be incremented and decremented from multiple tasks concurrently is a contention point. Every update requires either taking a lock on the counter's location or using an atomic operation with a retry loop. In a fan-out with many children completing in rapid succession on different tasks, those updates serialize on the counter's location. All the parallelism gained by distributing the child executions across the cluster is partially undone by the queue of tasks waiting to touch the counter.

A second natural approach is a barrier: a synchronization primitive that lets N threads signal their completion and then releases when all N have signaled. Barriers are fine when N is known upfront. Here it is not. You cannot construct a barrier for N threads when you do not know N until the start node has finished running. You could construct the barrier lazily after the start node completes, but that requires waiting for the start node to complete before allowing children to start — which defeats the purpose of parallelism, since you want children running before the start node has emitted its last value.

Agent-o-rama uses a different mechanism, one that sidesteps both problems. It is called the ack-val. The ack-val is initialized in the root PState when an aggregation begins. Its initial value is a large random number — chosen with the same entropy as half a UUID, which makes collisions negligible in practice. Call this initial value V.

Each time the start node emits to a child, two things happen atomically. A new random number is generated; call it C for contribution. That contribution is XORed into the ack-val. The ack-val is now V XOR C. When the child node eventually completes — which may happen on a different task, possibly much later — its completion is processed by the stream topology, which XORs the same value C back out of the ack-val. After this operation, the ack-val returns to V.

If two children are created with contributions C1 and C2, the ack-val after both are created is V XOR C1 XOR C2. After the first completes, it becomes V XOR C2. After the second completes, it becomes V again. The topology checks after each child completion: does the ack-val equal its initial value V? If it does, all children have reported back.

To understand why this works and not something simpler, it helps to examine the mathematical properties XOR has that make it the right operation here. The first property is commutativity: XOR does not care about order. V XOR C1 XOR C2 is the same value as V XOR C2 XOR C1, regardless of which child was created first or which completes first. If child A completes before child B but was created after child B, the ack-val still reaches V correctly when both have completed. Order does not matter. This is critical in a distributed system where completions arrive in whatever order network timing dictates.

The second property is that XOR is self-inverse: XORing a value twice with the same operand returns you to where you started. This is the property that allows the XOR-out operation to cleanly undo the XOR-in. There is no separate subtraction, no check for sign, no wrap-around arithmetic to worry about. The same value added is the same value removed.

The third property is that XOR is associative: you can apply it in any grouping. It does not matter whether you apply C1 first and then C2, or C2 first and then C1, or both together; the result is the same. Combined with commutativity, this means the ack-val can be updated incrementally and in any order — exactly what you need when updates are arriving asynchronously from different tasks.

The practical implication of these three properties is that the system never needs to know how many children will be created before it starts creating them. Each emit atomically reads the current ack-val, generates a fresh contribution, XORs the contribution in, and records the contribution alongside the child's node PState entry so that the topology can XOR it out when the child completes. Each child completion atomically reads the current ack-val, XORs out the recorded contribution, and writes the result back. The topology inspects the result: if it equals the stored initial value V, the aggregation is complete.

There is no counter to serialize updates to. There is no barrier waiting for a predetermined count. The operations are atomic PState updates — fast, local, and concurrent-safe by construction — and the completion signal emerges from arithmetic rather than from coordination. This is what it means to design for distributed execution rather than to adapt a sequential algorithm to run across machines.

Nested aggregation — an aggregation that itself fans out to child aggregations — works by the same mechanism applied at each level independently. Each level of nesting maintains its own ack-val in its own node PState entry. The outer aggregation's ack-val is not updated when individual inner leaves complete. It is updated only when inner aggregation end nodes fire — which themselves fire only when their own ack-vals have returned to their initial values. The synchronization is naturally nested. The outer level waits for the inner end nodes; the inner end nodes each wait for their own children. Each level's ack-val is private to that level and reflects exactly the children that level is waiting for, which is precisely the set that contributed to its ack-val. There is no explicit two-level coordination protocol. The nesting is a consequence of the mechanism, not a special case of it.

There is a deeper observation here about the relationship between mathematical properties and distributed design constraints. The requirement that the system should not have a centralized coordination bottleneck is not a soft preference. It is a hard constraint: a centralized bottleneck negates the scaling benefits of distribution. Meeting this constraint requires finding operations that are inherently decentralized — where each participant can contribute independently, where the contributions can be combined without a coordinator, and where the combined result has a detectable terminal state. Most arithmetic does not have all three of these properties simultaneously. Arithmetic addition has the first two but not the third in the way we need: detecting that all N contributions have been subtracted back out requires knowing what N was. XOR has all three properties, and specifically, its self-inverse property means that removing all contributions is detectable without any knowledge of how many there were. The ack-val returns to V not because the system counted N completions and compared against N creations, but because the mathematics guarantees that XORing out every contribution that was XORed in yields back the starting value. Completeness is a mathematical consequence, not a comparison.

When you encounter this kind of alignment between a mathematical operation and an engineering problem — where the operation's natural properties match the problem's natural requirements — it is usually evidence of something worth noting. Not the operation itself, which is a half-century old piece of computer science. What is worth noting is the recognition that the problem had a shape, that the shape matched XOR's properties, and that the system was designed to make that match exploitable. Distributed systems are full of places where a naive approach creates a bottleneck and a more careful approach finds an operation whose properties dissolve the bottleneck entirely. The ack-val mechanism is one of the cleaner examples. Understanding it is understanding not just how aggregation completion is detected, but how to look for that kind of solution when you encounter analogous problems in your own systems.

# Part Five: The Specialized Depots and Their Topologies

## Chapter 13: How Streaming Works Under the Hood

Every time a node produces a chunk of streaming output — a fragment of a language model response, an incremental result from a long computation — something specific has to happen with that chunk. It has to travel from the executing node, through the system's infrastructure, and arrive in front of the client that is waiting for it. It has to arrive in the right order. It has to be discarded if the node that produced it failed and restarted. And none of this can be allowed to slow down the critical path of execution management. Understanding how streaming works means understanding how Agent-o-rama solves all of those constraints simultaneously.

The starting point is a design decision that might seem obvious once you hear it but requires a moment to appreciate: streaming chunks do not travel through the main agent depot. When a node calls the streaming function to emit a chunk, that chunk goes to a dedicated streaming depot, completely separate from the depot carrying NodeComplete events and execution lifecycle signals. This separation is not incidental — it is the entire architectural premise of the streaming subsystem. Streaming chunks can be large, and during a generation they arrive frequently, sometimes dozens per second. If they traveled through the main agent depot, they would compete for space and processing time with the events that advance the execution graph. Every NodeComplete event would be delayed by the weight of concurrent chunk traffic. The streaming depot is a performance boundary, drawn deliberately to keep latency-sensitive execution events from contending with high-volume data events. Each class of traffic runs on its own rails.

The streaming depot uses partitioning by agent task identifier, which means every chunk produced by an agent execution lands on the same task that owns that execution's root PState. This is the same co-location principle at work that you saw in the main depot. When the stream topology processes a streaming event, it needs to update the streaming buffer in the root PState. If the chunk arrived on a different task, that update would require a network hop to reach the PState. Partitioning by agent task identifier eliminates that hop by ensuring the chunk always arrives where the relevant state already lives.

Each streaming event carries four pieces of information. The first is the chunk content itself — the actual bytes being delivered. The second is the invoke identifier of the specific node invocation that produced the chunk. This is important because in a fan-out scenario, where a node runs multiple times concurrently as part of an aggregation subgraph, each instance has its own invoke identifier. The third piece is a monotonically increasing index. This index is scoped to the invoke identifier — each invocation has its own counter starting from zero. The fourth piece is the retry number of the execution at the time the chunk was produced. Together, these four fields give the system everything it needs to validate, order, and attribute each chunk correctly.

When the stream topology receives a streaming event, its first step is to check the retry number. The valid-invokes PState records which retry generation is currently active for this execution. If the chunk carries a retry number from a previous generation — meaning the node that produced it has since failed and been abandoned — the event is discarded. This is the same retry generation filter pattern used everywhere in the system. It applies here without modification because streaming events are just depot events like any other, subject to the same validation logic.

If the retry number passes validation, the topology updates the streaming buffer in the root PState. Specifically, it appends the chunk to the list maintained for the combination of node name and invoke identifier, and it records the current high-water index for that invoke identifier. The index matters for ordering. In most cases chunks arrive in order, but the append-only log does not guarantee delivery at the precise instant of production — if chunks arrive slightly out of sequence, the stored index allows the client library to detect gaps and reorder accordingly.

The client side of streaming uses a mechanism called a foreign proxy. To understand what a foreign proxy is, think of it as a live subscription to a specific field inside a PState. When a client opens a foreign proxy on the streaming buffer field of an agent's root PState, it is saying: whenever this field changes, send me the new value. Rama evaluates the read path when the proxy is first established to get the current value, and then re-evaluates it every time the underlying PState changes. The client receives each new version of the field as it is updated, without polling and without holding a thread open waiting. This is Rama's reactive read primitive, and it is what makes streaming feel continuous even though the underlying mechanics are event-driven. The client library wraps this proxy in a higher-level interface: it registers a callback function, and as new chunks arrive in the PState and propagate through the proxy, the callback is invoked with each new chunk in sequence.

When a node fails and the execution retries, the streaming buffer for that node is cleared. This is paired with a reset signal delivered through the proxy to any clients that are currently subscribed. The reset tells the client to discard whatever chunks it has already received for this node, because those chunks are from an attempt that did not complete successfully. The node will run again, and a new sequence of chunks will follow. This reset mechanism closes the loop on retry semantics for streaming: it is not enough to discard chunks on the server side; the client must also know to start fresh. The depot's retry number validation and the client reset signal together make streaming exactly-once-visible from the consumer's perspective, even in the presence of node failures.

The full picture, then, is this. A node emits a chunk. The chunk travels to the streaming depot, partitioned to land on the task that owns the execution. The stream topology validates the retry number, updates the root PState's streaming buffer with the chunk content and index. The foreign proxy on the client side detects the PState change, re-evaluates its read path, and delivers the new chunk to the registered callback. If the node fails, the buffer is cleared, a reset is sent to the client, and the process begins again with the retry. At no point does any of this touch the main agent depot. The execution graph continues advancing on its own rails, unaffected by however many chunks are flowing through the streaming subsystem in parallel.

One aspect of streaming that deserves a final note is what happens with the streaming-all subscription type in fan-out scenarios. When a node runs multiple times concurrently — because it is a member of an aggregation subgraph where several invocations are executing in parallel — each invocation is identified by its own invoke identifier. A client that subscribes to streaming-all does not receive chunks interleaved in a single undifferentiated stream. Instead, the client library tracks the index per invoke identifier and presents each invocation's output as its own sub-stream. The monotonically increasing index is the mechanism that makes this separation reliable. Because each invoke identifier has its own counter, the client can always tell whether a chunk arrived in order, whether a chunk was missed, and which invocation it belongs to. This is why the invoke identifier and index travel together in every streaming event: they are not redundant metadata — they are the addressing scheme for concurrent multi-stream delivery.


## Chapter 14: How Human-in-the-Loop Works Under the Hood

Streaming is about carrying data out of a running node to a waiting client. Human-in-the-loop is the reverse: it is about carrying data from a waiting human back into a paused node. The mechanics are different because the direction is different, but the architecture follows the same depot-and-topology pattern, and the same co-location principles apply. What makes human-in-the-loop particularly interesting is what it reveals about virtual threads and the guarantee that waiting costs nothing.

When a node calls the get-human-input function, three things happen at roughly the same moment. First, a HumanInputRequest record is written to the human-requests set in the root PState. This is the mechanism by which the outside world learns that a request is pending. The web UI queries this set to display pending requests. The client API exposes it through polling and subscription. The record contains everything needed to surface the request to a human: the prompt text, the agent identifier, the node name, the invoke identifier, and a unique request identifier. Second, a HumanInputRequest event is appended to the human input depot, which triggers the stream topology to validate and persist the request state. Third, the virtual thread running the node function parks on a CompletableFuture, suspending its execution and releasing control.

A CompletableFuture is, in plain terms, a handle to a value that does not exist yet. Any thread can park on a CompletableFuture by waiting on it — the thread will remain suspended until the value arrives. A different thread can complete the CompletableFuture by providing the value, at which point any thread waiting on it wakes up and receives the value as if it had been returned normally. The CompletableFuture is the bridge between the event-driven world of the topology, where responses arrive as depot events, and the imperative world of the node function, where the response needs to appear as a return value from a function call. When the human input depot's stream topology processes a response event, it completes the CompletableFuture stored in the PState for the matching request identifier. The parked virtual thread wakes up, receives the response string as the return value of get-human-input, and continues running as if nothing unusual had occurred.

To understand why this guarantee matters, consider what happens in a system that uses operating system threads rather than virtual threads. An operating system thread parked on a blocking call holds a kernel resource — it occupies a thread handle, a stack allocation, and scheduler overhead. On most systems, you can have tens of thousands of operating system threads before the overhead becomes a serious problem. In an agent framework where executions can wait for human input for hours or days, and where you might have thousands of concurrent executions waiting simultaneously, operating system threads would be ruinously expensive. Virtual threads do not have this problem. A virtual thread that is parked on a CompletableFuture has been unmounted from its carrier thread and reduced to a lightweight continuation object on the heap. It holds no operating system resource. You can have millions of parked virtual threads and the cost is modest heap memory, not kernel scheduler overhead. This means Agent-o-rama can support thousands of concurrent human-in-the-loop pauses with no practical thread ceiling.

When a human provides a response — through the web UI, which calls into the client API under the hood, or through the client API's provide-human-input method directly — a HumanInput event is appended to the human input depot. This event carries the original request identifier and the response string. The partitioner for HumanInput events routes by the task identifier of the node that is waiting, which may differ from the agent task identifier if the waiting node was executing on a remote task. When the stream topology processes the event, it does four things in sequence. It looks up the pending request by request identifier. It completes the stored CompletableFuture with the response string. It removes the HumanInputRequest record from the human-requests set in the root PState. And it updates any audit or history state that tracks the interaction. The CompletableFuture completion is what wakes the virtual thread, and the removal from human-requests is what removes the request from the UI and client API surfaces.

This means the request lifecycle is fully reflected in the root PState. A request appears in the human-requests set the moment the node calls get-human-input. It disappears the moment the response is provided. Clients that are watching the human-requests set through a foreign proxy — the same reactive read mechanism used for streaming — receive a notification when new requests arrive and another when they are resolved. The web UI uses exactly this mechanism to display a live view of pending requests without polling.

The timeout question sometimes comes up in discussions of human-in-the-loop. What happens if the human never responds? The answer lies in the stall detection system introduced in Chapter 3. An execution that is waiting for human input is, from the stall detector's perspective, an execution that has not produced a NodeComplete in a long time. If the stall detector's configured threshold is exceeded, it will fire a RetryAgentInvoke event, which resets the execution and restarts it from the beginning. In practice, this means that human-in-the-loop workflows must be designed with the understanding that the stall timeout is the backstop for indefinite waits. Operators can tune the stall threshold to be generous for workflows that are expected to wait for human responses, or they can implement explicit timeout logic in the agent definition itself. The system does not prevent indefinite waiting — it simply ensures that executions cannot stall silently forever without eventually being noticed and acted upon.

The symmetry between streaming and human-in-the-loop is worth dwelling on. Both use a dedicated depot separate from the main agent depot. Both use depot event processing to update the root PState. Both use Rama's reactive proxy mechanism to notify clients of state changes. Both apply retry number validation to discard stale events. The differences are precisely those required by the difference in direction. Streaming pushes data from a node to a client. Human-in-the-loop pulls data from a client back into a paused node. Streaming uses the foreign proxy to push chunks outward. Human-in-the-loop uses the CompletableFuture to deliver responses inward. The architecture is a mirror.

This symmetry is not accidental. It reflects a design philosophy that the book has been building toward since Part One: every concern in the system is expressed as events in a depot, processed by a topology, and materialized into PState. Streaming output is a concern. Human input is a concern. Both follow the same pattern, not because the pattern was forced onto them, but because the pattern genuinely fits both. The depot-topology-PState model is not a constraint — it is a vocabulary, and both of these features are written in it.

There is also a failure-handling symmetry worth noting. For streaming, the failure case is a node that produces chunks and then crashes — those chunks are invalidated by the retry number filter and the client receives a reset signal. For human-in-the-loop, the failure case is a node that requests input and then crashes before the response arrives. When this happens, the stall detection and retry machinery eventually increments the retry generation, which invalidates the pending CompletableFuture. The HumanInputRequest record in the root PState is removed as part of resetting the execution. Any response that arrives for the old request identifier will be processed by the stream topology, which will find that the request no longer exists in the current retry generation and will discard the response. The human will need to be asked again by the retried execution. Both subsystems handle their failure cases through the same retry generation filter, and both make the cleanup visible through PState state changes that clients can observe in real time.


## Chapter 15: How Store Writes Achieve Retry Safety

Agent-o-rama lets node functions write to user-defined stores: key-value stores, document stores, and PState stores. These stores are where agent executions persist application-level data — the results of computations, intermediate state that needs to survive across retries, records that other agents or external systems will later read. From the perspective of a node function author, writing to a store looks like a straightforward operation: you provide a key, a path, and a value, and the write happens. What the node author does not see, and does not need to see, is the mechanism that makes that write safe in the presence of retries. That mechanism is worth understanding, because it illuminates a subtle correctness problem and explains why the indirection is necessary.

Start with the problem. Suppose a node runs and writes the value forty-two to a counter in a key-value store. Then the node fails — perhaps because an unhandled exception occurs after the write but before the node returns. The execution system retries the node. The node runs again and once more writes forty-two to the counter. If the write is an idempotent operation — setting the counter to a specific value regardless of what it was before — applying it twice causes no harm. But if the write is a relative operation — incrementing the counter by one — then two applications would increment twice, leaving the counter at a value two higher than it should be. The execution saw one logical write, but the store received two physical writes. This is the exactly-once problem applied to user-defined stores.

The solution Agent-o-rama uses is to route all store writes through the PState write depot. When a node writes to a store, the write does not go directly to the backing PState. Instead, it is captured as a PStateWrite event and appended to the write depot. The event carries the store name, the path expression describing where to write, the value to write, and the agent source context — which includes the agent task identifier, the agent identifier, and the retry number of the execution at the time the write was issued. The write goes into the log, and the node continues executing. The actual application of the write to the backing PState happens later, when the stream topology processes the event.

The stream topology's handler for PStateWrite events begins, as always, with a retry number check. It consults the valid-invokes PState to determine whether the retry number in the event matches the currently active retry generation. If the numbers match, the write is current, and the topology applies it to the backing PState using a task-local transform. If the numbers do not match, the write is stale — it was issued by a node that has since been abandoned — and the event is discarded without being applied. This single check is the mechanism that eliminates double writes.

To see why this works, return to the counter example. The node increments the counter and the write goes into the depot as a PStateWrite event with retry number three. The node then fails. The execution system increments the retry number to four and restarts the node. The stream topology is now checking writes against retry number four. When it processes the PStateWrite event from the failed attempt, it sees retry number three, which no longer matches. The event is discarded. The counter is not incremented. When the restarted node increments the counter again, it does so as a new PStateWrite event with retry number four. The topology processes this event, sees a matching retry number, and applies the increment exactly once. The store reflects the result of one increment, not two.

This is the same retry generation filter that governs the main execution topology, applied wholesale to store writes. It is not a special case — it is the same pattern, used again because the same problem is present. Any depot event that can be produced by a retried execution is subject to the possibility of delivering stale data. The retry number filter is the universal answer to that possibility. Once you have the vocabulary of retry numbers and valid-invokes PState, you can apply it wherever the problem appears, and it works the same way each time.

The partitioner for the PState write depot routes events by key. Because backing PStates are partitioned by key across the cluster, routing writes by key ensures that each write event lands on the task that owns the relevant partition of the target PState. This is co-location for writes: the topology processing the write event already has local access to the PState it needs to update, with no network hop required. This is the same co-location principle used throughout the system, now applied to the write path.

There is a cost to this approach, and it is worth naming honestly. Every store write requires one additional depot append — the PStateWrite event — before it is reflected in the backing PState. Depot appends are fast, but they are not free. There is latency in the path from the node's write call to the moment the write becomes visible to readers. In exchange for that cost, the system buys a correctness guarantee: you never have to reason about whether a write happened once or twice. The write is attributed to a specific retry generation of a specific execution. If that generation is current, the write applies. If it is not, the write is discarded. The outcome is deterministic, regardless of what failures occurred between the write being issued and being processed.

This is the fundamental trade Agent-o-rama makes throughout its design. Direct operations are faster but fragile in the presence of failures. Indirections through depots are slightly slower but robust. The streaming depot introduces indirection to protect execution throughput. The human input depot introduces indirection to carry responses into parked threads. The PState write depot introduces indirection to protect write semantics. In each case, the cost is measured and small — one additional depot event on a path that might produce dozens of other events anyway. The benefit in each case is a correctness property that would otherwise require complex application-level logic to achieve. The indirection does the work so the application does not have to.

Taken together, the three subsystems examined in this part — streaming, human-in-the-loop, and store writes — represent the three most important interactions between agent node functions and the world outside the execution graph. Data flows out through streaming. Human responses flow in through the human input mechanism. Mutations flow to persistent stores through the write depot. Each subsystem solves a distinct problem, but each solution is expressed in the same vocabulary: a depot carries the events, a topology validates and processes them, and a PState holds the resulting state. The vocabulary does not change. Only the concern changes.

What is remarkable about this architecture is that the correctness guarantees are not written into each subsystem individually. They are inherited from the structure that all three share. The retry number filter works for streaming because streaming events are depot events. It works for store writes because write events are depot events. It would work for any new concern you added to the system, as long as that concern was expressed as events in a depot. This is the deep design payoff of Rama's event-sourcing model: you write the validation logic once, at the topology level, and it applies universally. The system does not need a special case for streaming retry cleanup, a separate mechanism for invalidating pending human input on retry, or a dedicated guard against double writes. All three problems are solved by the same mechanism, applied uniformly. The sophistication is in the model, not in the number of exception handlers.

# Part Six: The Microbatch Topologies

## Chapter 16: The Stall Detector — How Retries Are Triggered

Every distributed system must eventually answer the question of how it knows when something is stuck. In a single-threaded program running on a single machine, this is almost trivial — a watchdog process on the same machine can check whether a thread is making progress and take action if it is not. The machine has full visibility into the work it is doing. But in a distributed system, the work of a single logical operation is often spread across many tasks running on many machines, and no single machine has a complete view of the whole. This is the fundamental challenge that Agent-o-rama's stall detector must solve: how do you know when an agent execution has stopped making progress when the execution itself is a distributed thing, with its events flowing through a depot and its state maintained across a cluster of tasks?

Agent-o-rama's answer is a dedicated microbatch topology driven by a periodic tick depot. A tick depot is simply a depot that emits events on a schedule — once per second, once per ten seconds, whatever interval the configuration calls for. Each tick is a heartbeat that wakes up the stall detector topology and tells it to do its work. The topology itself does not run continuously; it sleeps until a tick arrives, then performs a coordinated scan of the cluster's execution state, then sleeps again until the next tick.

When the tick fires, the stall detector topology scans the active-invokes set in the shared PState. The active-invokes set is exactly what its name suggests: the collection of all agent-ids for executions that are currently running. An execution enters this set when it is first created and leaves it when it completes, either successfully or with a terminal error. Any execution that remains in the set is, by definition, still active. The stall detector walks through every entry in this set and asks a simple question: has this execution made progress recently?

Progress, in this context, is defined precisely. A NodeComplete event being processed is progress. When the stream topology receives a NodeComplete event for a given agent execution, it records a timestamp — the "last-progress" timestamp — in the execution's record in the root PState. The stall detector compares the current time against this recorded timestamp. If the difference exceeds a configurable threshold, the execution is considered stalled. The threshold is typically generous enough that transient slowdowns — a language model API taking longer than usual, a network hiccup causing a retry of a downstream call — do not trigger a false stall detection. But if a node has been running for several minutes with no NodeComplete arriving, it is reasonable to conclude that something has gone wrong.

This is where the valid-invokes PState becomes essential. The valid-invokes PState is maintained by the stall detector microbatch topology, and it records, for each active execution, a retry generation number. When an execution is first created, its generation is zero. When the stall detector decides that an execution is stalled and needs to be retried, it increments the generation number for that execution in the valid-invokes PState. The generation number is a version counter, and it is the mechanism by which Agent-o-rama fences off stale events from earlier, now-abandoned execution attempts.

To understand why this matters, consider what happens in the interval between when a stall is detected and when the retry begins to run. There may be events already in flight — NodeComplete events from a node that was, in fact, making slow progress and did eventually finish, or ack events acknowledging work that was dispatched some time ago. These in-flight events were generated by the old execution attempt. Without some way to identify them as stale, the stream topology would process them, updating PState entries that now belong to the new execution attempt. The result would be corrupted execution state — records from two different attempts interleaved in a single logical execution.

The generation number solves this cleanly. Every event that carries execution context — NodeComplete, ack messages, and so on — carries the generation number it was created with. When the stream topology receives an event, it looks up the current generation for that execution in the valid-invokes PState. If the event's generation number does not match the current generation, the event is discarded. It is stale. It belongs to an old attempt that has already been superseded. This filter operates on the hot path of event processing, and it is precise: events from the current generation pass through, events from any previous generation are silently dropped.

When the stall detector determines that an execution needs to be retried, it takes two actions atomically, within a single microbatch commit. First, it increments the generation number in the valid-invokes PState. Second, it appends a RetryAgentInvoke event to the main agent depot. This event carries both the agent-id and the new, incremented generation number. The stream topology receives this event, reads the retry invocation, reinitializes the execution state in the root PState for the new generation, and schedules the first node of the execution again. The old execution is effectively erased and replaced with a fresh start, but with the same identity — the same agent-id — so that clients waiting on the result are none the wiser.

This brings us to why microbatch is the right choice for the stall detector, rather than stream. The difference is not cosmetic. A stream topology processes events individually — one tick, one processing step, one commit. If you tried to implement the stall detector as a stream topology, each tick event would trigger a scan of the active-invokes set, but that scan would happen within the processing of a single event, without any atomic relationship to the scans happening on other tasks for other partitions. There would be no single moment at which the state of all active executions was inspected together and all retry decisions were committed together. Some executions might be scanned on one tick and others on the next, creating a window during which the valid-invokes PState and the retry events written to the depot are out of sync.

With microbatch, the entire scan of the active-invokes set — across all tasks, across all active executions — happens within a single batch commit. All stall detections and all generation increments and all RetryAgentInvoke events are committed together as an atomic unit. Either the entire batch succeeds and the system is in a consistent state where stalled executions have been retried and their generations have been incremented, or the batch fails and none of it happened and the next tick will try again. This is the atomic coordination boundary that microbatch provides, and it is exactly what reliable stall detection requires.

The stall detector and the generation filter are two halves of a single fencing mechanism. The stall detector decides when to act. The generation filter ensures that when it acts, the old execution cannot contaminate the new one. Neither half works without the other. Together they form the foundation of Agent-o-rama's ability to recover from stuck executions without operator intervention — a production system that can heal itself when individual nodes or network calls fail to complete.

## Chapter 17: The Analytics Microbatch Topology — Rules and Telemetry

The analytics topology is Agent-o-rama's system for making sense of what has already happened. Where the stream topology is concerned with what is happening right now — executing nodes, updating execution records, emitting results — the analytics topology sits downstream of that activity and asks a different kind of question: of all the executions that have completed, which ones should trigger an action? Which ones should contribute to a metric? What does the population of completed executions tell us about how the system is performing?

The topology has two jobs, and it does them in the same pass. The first job is rule evaluation: for each completed invocation that has not yet been evaluated against a given rule, check whether it satisfies the rule's conditions and, if so, trigger the rule's configured action. The second job is telemetry aggregation: for each completed invocation, extract any defined metric values and accumulate them into the time-series telemetry PState. Both jobs are driven by the same tick depot, which fires on a configured schedule — typically every few seconds — and both jobs share the same scanning mechanism: the cursor.

The cursor is the organizing principle of the analytics topology, and it is worth spending some time with it because the same pattern appears in many distributed systems that need to process an ever-growing log of data reliably. Each rule has a cursor per task. A cursor is simply a pointer — specifically, the invoke-id of the most recently processed invocation for that rule on that task. When the analytics tick fires, each task looks at the root PState starting from the position of the cursor and reads forward up to a configurable batch size. These are the invocations that have completed since the last tick but have not yet been evaluated against this rule. The topology processes them in order, advances the cursor to the invoke-id of the last invocation it processed, and commits. On the next tick, scanning resumes from exactly where it left off.

Think of it this way: the cursor is a bookmark in a very long book of completed invocations. Each tick, the topology opens the book to the bookmark, reads a chapter, moves the bookmark forward, and closes the book. The book grows at its front end as new invocations complete, and the bookmark pursues it from behind. The distance between the front of the book and the bookmark is the lag: the number of invocations that have completed but not yet been evaluated. In a healthy system, this lag stays small. In a system under heavy load or with a slow rule action, the lag may grow. The cursor makes this visible and measurable.

Rule evaluation is more than just checking whether an invocation completed. A rule is a filter with a structured set of conditions. When the topology evaluates a rule against an invocation, it checks several things in sequence. First, scope: is this rule configured to apply to all agents, or only to a specific one? If the invocation belongs to an agent that the rule does not cover, it is skipped immediately. Second, status: did this invocation succeed, or did it error? Some rules are only interested in successful executions; others specifically target failures. Third, sampling rate: rules can be configured to apply to only a fraction of matching invocations, which is useful when you want to evaluate a slow or expensive action — like calling a language model judge — on a representative sample rather than every execution. Fourth, conditions on the invocation's input, output, and metadata: a rule might specify that it only applies to invocations where a particular metadata field is set, or where the output contains a certain structure, or where the input exceeds a certain size.

An invocation that passes all of these filters is considered a match. The topology then dispatches the match to the rule's action. The action function receives the full context of the invocation: the input that was passed to the agent or node, the output that was produced, the metadata the invocation carried, the timing information including how long each node took, and the run information that identifies which experiment or configuration was active during this execution. What the action does with this context depends on what the rule is configured to do. It might call an LLM judge and store the resulting evaluation score. It might add the invocation to a dataset for later fine-tuning. It might call a webhook to notify an external system. It might execute custom logic — any code the developer has registered as a rule action. The analytics topology does not prescribe what actions do; it guarantees that matching invocations reach them exactly in the order they completed, with no invocation being missed and no invocation being skipped over.

After all invocations in the current batch have been processed, the cursor advances to the invoke-id of the last invocation in the batch, and the commit happens. The cursor advancement and all resulting state changes — scores written to the telemetry PState, dataset entries created, whatever the actions produced — are committed atomically as a single microbatch. Either all of it commits, or none of it does.

This atomic commit boundary is also what makes backfill straightforward. If you define a new rule and want it to evaluate against historical invocations — perhaps you want to score everything from the past month against a new quality judge — you simply reset the cursor for that rule to the invoke-id of the earliest invocation you want to include. The topology will begin reading forward from that position on the next tick. There is no special backfill mode, no batch job to launch, no separate infrastructure to configure. The cursor is just a number, and moving it backward is the same operation as moving it forward. The topology does not know or care whether it is doing forward processing or backfill. It reads from the cursor, processes, advances, and commits. This uniformity is a significant operational advantage: the code that handles normal operation is identical to the code that handles historical replay.

The second job of the analytics topology — telemetry aggregation — happens in the same scan pass. As the topology reads each unprocessed invocation, it also evaluates any metric definitions that apply to it. A metric is defined by a value function: a function that takes an invocation record and extracts a number from it. Latency is a common metric — the total wall-clock time from when the invocation was created to when it completed. Token count is another — the total number of tokens consumed by all language model calls within the execution. Error flag is a binary metric that is one if the invocation failed and zero if it succeeded. Evaluator scores, if any rules ran LLM judges against this invocation, can themselves be aggregated as metrics. Human feedback scores, if a human reviewer rated the output, are another.

The extracted value is accumulated into the telemetry PState using a data structure called a T-Digest sketch. A T-Digest is a probabilistic data structure designed for streaming computation of percentile statistics. Rather than storing every individual value — which would grow without bound as more invocations complete — a T-Digest maintains a compact summary of the distribution of values it has seen. From this summary you can compute the median, the ninety-fifth percentile, the ninety-ninth percentile, and similar statistics with bounded error. The analytics topology appends each new metric value to the appropriate T-Digest in the telemetry PState, and the telemetry PState reflects the up-to-date distribution of that metric across all invocations processed so far.

The processing guarantee for the analytics topology is worth stating precisely. Because the cursor advances atomically with the processing commit, if the topology fails partway through a batch — say, a machine crashes after processing ten invocations but before the batch is committed — the topology will restart from the same cursor position. Those ten invocations will be processed again. This means the guarantee is "at least once" rather than "exactly once." An LLM judge might evaluate the same invocation twice; a T-Digest might receive the same value twice. For analytics purposes, this is almost always acceptable. The error introduced by an occasional duplicate is small compared to the operational complexity of a true exactly-once system. If a specific use case requires exactly-once guarantees, additional deduplication logic can be added to the action, but the default behavior embraces the simplicity of at-least-once.

The parallelism of the analytics topology is one of its most important properties. Because each task has its own cursor, rule evaluation across the entire cluster is embarrassingly parallel. If the module is configured with thirty-two tasks, then thirty-two independent portions of the invocation history are being evaluated simultaneously and independently. Task twelve is evaluating its slice of invocations while task seven evaluates its slice and task twenty-nine evaluates its own. There is no coordination between tasks during the evaluation phase. Each task commits its own cursor independently. The only shared state is the telemetry PState, and writes to it are partitioned by metric identity, so even those writes are distributed. This is one of the reasons that adding tasks to the cluster scales the analytics throughput nearly linearly — there is very little work that cannot be parallelized by simply adding more tasks.

## Chapter 18: The Garbage Collector — Managing State Growth

The root PState and the node PState are the living memory of Agent-o-rama's execution machinery. Every running execution has entries in these PStates — the execution record, the node records, the timing data, the token counts, the nested operation logs. As long as an execution is active or recently completed, these entries need to be there. But in a long-running production system, executions complete and new ones begin continuously, around the clock. If completed executions are never removed, both PStates grow without bound. After weeks or months of operation, the memory footprint would be enormous, reads would slow down as data structures grew larger, and the system's resource consumption would be driven not by the current load but by the accumulated history of everything that had ever run.

Agent-o-rama addresses this with a dedicated garbage collection topology, driven by its own tick depot. The GC tick fires on a much slower schedule than the stall detector or analytics ticks — perhaps every few minutes — because the consequences of a GC cycle are durable state deletions, and there is no urgency to GC individual executions the moment they become eligible. The GC topology is background infrastructure: it runs when it runs, it cleans up what it can, and it leaves the hot-path stream topology free to focus entirely on active executions.

When the GC tick fires, the topology identifies completed executions that are old enough to be eligible for removal. What "old enough" means is determined by the retention policy, which is a configurable parameter. An execution might be retained for a day — long enough for a developer to inspect the trace if something went wrong. It might be retained for a week in environments where historical analysis is important. It might even be retained until the analytics topology has confirmed, via the cursor mechanism, that it has been fully processed against all configured rules, ensuring that no invocation is GC'd before every rule has had a chance to evaluate it. The retention policy is a knob, and the right setting depends on the operational needs of the deployment.

The GC topology does its work in two phases, and understanding why requires thinking about what other parts of the system might be doing at the same moment the GC is running.

In the first phase, the topology moves completed invocations that have passed their retention deadline into a GC-marked set within the shared PState. The entries themselves are not deleted yet — they are simply flagged as candidates for deletion. The GC-marked set is a staging area. The GC commits this marking atomically at the end of the first batch.

Then, in a subsequent tick, the topology reads from the GC-marked set and performs the actual deletions: it removes the flagged entries from the root PState and from the node PState. This commit completes the cleanup.

The reason for this two-phase design is that deletion is not safe the moment an execution completes. Other parts of the system may still be actively reading that execution's data. The analytics topology, if it is running behind its cursor, might be processing an invocation that the GC would otherwise delete. A client application might be in the middle of fetching the trace for a completed execution to display in the web UI. A query topology call might be reading the execution's node records to assemble a full view of what happened.

If the GC deleted entries immediately on the first pass, any in-flight read that happened to be looking at one of those entries at the moment of deletion would encounter a sudden absence. The data would simply be gone mid-read. The result, depending on the system, would be an error returned to the client, a corrupted trace view, or — in the case of the analytics cursor — an invocation that was never processed because it was deleted before the cursor reached it.

The two-phase approach handles this gracefully. The first phase marks the entries but leaves them in place. In-flight reads that are happening during the first phase can still see the full data. By the time the second phase runs — in the next GC tick, minutes later — those in-flight reads have long since completed. The data has been read by everything that needed it, and now it can be safely removed. Think of it as a graceful shutdown protocol applied to data rather than to services. When you want to shut down a server, you stop accepting new connections but finish serving the connections that are already open. When the GC wants to delete an execution record, it stops the record from being considered an active part of the system but finishes serving the reads that are already in progress.

The relationship between the GC and the analytics cursor deserves explicit attention. The analytics cursor creates a soft ordering constraint: the GC should not delete an invocation before the analytics topology has advanced its cursor past that invocation. If it did, the analytics topology would try to read an invocation record that no longer exists. The retention policy is the mechanism that enforces this constraint in practice. By configuring the retention window to be longer than the maximum expected analytics lag — if the analytics topology is running a few seconds behind and the retention is set to twenty-four hours, there is an enormous safety margin — you ensure that the GC never races ahead of the analytics cursor. In deployments where the analytics topology is slow for some reason — perhaps a rule is dispatching to a slow LLM judge and creating a large backlog — the retention policy can be extended to prevent data loss.

This interaction between the GC and the analytics cursor illustrates a broader principle: in a distributed system built on microbatch topologies, the topologies are not truly independent. They operate on shared state, and the timing relationships between them have consequences. The GC assumes that the analytics cursor is not too far behind. The analytics cursor assumes that the invocations it wants to read have not yet been GC'd. These assumptions are managed through the retention policy, which is a single configuration knob that controls the margin of safety between the two.

To close this part of the book, step back and look at all three microbatch topologies together. The stall detector, the analytics engine, and the garbage collector are structurally the same. Each is woken by a periodic tick from a tick depot. Each performs a scan of shared PState — the active-invokes set, the invocation history, the completed executions — and derives a set of actions from the scan. Each commits the results of that scan atomically, so that the post-commit state is always consistent and complete. Each tracks its position in the data it is scanning, so that on the next tick it can resume where it left off rather than starting over.

The choice to implement all three as microbatch topologies rather than stream topologies is not arbitrary. It reflects the nature of the work each one does. Stall detection requires looking at many executions together and making coordinated decisions about which ones to retry. Analytics requires scanning a shared history and advancing a shared cursor. Garbage collection requires a two-phase commit across a shared set of PState entries. All of these tasks involve coordination across multiple data points, and all of them require the atomic commit boundary that microbatch provides. A stream topology, processing events one at a time, could not provide that boundary. Microbatch can.

The trio of topologies forms a complete operational picture. The stall detector ensures that stuck executions are recovered. The analytics engine ensures that completed executions contribute to rules, metrics, and datasets. The garbage collector ensures that the system does not accumulate state without limit. Together, they constitute the background intelligence of Agent-o-rama — the processes that keep the system healthy, measurable, and sustainable over the long lifetime of a production deployment.

# Part Seven: Advanced Mechanics

## Chapter 19: Module Updates and the Graph Version System

One of the harder problems in any long-running distributed system is what happens to in-flight work when you deploy new code. In a web server, the answer is simple: requests are short-lived, so you wait for active requests to drain and then restart the process with the new version. In a batch job, the answer is also manageable: jobs run to completion before you redeploy, or you restart the job from scratch with the new code. But in an agent system, "in-flight work" has a different character entirely. An agent execution may span minutes, hours, or longer. It may be suspended, waiting for a human to respond. It may be executing a deep fan-out of parallel branches, each waiting on a language model. These executions did not just start — they are partway through their graphs, with some nodes already completed and their results recorded, with downstream nodes queued and waiting for results that have not yet arrived. Telling users they cannot deploy updates until all active executions complete is not a viable answer. Agent-o-rama's solution to this problem is the graph version system.

The core idea is straightforward even though the implementation has subtleties. Every time an agent's node definitions change, the system assigns a new version number to that agent's graph definition. This version number is not merely a deployment label — it has operational significance at runtime. When an update arrives and the graph version increments, every active execution in the system has a record of which version governs it. That record lives in the root PState entry for the execution, stored alongside the agent-id, the arguments, and the timing information we have discussed in earlier chapters. The execution's graph version is the lens through which all subsequent processing must be interpreted.

The stream topology enforces three update modes, each representing a different answer to the question of how a particular update should interact with executions already in progress. The first mode is Continue. When the topology processes a node event for an execution, it checks the graph version stored in that execution's root PState entry against the current version of the agent graph. If the versions differ, the topology applies new node definitions to the remaining unexecuted work. Any nodes that have already run keep their results — those are committed, immutable entries in the node PState, and they do not change. But any emit records from those completed nodes that have not yet spawned their downstream child nodes, and any nodes already scheduled but not yet executed, will be processed using the new code. This is the lowest-disruption mode. The execution does not restart. It simply transitions to the new code as it encounters fresh work. An execution that is sixty percent complete when you deploy an update will finish its remaining forty percent under the new definitions, while the already-completed sixty percent remains unchanged.

The second mode is Restart. When the topology detects a version mismatch in Restart mode, it sends the execution a RetryAgentInvoke event carrying the new graph version. This causes the execution to begin again from the start — the initial AgentInitiate event is replayed, a fresh root PState entry is created with the new graph version, and the execution proceeds as if it had never started. The node PState entries from the old attempt are still present and correctly labeled with their retry generation, but the retry filter we examined in Chapter Nine ensures they no longer affect the new attempt. Restart mode is appropriate when the changes between graph versions are substantial enough that old and new code are genuinely incompatible. If a node's output shape changes, or if the graph's structure changes such that the sequence of nodes in the old version corresponds to a different sequence in the new version, trying to splice new code into a half-completed old execution could produce incoherent results. Restart avoids the incoherence by starting fresh.

The third mode is Drop. In Drop mode, when the topology detects a version mismatch, the execution is simply removed from the active-invokes set and its results are discarded. No retry, no continuation, no record of a result. Drop is forceful. It is appropriate for cases where the update reflects such a fundamental change that completing the old execution — in any form — is not meaningful. If the agent's purpose has been redefined, if the output format has changed in a way that would confuse downstream consumers, or if correctness requires that all results be produced by the same version of the code, Drop is the right answer.

The history of which graph versions have existed is stored in the shared PState, keyed by version number. Old versions are not deleted when a new version is deployed. They are retained as long as there are active executions still using them. This is necessary because Continue mode, in particular, may need to examine an older version to determine which nodes were already completed under that version. Once all active executions have either finished, restarted, or been dropped, the old version's entry in the shared PState becomes eligible for garbage collection.

The subtlety of Continue mode deserves more attention, because it is not just a matter of running new code on future nodes. It is running new code against execution state that was produced by old code. The node functions may have different signatures. They may emit to different downstream targets. They may produce outputs in a different format than the old code expected its consumers to receive. Continue mode is safe only when the developer has designed the update to be backward-compatible with in-flight state. This is the same challenge that database schema migrations face — changing a live system without invalidating existing data — and it requires the same discipline. The system supports Continue mode because there are genuine cases where updates are backward-compatible, and the smooth continuation of in-flight executions is worth preserving in those cases. But the system cannot verify backward compatibility for you. That judgment belongs to the developer.

This brings us to the deeper observation that the graph version system depends on. Making deployment non-disruptive to in-flight executions requires the system to know, in precise detail, what state those executions are in. Which nodes have completed. Which emits have been processed. Which downstream nodes are scheduled. This is exactly what the root PState and node PState record. The event-sourced design that we established in Part One — the design that stores every completion and every emit as durable, committed state — turns out to be a prerequisite for this feature. A system that tracked execution progress only in memory, or only in the stream topology's own local state, could not offer any of these three update modes. It would have no reliable picture of in-flight executions from which to reason about how to handle an update. The graph version system is one more downstream benefit of the event-sourced design, which keeps revealing new consequences as the system's requirements grow more sophisticated.

## Chapter 20: Forking — How the UI's Fork Feature Works

The web UI includes a feature that, once you understand it, becomes one of the most useful tools for iterative development and debugging. It is called forking. Forking lets you take any completed execution, modify its inputs or metadata, and run it again. Not just by submitting a new invocation with different arguments — that is trivially possible with any agent system. Forking is more specific and more powerful than that. It lets you re-run only the parts of the execution that would be affected by your changes, replaying the unchanged parts from cache rather than re-executing them. If your agent has an expensive first stage that retrieves and processes a large corpus of documents, and you want to change only the final synthesis step, forking lets you run the modified synthesis step without paying the cost of the retrieval step again.

A fork begins with a ForkAgentInvoke event appended to the main agent depot. This event carries the original execution's agent-id, the modified arguments or metadata that represent the change you want to explore, and a fork context. The fork context is the heart of the mechanism — it describes which specific nodes in the original execution should be re-executed with the new inputs and which should be replayed from the original's cached results. The stream topology's fork handler receives this event and begins constructing the forked execution. It creates a new root PState entry with a fresh agent-id, so the fork is a distinct execution with its own identity and its own result. It stores the fork context alongside the standard execution metadata. Then it replays the original execution's graph up to the fork point by reading the node PState entries of the original execution and re-creating them in the fork's namespace.

The determination of which nodes are affected is called the fork-affected nodes calculation, and it is not as simple as identifying the nodes whose immediate inputs changed. In an agent graph, nodes can have complex dependency relationships. If you change the input to node A, and node A's output feeds into node B, and node B's output feeds into an aggregation that also receives input from nodes C and D, then the fork needs to re-execute A and B at minimum, and may need to re-examine the aggregation as well. The topology works through the graph structure, identifying which aggregation boundaries are downstream of the changed inputs and tracing the consequences forward. Only the affected portions of the graph are re-executed. Nodes upstream of the fork point that produced unchanged outputs are replayed from the cached results in the original execution's node PState.

To see how this plays out in practice, consider an agent that has three stages. The first stage calls a retrieval tool to fetch relevant documents from a knowledge base. The second stage runs those documents through a scoring model to rank them by relevance. The third stage synthesizes the top-ranked documents into a final answer using a language model. You ran this agent, examined the results, and decided that the prompt for the synthesis stage needs adjustment. That change affects only the third stage. When you submit a fork with the modified prompt, the fork-affected nodes calculation determines that the first and second stages are upstream of the change and their outputs are unchanged. Those stages are replayed from cache — their node PState entries are copied into the fork's namespace, effectively telling the stream topology that those nodes already completed with known results. Only the third stage is re-executed. The cost of the fork is the cost of one model call for synthesis, not three stages of work. If the retrieval call was expensive or the scoring model was slow, the savings are substantial.

The fork context that is constructed from this analysis is a precise specification: these invoke-ids from the original execution are to be replayed from cache, and these invoke-ids are to be re-executed from scratch. The fork context is stored in the new execution's root PState entry so that the stream topology can consult it as it processes each node. When the topology encounters a node that the fork context marks for replay, it copies the original node PState entry rather than scheduling a NodeOp. When it encounters a node marked for re-execution, it schedules a NodeOp as it would for any normal execution. The two paths converge on the same topology logic for handling the downstream consequences of each node's completion, whether the completion came from real execution or from replay.

Replaying from cache is worth explaining precisely, because it is doing something that sounds trivial but is architecturally significant. Instead of running the node function again and waiting for new results, the system copies the output records from the original execution's node PState entry into the forked execution's node PState entry, under the forked execution's agent-id and invoke-ids. From the perspective of the stream topology processing the fork, these entries are indistinguishable from freshly computed results. The topology sees a node PState entry with a completed status, an emit list, a nested ops record, and timing information, and it processes it exactly as it would process a NodeComplete event from a real execution. The node, in every sense the topology can observe, ran instantaneously. The performance benefit is that the underlying work — the model calls, the store reads, the expensive external operations — does not happen again. The correctness property is that the topology does not need a special path for replay; it treats replayed results identically to real results.

The ack-val requires careful handling when a fork changes which branches of an aggregation are executed. When a fork re-executes some children of an aggregation but replays others from cache, the initial ack-val for that aggregation in the fork cannot be the same as in the original execution. It must be calculated to reflect only the branches that are being re-run. A query topology computes the adjusted ack-val before the fork execution begins. This adjusted value accounts for the contributions that will be replayed — they are effectively pre-loaded into the ack-val in their completed state — so that the aggregation end node fires correctly when only the re-run branches have reported back. The XOR properties we examined in Chapter Twelve make this pre-loading straightforward: to pre-load a replayed branch's contribution in its completed state is simply to not include that contribution in the initial ack-val at all.

It is worth pausing to appreciate why forking is a first-class feature rather than an afterthought, and why it would be difficult to add to a system that was not designed for it. The node PState already records everything needed to replay an execution. Every input the node received, every output it produced, every emit it declared, every nested operation it performed — all of it is in the node PState, committed durably, identified by a stable invoke-id. Forking is the natural consequence of having a complete execution record. The infrastructure that was built to provide observability — to let you examine any execution in the trace page and understand exactly what happened — turns out to also be the infrastructure that enables replayability. The two features are not independent. The design that makes an execution fully inspectable also makes it fully replayable. This is a pattern worth recognizing: in systems built on event sourcing and explicit state recording, observability and reproducibility tend to come together as a pair.

## Chapter 21: The Query Topology Layer — Serving the UI and Clients

Everything we have examined so far has been push-driven. Events arrive at depots, stream topologies process them, PStates are updated. The system reacts to inputs. But clients — whether the web UI browsing executions or a program waiting on a result — need to pull information out of the system. They need to ask questions and receive answers. This is the role of query topologies. Query topologies provide the synchronous read path, and they are the layer through which all external consumers interact with the system's accumulated state.

A query topology is a named procedure that accepts arguments, reads from one or more PStates using path expressions, and returns a result. It is not a stream processor. It does not run continuously. It runs when called, completes when it has assembled a result, and returns. From the caller's perspective, it behaves like a remote function call.

The trace page query is the most structurally complex of the query topologies. Given an agent-id, it traverses the node PState starting from the root invoke-id for that execution. It follows the emit chains recorded in each node's entry, expanding children depth-first, reconstructing the execution tree in memory as it reads. The result is a hierarchical structure of nodes with their timing, nested ops, and status — the data that the trace page renders as a visual execution tree. The query does not compute this structure; it reads a structure that was written incrementally by the stream topology as the execution progressed. Each NodeComplete event that was processed wrote another piece of the puzzle into the node PState, and the trace page query assembles those pieces on demand.

The invocations list query is a paginated scan of the root PState, returning summaries of recent or matching executions. It supports filtering by metadata, time range, and completion status. Metadata-based filtering is efficient because the shared PState maintains a metadata index — an additional index structure, written by the stream topology at execution start, that maps metadata keys and values to sets of agent-ids. The invocations list query reads this index first to identify matching executions, then fetches the corresponding root PState entries. Without this index, metadata filtering would require a full scan of the root PState, which would be prohibitively slow as the number of executions grows.

The current graph query returns the current agent graph definition: node names, edges, configuration, and the current version number. It reads from the latest entry in the shared history PState. This is the query the web UI uses to render the graph visualization, and it is also used internally by the fork-affected nodes calculation to understand the structure of the graph at the time of a fork.

The dataset and evaluator queries support the evaluation infrastructure. They search the global datasets PState by name, description, or tag and return paginated results. These queries are structurally simpler than the execution queries — the datasets PState is organized for retrieval by these fields, and the queries are direct lookups into that organization. The experiment results query is more computationally involved: it aggregates per-invocation scores stored in the datasets PState into summary statistics — average scores, latency distributions, comparisons across evaluation targets. This aggregation happens at query time, reading the individual result records and computing the statistics in the query topology itself.

The client API's blocking result method deserves particular attention because it illustrates a capability that is not commonly available in distributed systems. When a client calls this method, it is asking to receive the result of an execution that may not yet be complete. Under the hood, this is implemented as a foreign proxy on the root PState's result field. In Rama, a foreign proxy is a mechanism for reading a PState field reactively: the proxy does not poll for the field to change, and it does not impose a timeout that requires a retry. It simply parks the calling thread until the field transitions from null to a non-null value, then returns the value. The stream topology writes to the result field when it processes an execution's final completion. The moment that write commits, the proxy unblocks and the value is returned to the client. No polling, no exponential backoff, no coordination protocol between the client and the system. The liveness guarantee comes from Rama's foreign proxy mechanism, and the only condition under which the call does not eventually return is the condition under which the execution itself never completes.

The performance characteristic of query topologies follows from the same co-location principle that governs everything else in the system. Query topologies run on the Rama task that owns the relevant PState partition. A trace page query for an execution whose node PState is partitioned to task seven runs on task seven. The reads are local to that task. There is no query planner, no optimizer, no temporary materialization of intermediate results. There are direct reads from co-located state, assembled according to the logic of the query procedure, and returned. This is fast not because any particular implementation trick is employed, but because the architecture ensures the data is where the computation is.

This is also the right moment to contrast query topologies with the stream and microbatch topologies we examined earlier. Stream and microbatch topologies are push-driven: events arrive and processing happens in response. Query topologies are pull-driven: a client asks and the system reads. They represent fundamentally different computation models, and the distinction is not merely academic. Push-driven topologies have guaranteed execution ordering, retry semantics, and exactly-once processing guarantees enforced by the Rama platform. Pull-driven query topologies have none of these properties by default — they run once, return a result, and do not have retry guarantees in the same sense. But they share the same state store. A stream topology writes execution records, and a query topology reads them. The two models coexist because the system's needs are genuinely different in the two directions: durable, ordered, exactly-once processing on the write side, and low-latency, synchronous reads on the query side.

## Chapter 22: Cross-Module Communication — Mirror Depots and PStates

Agent-o-rama is a multi-module system. A module is the unit of deployment in Rama — a self-contained package of depots, PStates, and topologies that is deployed to a cluster and runs as an independent service. Agent-o-rama itself is organized into multiple modules, and the agents it manages can span module boundaries. An agent defined in one module can call an agent defined in another module as a subagent. At the application level, this looks no different from calling a subagent within the same module. Under the surface, the mechanism is different, and understanding it reveals something important about how Rama composes distributed systems.

When two components exist in the same module, their interactions are straightforward. An event appended to a depot in module A is processed by a topology in module A. A PState written by module A's topology is readable by any query topology in module A. Everything is co-located by definition. Cross-module interaction breaks this assumption. If module A wants to append to a depot owned by module B, the append must cross a module boundary — which in a distributed system means crossing a network boundary.

Rama's mirror mechanism is the answer to this challenge. A module can declare a mirror of another module's depot or PState. The mirror is a local structure that the Rama platform keeps up to date with the source. Reads from a mirror are task-local and do not require network calls to the source module. The platform handles the replication. From the perspective of code running in the mirroring module, a mirror looks and behaves like a locally owned resource.

Mirror depots work in the outbound direction. When a node function in module A wants to append an event to a depot owned by module B, it uses a mirror depot declaration. The append goes to the local mirror first, and the Rama platform takes responsibility for routing it to the source module asynchronously. The node function does not need to know that module B exists, where module B is deployed, or which tasks module B runs on. It appends to the mirror, and the platform handles the rest. The delivery semantics — durability, ordering, exactly-once guarantees — are preserved across the module boundary.

Mirror PStates work in the inbound direction. When a node function in module A wants to read a PState owned by module B, it uses a read-only mirror. The platform replicates the relevant partitions of module B's PState into module A's task structure. Reads from this mirror are local reads — no network hop, no coordination with module B. The mirror is updated by the platform as module B's topology writes to the original PState. The replication is not instantaneous — there is a propagation delay — but for the typical use case of reading configuration, agent definitions, or the output of recently completed executions, the delay is small enough to be unimportant.

When a node calls get-mirror-store, it receives a store implementation backed by a mirror PState. The interface is the same as a regular store — the node function does not need to know whether the backing PState is local or mirrored. Reads work the same way. The one explicit difference is that writes are rejected. Mirror stores are read-only by design. Allowing writes would create an ownership ambiguity — who owns this data? — and would make the replication semantics much harder to reason about. The read-only constraint is not a limitation in practice, because the correct way to write to another module's state is always through events appended to that module's depot, not through direct PState writes.

Mirror query topology invocation follows a different path. When a node calls get-mirror-query-topology-client, it receives a proxy that routes query calls to the source module's query topology. The routing in this case does cross the module boundary — query topology calls are not replicated locally because they involve computation, not just data. But from the node function's perspective, the proxy interface is the same as a local query topology client. The function calls a named query with arguments and receives a result. The platform handles the routing, and the result comes back synchronously.

The design implication of the mirror mechanism is worth making explicit. Cross-module agent calls are not fundamentally different from within-module calls at the application level. The module boundary is a deployment concern, not an application concern. A node function that calls a subagent does not need to specify whether that subagent lives in the same module or a different module. If it lives in a different module, the mirror mechanism handles the bridging. The node function issues the same call, receives the same result, and works through the same AgentNode interface. The infrastructure difference — local versus mirrored — is resolved at the framework level, not at the application level.

This has a consequence for how you think about module organization. Modules are the unit of deployment, and they can be updated independently. An organization that manages a large Agent-o-rama deployment might divide agents across modules by team, by business function, or by scaling requirements. Team A's agents are in module A, Team B's agents are in module B. Either team can update their module without coordinating with the other. Agents in module A can still call agents in module B, through mirror depots and mirror PStates, without any changes to the application code. The mirror mechanism is what allows this independence to coexist with genuine interconnection.

The broader point is that the mirror mechanism resolves a tension that would otherwise be irreconcilable. A system composed of independent modules gains flexibility: modules can be scaled, updated, and maintained independently. But a system whose components cannot communicate efficiently is a system whose components cannot collaborate. The mirror mechanism gives you both. Each module is self-contained in the sense that matters for deployment and operations. But the platform replicates the data structures that enable communication, so module boundaries do not become communication barriers. Modules are the unit of deployment but not the unit of isolation. The system scales and deploys as a collection of independent modules, but it reasons and communicates as a single coherent system.

# Part Eight: Putting It All Together

## Chapter 23: A Complete Trace Through the System

Every chapter up to this point has examined one component in depth: a particular depot, a specific PState, a topology's processing logic, a partitioning mechanism. That approach is necessary — you cannot understand the whole without understanding the parts. But there comes a point where the parts need to be reassembled, and that is what this chapter does. What follows is a single agent invocation traced from beginning to end, touching every layer of the system in the order it actually encounters them. Nothing here is new. The point is to watch it all work together.

The scenario is deliberately simple: an agent with two nodes, no fan-out, no aggregation, no retry. The client calls agent.invoke. What happens next is a sequence of eleven steps, each of which will be described with enough detail to locate it in the architecture you now know.

---

The first step is the client call itself. When a client calls agent.invoke, the client library constructs an AgentInitiate event containing the invocation arguments, the agent identifier, and the metadata the caller supplied. It then appends this event to the main agent depot. The critical question — which task receives it? — is answered by the depot partitioner. For AgentInitiate events, the partitioner makes a random selection from the available tasks. Say it selects task 7. The event is appended to task 7's partition of the main depot, and task 7 will be the home task for this execution. The assignment is made here, once, and it will govern every subsequent routing decision for the lifetime of this invocation. The client's call has now returned from its perspective — the submission is complete — though the result is nowhere near ready yet.

The second step belongs to the stream topology running on task 7. It picks up the AgentInitiate event from the depot. The first thing it does, as always, is check the retry generation — this is a fresh execution, so the check passes trivially. Then it creates an entry in the root PState for this execution, keyed by the agent-id A that was assigned to this invocation. That entry records the invocation arguments, the graph version governing this run, the caller's metadata, and an initial ack-val. Alongside the root PState entry, the topology creates an entry in the node PState for the first node, assigning it invoke-id N1, recording which node it corresponds to, marking it as pending, and noting that its target task is task 7 — the home task, where the first node will run by default. Finally, the topology constructs a NodeOp message targeting N1 on task 7 and routes it. The topology commits. Its work for this event is done. The root PState now reflects an active execution, and task 7 has a pending NodeOp in its queue.

The third step is the node executor on task 7 picking up the NodeOp for N1. The executor pulls a virtual thread from its pool, constructs an AgentNode context for the invocation, initializes the thread-local list of NestedOp records, and calls the user's first node function with the invocation arguments. The function begins executing. From the user's perspective, this is ordinary code — a function receiving arguments and about to do some work. From the system's perspective, the virtual thread is now live on task 7, and everything it does is being quietly observed.

The fourth step is the model call inside the node function. The user's code calls the AgentNode interface to invoke a language model. The client library underneath that interface sends an HTTP request to the model provider and parks the virtual thread on the response. The virtual thread is now suspended — it holds no operating system thread, just a lightweight continuation object on the heap. The node executor's carrier thread is free to pick up other work. Some time passes — milliseconds to seconds, depending on the model and the prompt. The model responds. The JVM wakes the virtual thread, delivering the response as the return value of the model call. The thread resumes as if it had simply been waiting in line. The AgentNode implementation records the model call as a NestedOp entry in the thread-local list: the model name, the token counts, the latency, the result. The user's function continues.

The fifth step is the emit call. The user's first node function calls emit on the AgentNode, passing the name of the second node and the value it wants to hand downstream. The emit is not sent anywhere yet — it is recorded in a second thread-local list alongside the NestedOps. The function returns. There is nothing more to do on this thread.

The sixth step is the executor's cleanup. Now that the node function has returned, the executor collects everything: the list of emits the function declared, the accumulated NestedOps, and the result if the function declared one. It packages these into a NodeComplete event addressed to the home task — task 7 — and appends that event to the main agent depot. The event carries the invoke-id N1, the agent-id A, the agent-task-id pointing to task 7, and the full payload of emits and nested ops. The virtual thread is released back to the pool. The executor's responsibility ends here. It has produced exactly one artifact — the NodeComplete event — and handed it to the depot.

The seventh step is the stream topology on task 7 processing the NodeComplete for N1. The topology confirms the retry generation, then updates the node PState entry for N1: it writes in the emit list, the nested ops, the timing information, and marks N1 as complete. Then it works through the emits. There is one emit — to the second node. The topology creates a new node PState entry for this second node, assigning it invoke-id N2. It needs to choose a target task for N2. For a regular, non-aggregating node, the choice is random. Say it selects task 12. The node PState entry for N2 records task 12 as its target, notes the invoking emit, and marks N2 as pending. The topology constructs a NodeOp for N2 and routes it to task 12. It commits. At this point, N1 is fully recorded in the node PState with all its nested operations, and task 12 has a new NodeOp waiting for it.

The eighth step takes place on task 12. The node executor there picks up the NodeOp for N2 and runs the second node function on a virtual thread, just as task 7 ran the first. The second node reads from a key-value store. This read is implemented as a task-local select on the backing PState for that store, and because the backing PState is partitioned by key and the appropriate key's partition lives on task 12, the read is local — no network hop is required. The result comes back immediately and is recorded as a NestedOp in the thread-local list, along with the key, the path, and the timing. The second node calls result, declaring the final output of the entire invocation as a specific value.

The ninth step is the executor on task 12 constructing the final NodeComplete. It packages N2's result, its NestedOps — including the store read — and the absence of any emits into a NodeComplete event. This event is addressed to the home task, task 7, because all lifecycle events for this execution route back to the agent-task-id regardless of where the node ran. The event is appended to task 7's partition of the main depot.

The tenth step is the stream topology on task 7 processing this final NodeComplete. It confirms the retry generation, then updates the node PState entry for N2 with the NestedOps, the result, and timing information, marking N2 as complete. Because this NodeComplete carries a final result — rather than merely emits — the topology does two additional things. It updates the root PState entry for agent-id A, writing the result value into the result field and marking the execution as complete. And it removes A from the active-invokes set in the shared PState, which tracks which executions are currently in flight across the cluster. The topology commits. The execution is finished. Every record that describes what happened, from the initial arguments to the model call's token count to the store read's latency, is now persisted in the PStates on task 7.

The eleventh step returns us to the client. When the client called agent.invoke, it did not simply submit the event and walk away — it also established a foreign proxy on the result field of the root PState entry for agent-id A. The foreign proxy is a live subscription: Rama evaluates the read path when it is first established and re-evaluates it whenever the underlying PState changes. For most of the execution's lifetime, the result field is null. But in the tenth step, the stream topology wrote the result value into that field. The change is detected by the foreign proxy. Rama re-evaluates the read path, sees the populated result field, and delivers the value to the client thread that has been waiting on it. The client's invoke call returns. From the caller's perspective, the call was blocking: they submitted arguments and received a result. Everything described in the preceding ten steps happened invisibly between those two moments.

---

Stepping back from the sequence, a few properties of this execution are worth naming explicitly, because they are not obvious from the individual steps but emerge clearly when you see the whole.

The execution touched exactly two tasks: task 7, which was the home task and processed all lifecycle events for the execution, and task 12, which ran the second node. No other task was involved. The routing mechanism ensured that the AgentInitiate event, both NodeComplete events, and all PState reads and writes for the execution's core records landed on task 7. The second node ran on task 12 because a randomly selected target happened to be task 12, not because any coordination step placed it there. Each task operated on its own local data.

No network hop was required to read PState during node execution on each respective task. When task 7 ran the first node, any PState access was local to task 7. When task 12 ran the second node, the key-value store read was a local select because the relevant key's partition happened to live on task 12. This is the co-location strategy in action: the placement decisions made upfront — home task assigned at AgentInitiate time, target task assigned at emit time — are what make local reads possible. The locality is not accidental; it is the payoff of the partitioning design.

The result was delivered to the client via a reactive read with no polling. The client did not submit a request and then loop asking whether the result was ready. The foreign proxy mechanism delivered the result the moment it became visible in the PState, driven by the topology's commit rather than by any client-initiated check. This is what makes the system responsive rather than merely fast: the notification path runs from the infrastructure outward to the client, not from the client inward to the infrastructure.

The complete trace of this execution is now stored in the node PState on task 7, including the model call's timing and token counts from N1 and the store read's timing from N2. This record is the raw material for the analytics pipeline. When the cursor-based analytics topology eventually scans past this execution, it will find everything it needs to compute percentiles, detect anomalies, and update the telemetry PState — because the node executor recorded it, the NodeComplete event carried it, and the stream topology persisted it. Observability is not an add-on. It is woven into the execution model.


## Chapter 24: Design Decisions and the Tradeoffs They Create

A system's architecture is a record of decisions made under uncertainty. Every design choice in Agent-o-rama reflects a judgment about what matters: what to optimize for, what to accept as a cost, and what to treat as non-negotiable. This chapter examines those choices honestly — not as a celebration of clever engineering, but as an accounting of what each decision costs and what it buys. Understanding the tradeoffs is what lets you reason about the system's behavior in cases the documentation does not cover.

---

The most foundational decision in the system is the choice of event sourcing over direct mutation. When the stream topology processes an event, it does not simply update the PState. An event first arrives at the depot — which means it is durably logged — and only then does the topology apply it as a PState transition. Every state change in the system follows this path. The upside is significant: if the topology crashes mid-processing, Rama restarts it from the last committed position in the depot. The log is still there. The PStates reflect exactly the state as of the last successful commit. The processing logic picks up where it left off with no data loss and no need for crash recovery logic. Replay, which would otherwise require careful engineering, comes for free from the log. Retries become safe because the log is immutable and the retry generation filter is the only mechanism needed to distinguish current events from stale ones.

The cost of this approach is write amplification. Every state change requires two writes: one to append the event to the depot, and one to apply the event to the PState. For a system processing thousands of NodeComplete events per second, those depot writes accumulate. Depot append latency is low but not zero, and the volume of appends is proportional to the activity of the system. An alternative design — writing directly to a distributed state store, accepting that failures may produce partially applied states and require compensating logic — would have lower write overhead at the cost of significantly more complex failure handling. Agent-o-rama judges that the complexity of handling partial mutations is a worse problem than the overhead of the double write. That judgment is reasonable, but it means the depot is a resource that grows over time and must be managed.

---

The partitioning strategy is the second fundamental decision: using a custom depot partitioner that reads a pre-assigned task identifier from each event, rather than deriving a partition from a hash of the event's content. Hash partitioning is the default in most distributed systems because it distributes load automatically and requires no upfront assignment. Agent-o-rama's custom partitioner does something different — it uses a routing key embedded in the event to route to a specific task, and that routing key is assigned when the execution begins, not when the event is created.

The benefit of this approach is co-location: because all events for an execution route to the same task, and because PStates are partitioned by the same key, the stream topology on that task can read and write PState without network round-trips. The execution's home task becomes a self-contained processing environment for that execution. This is the property that makes the trace described in the previous chapter efficient.

The cost is that load distribution is not automatic. If a long-running execution happens to be assigned to task 7, and then ten more long-running executions are also assigned to task 7 by chance, task 7 carries a disproportionate load for the duration of those executions. Hash partitioning would have spread those executions across the cluster. The custom partitioner concentrates them on whatever task was randomly selected. In practice, with a large enough cluster and a large enough volume of concurrent executions, the law of large numbers smooths out these fluctuations. But the system does not guarantee uniform load distribution, and workloads with a small number of very heavy executions can create task hotspots that hash partitioning would have avoided.

---

The choice of virtual threads over asynchronous futures is a decision about the programming model as much as the execution model. An asynchronous future-based system — the kind built on CompletableFutures chained with callbacks, or on reactive streams frameworks — can achieve similar concurrency properties. When a model call is pending, the calling thread does not block; instead, a callback is registered to receive the result when it arrives. The thread is free to do other work in the meantime.

Agent-o-rama uses virtual threads instead, which means node functions are written as ordinary blocking code. You call a method to invoke a model, and you wait. The thread parks. The result arrives and the thread wakes. This is the simplest possible programming model: sequential code, one thing after another, exactly as you would write it for a single-threaded application. The benefit is readability and debuggability. Stack traces reflect actual call sequences. Error handling is try-catch rather than error-callback chaining. Testing is straightforward because the code is not split across multiple callbacks.

The cost is a dependency on Java 21 and a JVM that correctly implements virtual thread carrier-thread unmounting on blocking operations. Virtual threads were a preview feature for years before becoming stable in Java 21. Not every library that claims to support virtual threads actually unmounts the carrier thread on every blocking call — some operations still pin the virtual thread to its carrier thread, which defeats the point. The system requires careful validation that every blocking call in the hot path correctly unmounts. That validation work is ongoing rather than a one-time cost. An async future-based system would not have this dependency and would run on earlier JVM versions. The tradeoff is a better programming model at the cost of a tighter platform dependency.

---

The XOR ack-val mechanism for detecting aggregation completion is a choice with a particularly tight shape. The alternative — a counter that is incremented when a child is created and decremented when a child completes — is simpler to explain and simpler to implement locally. The ack-val is less obvious. It requires understanding XOR's commutativity and self-inverse properties to trust it.

The benefit of the ack-val is that it requires no centralized coordination. Each XOR operation is local to the task that processes it. The aggregation task monitors a single field in its local PState. No task needs to consult any other task to determine whether the aggregation is complete. In a large fan-out with hundreds of parallel children, this matters: a centralized counter becomes a serialization point that all children must pass through to report their completion. The ack-val eliminates that bottleneck.

The cost is the requirement that branch counts and ack contributions are computed correctly at emit time. If a contribution is XORed in when a child is created but the same contribution is not correctly XORed out when the child completes, the ack-val never returns to its initial value and the aggregation never fires. The correctness of the mechanism depends on the contributions being symmetric. This is not difficult to maintain — the framework manages it, not the application author — but it means the mechanism is less forgiving of implementation errors than a counter would be. A counter that fails to decrement will eventually produce an obviously wrong result. An ack-val that fails to remove a contribution will silently stall the aggregation forever. The ack-val trades a more obvious failure mode for a better performance characteristic.

---

For telemetry, the system uses T-Digest sketches rather than storing raw measurement values. T-Digest is a data structure that computes approximate quantiles — median, ninety-fifth percentile, ninety-ninth percentile — from a stream of values using a fixed, configurable amount of memory, regardless of how many measurements are incorporated. The benefit is straightforward: a T-Digest for an execution node that has run ten million times occupies the same memory as one for a node that has run a hundred times. The telemetry PState does not grow unboundedly as the system processes more executions. Percentiles are available immediately from the sketch without scanning raw data.

The cost is approximation. A T-Digest's percentile estimates are not exact. The error is bounded and configurable, and in practice the ninety-fifth and ninety-ninth percentile estimates are accurate to within a fraction of a percent for most distributions. But if the exact timing of the slowest one percent of executions matters for your analysis — if you are debugging a specific extreme outlier — the T-Digest cannot give you the precise value, only a close estimate. If exact values were required, the system would need to store raw measurements, which either means unbounded storage growth or a bounded window that loses historical data. For the use case of operational monitoring and performance trending, approximate percentiles are entirely sufficient. For forensic analysis of individual extreme events, you would need to look at the node PState records directly rather than the telemetry sketches.

---

The analytics pipeline uses cursor-based scanning rather than a publish-subscribe model. When a NodeComplete event is processed by the stream topology, the analytics pipeline does not receive a notification immediately. Instead, the cursor-based analytics topology periodically scans the node PState looking for records it has not yet processed, advances a cursor as it goes, and applies telemetry rules to each newly discovered record. The benefit of this approach is that it provides exactly-once processing semantics for analytics. Because the cursor marks a stable position in the PState, a failure mid-scan simply restarts from the last cursor position. No record is processed twice, and no record is skipped. This also means backfill is trivially supported: if a new telemetry rule is deployed, you can reset the cursor to the beginning of history and the rule will be applied to all past records as if they were new.

The cost is latency between execution completion and analytics visibility. There is a delay — typically seconds, configurable — between the moment a NodeComplete event is processed by the stream topology and the moment the cursor-based analytics topology discovers the resulting node PState record and updates the telemetry sketches. For operational dashboards where near-real-time visibility is expected, this delay may be noticeable. A publish-subscribe model — where the stream topology notifies the analytics pipeline directly when a record is created — would eliminate this latency. But a pub-sub model introduces at-least-once delivery semantics by default, requires additional logic to prevent duplicate processing, and does not naturally support backfill. The cursor-based approach accepts a fixed latency in exchange for strong processing guarantees and operational simplicity.

---

The separate streaming depot is a choice about traffic isolation. When a node emits a streaming chunk, that chunk goes to a dedicated streaming depot rather than the main agent depot. The benefit is that streaming throughput does not compete with execution management traffic. During a long generation where a language model produces dozens of chunks per second, those chunks would otherwise intermingle with NodeComplete events and AgentInitiate events on the main depot. A busy streaming session could delay execution events that are on the critical path of other agents' progress. The separate depot gives each class of traffic its own processing pipeline with no cross-contamination.

The cost is an additional depot write for every streaming chunk. Each chunk requires an append to the streaming depot before it can be processed by the streaming topology and become visible in the root PState. This adds a layer of latency to the streaming path — small, but present. A system that routed streaming chunks through the main depot would have one fewer write per chunk. The tradeoff is that the streaming path is slightly slower in isolation, but the rest of the system is protected from being slowed by streaming volume. For a production system where streaming sessions can be high-volume and unpredictable, protecting the main execution path is worth the marginal cost.

---

Stepping back from the individual tradeoffs, a pattern emerges. Every decision described in this chapter makes the same kind of choice: it accepts a modest cost in raw performance or implementation simplicity in exchange for a stronger guarantee in reliability, observability, or correctness under failure. Event sourcing adds write overhead but makes failure recovery trivial. Custom partitioning may create hotspots but makes task-local processing the default. The ack-val requires careful contribution tracking but eliminates coordination bottlenecks. T-Digest accepts approximation but bounds telemetry storage. Cursor-based analytics introduces latency but provides exactly-once guarantees. The separate streaming depot adds a depot write but protects the main execution path.

This coherence is not accidental. It is the mark of a system built with a specific set of priorities held consistently throughout the design. The priorities are production reliability, observability, and fault tolerance — not implementation simplicity and not raw throughput maximization. When you encounter a behavior in Agent-o-rama that puzzles you, asking "which of these priorities does it serve?" will usually lead you directly to the explanation. The design is coherent in the sense that all the decisions point in the same direction. They are not a collection of locally optimal choices assembled from convenient components. They are a single consistent argument about what a distributed agent framework should optimize for, expressed in every layer of the architecture.

# Conclusion: Rama as the Right Foundation

## Chapter 25: Why Rama Makes This Possible

The previous chapter catalogued the tradeoffs in Agent-o-rama's design. But there is a prior question that deserves its own answer: why is any of this design even feasible? The answer is not just that the engineering was careful, though it was. The answer is that the platform Agent-o-rama is built on provides a set of primitives that make each of the design choices tractable. Take away Rama, and the entire architecture becomes a wishlist rather than a system. Understanding what Rama contributes is the only way to appreciate what Agent-o-rama actually had to build.

Start with depots. A depot is an append-only log partitioned across a cluster, with exactly-once processing guarantees for consumers. This means that when Agent-o-rama appends a NodeComplete event to the depot, that event will be processed by the stream topology exactly once, even in the presence of failures. If the topology crashes and restarts, it picks up from its last committed position. It does not process the event again. It does not skip the event. The depot is durable: events are not lost when a machine fails. The partitioning is built in: events are routed to specific partitions without any application-level routing code. These are not simple properties to implement. A durable, partitioned, exactly-once-delivery log at production scale is a substantial piece of infrastructure. Agent-o-rama's retry semantics, its fault tolerance, its ability to recover from topology crashes without losing execution state — all of these depend on the depot's guarantees. Without Rama, this would be a durable message broker that had to be built, configured, operated, and integrated separately.

Then there are PStates. A PState is a distributed, replicated, strongly consistent indexed data structure that topology code can read and write without network overhead when the operation is local to the task. This last property — local access without network overhead — is the one that makes the co-location strategy work. When the stream topology on task 7 reads the node PState entry for N1, that read is fast because the PState partition lives on task 7 and the access is local. If PState were an external distributed key-value store, every PState read and write would be a network call. The stream topology would spend most of its time waiting for network responses rather than processing events. The entire performance argument for co-location would collapse. PStates are also replicated, which means their data survives machine failures without the application needing to implement replication logic. And they are strongly consistent, which means the stream topology never reads stale data from a previous topology instance that may have applied partial state transitions. Without Rama, this would be a distributed KV store — with its own networking, replication, consistency protocol, and operational overhead — integrated via a client library.

Topologies are the third major Rama primitive, and they provide a processing model where failures automatically replay from the log. A stream topology is not a thread that might die and leave state corrupted. It is a processing loop that is always restartable from a well-defined position. Agent-o-rama's stream topology contains no mutable variables — it reads events, reads and writes PStates, and commits. This statelessness is only safe because Rama's topology model guarantees that if the topology crashes between a PState write and a commit, the write is rolled back. The topology will replay from the last successful commit and re-apply the transition cleanly. Achieving this behavior without Rama would require implementing a change-data-capture system — something that tracks which PState changes have been durably committed versus which are provisional — along with transaction semantics for the state transitions.

Query topologies are Rama's mechanism for synchronous reads on top of the same PState that streaming topologies maintain. This is how the foreign proxy mechanism works. A client establishes a read on a specific field in a PState — the result field of a root PState entry, or the streaming buffer, or the list of pending human input requests. Rama evaluates that read immediately and then re-evaluates it every time the underlying PState changes, pushing the new value to the client. Without this mechanism, Agent-o-rama would need a change-data-capture system wired to a pub-sub delivery layer, with subscriptions tracked in some additional state store, and a mechanism to correlate PState changes with interested subscribers. The foreign proxy does all of this as a platform primitive.

The mirror system handles cross-module data sharing. When the analytics topology needs to see data from the agent execution module, it accesses it through a mirror — a read-only replica of the source PState, kept in sync by the Rama runtime. Without mirrors, cross-module access would require an external service call, an API contract between modules, versioning, authentication, and all the operational machinery of service-to-service communication. With mirrors, it is a read on a local replica. The runtime handles synchronization. The modules remain independently deployable without sharing a process.

Virtual tasks give the framework the primitives to run node functions in a controlled, partitioned way. A virtual task is a unit of computation with a known location in the cluster's partition scheme. Agent-o-rama's node executor runs on virtual tasks, which means the executor has predictable co-location properties. The NodeOp message can be routed to a specific task and will be processed by the executor on exactly that task. Without this, routing a node invocation to a specific location in the cluster would require application-level service discovery, load balancing, and connection management.

Taken together, what Rama provides is a complete substrate for distributed stateful stream processing. What it saves Agent-o-rama from building is extensive. There would need to be a durable message broker — Kafka or a similar system — with all the configuration and operational care that entails. There would need to be a distributed KV store for execution state — DynamoDB, Cassandra, or similar — with its own consistency and replication considerations. There would need to be a change-data-capture system to propagate PState changes to interested clients, wired to a pub-sub delivery mechanism. There would need to be a distributed lock or coordination service — ZooKeeper or etcd — to handle cases where multiple processes might need to agree on state transitions. There would need to be a cross-service RPC framework for cross-module communication, with all the versioning and fault tolerance that implies. There would need to be a replication mechanism for high availability, a deployment system for cluster management, and a scaling system to add and remove capacity. Each of these is a well-understood problem with good solutions — but each solution brings its own operational footprint, its own failure modes, its own integration surface. The sum of those operational footprints is a distributed systems stack that would require dedicated engineering effort to build and maintain, separate from the agent framework itself.

This is what it means for Agent-o-rama to be built on Rama rather than assembled from commodity components. It is not simply that the components are already there. It is that the components compose coherently because they share a model. The depot and the PState share a partitioning scheme, so co-location is achievable. The topology and the depot share exactly-once semantics, so retry logic is clean. The query topology and the stream topology share the same PState, so live reads and write processing are consistent without any synchronization layer in between. If each component were from a different vendor with a different data model, these compositional properties would not be available. You would have a distributed system built from parts, and the seams between the parts would be the source of most of your failure modes.

This is the platform bet that Agent-o-rama makes, and it is worth naming clearly: the design assumes Rama, pervasively and deeply. It is not a portable architecture that happens to use Rama as a convenient backend. It is a design whose specific properties — co-location, cursor-based analytics, live query delivery, retry semantics — are all expressions of Rama's capabilities and idioms. That bet has a cost. The cost is that Agent-o-rama is not portable. If Rama were no longer viable, the migration path to any other backend would require redesigning most of the mechanisms described in this book. The foreign proxy would need a replacement. The depot partitioning would need a replacement. The exactly-once guarantees would need a replacement. The tradeoff is deep capability in exchange for deep dependency.

This is worth stating without dismissal, because the same tradeoff applies to every non-trivial distributed system. A system built on Kafka has Kafka's log semantics baked into its design. A system built on DynamoDB has DynamoDB's consistency model and partitioning strategy shaping its access patterns. No distributed system floats free of its infrastructure dependencies. The question is never whether you have an infrastructure dependency. The question is whether that dependency is deliberate and well-considered — whether the design is shaped by what the infrastructure actually provides, or whether it merely hopes the infrastructure will not let it down. Agent-o-rama's dependency on Rama is deliberate and well-considered. Every mechanism in the system traces back to a specific Rama capability that makes it possible. That traceability is what distinguishes a platform bet from a vendor lock-in accident.


## Chapter 26: What Understanding the Internals Changes

There is a particular moment in learning a system when the documentation stops being enough. The documentation tells you what to call and what to expect back. It tells you what the configuration parameters mean and what errors you might encounter. It gives you a vocabulary and a set of guarantees. What it cannot give you — what only a working understanding of the internals provides — is the ability to reason about the system's behavior in cases the documentation does not cover. That is what this chapter is about: the shift from using a system to understanding it, and what that shift makes possible.

When you know that NodeComplete events are the unit of state change — that every consequence of a node's execution is encoded in a single depot event — you understand what it means for a node's argument list or result to be large. The depot event must carry those arguments and results in its payload. A node that receives a ten-megabyte document as an argument is a node whose AgentInitiate event weighs ten megabytes, and whose NodeComplete event carries whatever portion of that document was included in the result. Depot events are not just logical records — they are bytes that must be stored, replicated, and transmitted to the stream topology for processing. Large payloads do not cause failures, but they do cause the depot to grow faster and the stream topology to spend more time on serialization and deserialization. When you see a system that feels slower when dealing with large payloads, you no longer need to guess at the cause. You know exactly where the weight accumulates.

When you know that streaming chunks travel through a separate depot from the main agent depot, you understand why streaming throughput does not saturate the main execution pipeline. A node running a long generation — producing hundreds of chunks over the course of a conversation — is writing intensively to the streaming depot while the main execution depot carries only the usual NodeComplete events and occasional lifecycle signals. The two depots do not share processing capacity. Other agent executions running concurrently are unaffected by the streaming volume of any single execution. This is not something the documentation needs to promise — it is a structural property of the architecture. When you understand the structure, you understand the guarantee.

When you know about the cursor-based analytics scan — that the analytics topology periodically advances a cursor through the node PState, applying rules to newly discovered records — you understand why there is a brief delay between an execution finishing and its metrics appearing in the telemetry charts. The stream topology committed the node PState record. The analytics topology has not yet scanned past it. The cursor has not yet advanced to that position. The rule has not yet been evaluated. The T-Digest sketch has not yet been updated. All of this happens reliably, but it happens on the analytics topology's schedule, not on the execution's schedule. If your dashboards show metrics that are a few seconds behind the actual executions, you are seeing the cursor interval at work, not a bug.

When you know about the XOR ack-val, you understand why aggregation completion is reliable even when branches complete out of order on different machines. The ack-val does not depend on receiving contributions in a specific sequence. Each contribution is XORed in when its branch is created and XORed out when its branch completes. The order does not matter because XOR is commutative. The ack-val can only return to its initial value when every contribution that was added has been removed, regardless of the order in which removals arrive. When you have a large fan-out with branches completing at wildly different speeds — some fast, some waiting on slow model calls — the aggregation end node does not fire prematurely for the fast ones and does not hang waiting for a specific sequence from the slow ones. It fires exactly when the last branch reports back, with no polling and no coordination overhead. This is not magic. It is arithmetic. But knowing it is arithmetic means you can trust it in a way that "it uses some kind of tracking mechanism" does not support.

When you know about the retry generation filter — that every event carries a retry number and is silently dropped if that number does not match the current valid generation — you understand why retrying an execution is safe even if the failed execution's events are still in-flight in the depot. There may be NodeComplete events from the failed run sitting unprocessed in the depot queue. When the stream topology eventually reaches them, it checks the retry number. The failed run's retry number is lower than the current generation. The events are discarded. They cannot corrupt the state of the restarted run because the filter stops them before they reach the state-writing logic. You do not need to worry about drain time, about in-flight event cancellation, about the window between a failure and a retry during which old events might slip through. The filter handles it, always, by construction. Retrying is safe because the filter is always applied before any state transition, and the filter's correctness does not depend on timing.

When you know about the partitioning strategy — that executions are randomly assigned to tasks, and that all events for an execution route to its home task — you can reason about load distribution in a way that generic advice about horizontal scaling does not provide. Concentrating many concurrent executions on a single module instance is fine. The executions will distribute across the tasks in that instance, each assigned to a different home task, each running its nodes on whichever tasks are randomly selected. The module instance does not become a bottleneck just because it is handling many concurrent invocations. But an execution pattern where a single execution generates an extremely large fan-out — emitting hundreds of times from a single node — may create momentary pressure on the home task, because all those NodeOp messages for the child nodes are routed from the home task and all the corresponding NodeComplete events eventually route back to it. A system with many concurrent small executions distributes well. A system with a small number of very large fan-outs may see the home tasks of those executions become temporarily hot. This is a behavioral property you can reason about once you understand the partitioning model, but not before.

These connections between internal knowledge and practical intuitions are not merely interesting. They change how you operate the system. When an execution is running slowly, you know to look at event payload sizes before assuming the cluster is undersized. When streaming seems to lag during periods of high execution volume, you know the two concerns are separated by depot and should not interfere — which means if they are interfering, something structural has changed. When metrics are delayed, you know the cursor interval is the dial to turn. When a large fan-out is slower than expected, you know to examine whether the home task is under unusual load. In each case, the internal knowledge translates into a specific, actionable hypothesis rather than a vague suspicion that something is wrong somewhere.

This is the practical payoff of architectural understanding. It does not replace operational experience. It does not replace load testing or monitoring or careful incident analysis. But it provides the frame into which all of those things fit. Without an internal model, an unexpected behavior is a mystery. With an internal model, it is a diagnostic exercise with a tractable answer.

There is a deeper observation that ties everything in this book together, and it is the right place to close. A system's architecture is its deepest documentation. The README tells you how to start it. The API reference tells you what to call. The configuration guide tells you what knobs exist. But the architecture tells you what the system is optimized for, what it treats as the hard problems, and where it draws its reliability guarantees from. Agent-o-rama's architecture — event sourcing on Rama depots, co-located PState processing, XOR aggregation detection, cursor-based analytics, virtual thread execution — is an argument. It is an argument that production reliability, observability, and fault tolerance are more important than implementation simplicity. It is an argument that a well-chosen platform dependency is better than a maximally portable design. It is an argument that the right place to handle correctness concerns is at the infrastructure layer, not the application layer, because infrastructure-layer correctness is available uniformly to everything built on top of it.

You may agree with that argument or you may not. You may have different priorities for your system. But when you understand the argument — when you can trace each design choice back to the priority it serves — you are no longer using a black box. You are a collaborator in the design. You can evaluate the tradeoffs against your own requirements. You can reason about which guarantees apply to your use case and which costs you are paying for properties you may not need. You can contribute to the system's evolution because you understand what it is trying to be.

That is what this book was for. Not to impress you with the system's cleverness. The system is clever, but cleverness is not the point. The point is that you now understand it — precisely, concretely, and deeply enough to trust it when it behaves correctly and to diagnose it when it does not. That understanding is what a working knowledge of the internals provides. It is yours now.

## Appendix A: Depot, PState, Topology — Verbal Definitions

A depot is an append-only, durably stored, partitioned event log. You interact with a depot by writing events to it. Once written, an event is stored persistently and replicated across the cluster according to the configured replication factor. Events within a single partition are ordered strictly: an event written before another will always be read before it. A depot is not passive storage. Topologies subscribe to depots and receive events as they arrive, making a depot the trigger for computation as well as the record of it. If you have used Kafka, the mental model is similar, but the integration between depot and topology in Rama is tighter: the platform manages the relationship between writing to the depot and consuming from it, removing the operational gap that exists when you wire together a broker and a processing framework separately.

A PState, which stands for partitioned state, is a distributed, indexed, durable data structure — the persistent state layer of a Rama application. The simplest way to picture it is as a very large nested map: paths within the map can hold any combination of maps, lists, and scalar values, and the whole structure is partitioned across the tasks that make up the topology. PState writes happen within topology processing, and they are consistent within a partition: two writes to the same partition are always serialized, and a reader on the same partition sees the effects of all prior writes. A PState can also be read from any other part of the cluster through a foreign proxy, which crosses the network to the partition holding the requested data and returns the current value. PState data is not the source of truth in an event-sourced system — the depots that produced the events are — but a PState is the materialized view of that truth, kept up to date by the topologies that consume events.

A stream topology is a Rama computation layer that processes events one at a time. For each event, the topology reads state from one or more PStates, transforms the event, writes any resulting changes to PStates, and commits. The next event is not picked up until the commit for the current event completes. This one-event-one-commit model provides low latency — the time between an event arriving and its effects becoming visible in a PState is typically a few milliseconds — and it provides exactly-once processing semantics within a partition. Stream topologies are the right choice when events can be handled independently and when responsiveness to individual events matters.

A microbatch topology is a Rama computation layer that processes events in time-windowed batches rather than one at a time. The topology accumulates events arriving within a configurable time window and processes the entire batch together as a single atomic unit, committing all resulting PState changes at once. The time window introduces some latency relative to stream processing, but it enables coordination that is not possible event by event: a microbatch topology can inspect the aggregate of many events, make decisions that depend on the relationship between events in the batch, and commit all consequences together so that either every change in the batch is visible or none of them are. Microbatch topologies are the right choice when a correct answer requires reasoning about many events together rather than each event in isolation.

A query topology is a synchronous, request-and-reply mechanism for reading PState data. You define a query topology as a named procedure that accepts arguments, performs reads against one or more PStates, and returns a result. A caller invokes a query topology by name, passing the required arguments, and blocks until a result is returned. Internally, Rama routes the invocation to the task that owns the relevant partition of the data being read, executes the read logic locally on that task, and returns the result to the caller. From the caller's perspective, a query topology behaves exactly like a function call: synchronous, typed, and transparent about whether the data was local or remote. Query topologies are how Agent-o-rama exposes execution traces, invocation lists, telemetry statistics, and other structured data to the web UI and client libraries.

A task is Rama's unit of computation: a thread or thread pool running on a specific machine in the cluster, responsible for owning a specific set of partitions from both depots and PStates. When a module is configured to run with thirty-two tasks, the depots and PStates of that module are each divided into thirty-two partitions, and each partition is assigned to exactly one task. The task that owns a partition is the only place where events in that partition are processed and where state in that partition is read and written by topology logic. The number of tasks determines both the degree of parallelism the system achieves and the number of machines the work can be spread across.

Partitioning is the mechanism by which depot events and PState data are divided across tasks. In a depot, partitioning determines which task a given event is routed to. In a PState, partitioning determines which task stores and services reads for a given entry. Both use a partitioner function: a function that takes a key — either the key extracted from an event or the key of a PState entry — and returns the task index that should own it. Partitioner functions can be standard hash functions, or they can be custom. Agent-o-rama defines custom partitioners on its core depots so that events can carry an explicit target task identifier rather than being placed by key hash, which is what makes the co-location strategy possible.

Co-location is the design principle that places an execution's state on the same task as the events that drive that execution. When an agent execution is assigned to task seventeen, its entries in the root PState and the node PState are stored on task seventeen, and every event related to that execution — NodeComplete events, streaming chunks, human input responses — is routed to task seventeen via the custom depot partitioner. The result is that when the stream topology on task seventeen processes any event for that execution, every read and write it performs against those PStates is a task-local operation: no network hop, no serialization cost, just direct access to data structures in memory. Co-location does not eliminate all network traffic in the system — fan-out to child nodes genuinely distributes work across tasks — but it ensures that the hot path of execution, the sequence of reads and writes that happens on every node completion, never requires crossing a machine boundary.

A foreign proxy is the mechanism by which a topology or query topology reads a PState partition that lives on a different task. When the reading code is executing on task three but the PState entry it needs is on task nineteen, Rama handles the cross-task read transparently: it serializes the request, sends it over the network to task nineteen, waits for the response, deserializes it, and returns the value to the reading code. From the code's perspective, the API is the same as a local read. From a performance perspective, a foreign proxy read carries network latency and serialization cost. This is why co-location is designed to minimize the number of foreign proxy reads on the critical execution path. Foreign proxy reads are used deliberately in contexts where they are infrequent — reading the shared PState for config lookups, querying a remote PState from a query topology — but are avoided in the per-event hot path.


## Appendix B: The Full Depot Inventory

The main agent depot is the central depot of the system, and each agent type in Agent-o-rama has its own instance of it. It is partitioned using a custom partitioner that reads a target task identifier directly from the event: if the event carries an explicit target task, it is routed there; if not, it is sent to a randomly selected task. This custom partitioner is the foundation of co-location. Five event types flow through the main agent depot. The first is AgentInitiate, which carries the invocation arguments, execution metadata, the identity of the caller, and optional overrides for the target task and agent identifier. The second is NodeComplete, which carries the invoke-id and retry number of the node that finished, the full list of emits the node declared, its result if one was produced, the accumulated list of nested operations it performed during execution, and any streaming output. The third is NodeFailure, which carries the invoke-id and exception information when a node raises an unhandled error. The fourth is RetryAgentInvoke, which is a synthetic event generated by the stall detector and carries the agent task identifier, the agent identifier, and the expected retry generation number, used to restart a stuck execution. The fifth is ForkAgentInvoke, which carries the original execution's identifiers and a map from existing node invoke-ids to new argument lists, used to spawn a derived execution that replays only the affected portions of the execution graph.

The streaming depot carries NodeStreamingResult events and is partitioned by agent task identifier, routing every streaming event for a given execution to the same task that owns the execution's state. Each event carries a streaming chunk, the agent task identifier, the agent identifier, the node name, the invoke-id of the specific node invocation that produced the chunk, a monotonically increasing index number that allows chunks to be reassembled in order even if they arrive slightly out of sequence, and the retry generation number. The retry number is essential here for the same reason it is essential in the main depot: if an execution is retried, streaming chunks from the failed attempt must not be incorporated into the new attempt's buffer. The streaming depot is separate from the main agent depot so that potentially large and frequent streaming payloads do not contend with the NodeComplete events that are critical to execution progress.

The human input depot handles the pause-and-resume lifecycle of executions that require a human response before they can continue. It carries two event types. The first is NodeHumanInputRequest, which is appended when a node pauses to wait for a human, and carries the agent task identifier, agent identifier, node name, the invoke-id of the paused node, the task that node is running on, and the prompt string to be displayed to the human. The second is HumanInput, which is appended when a human provides a response through the web UI or client API, and carries the original request record plus the response string. The partitioning strategy differs between these two event types by design: HumanInputRequest events are partitioned by agent task identifier, because the request needs to be processed by the task that owns the agent execution's root state, while HumanInput response events are partitioned by the task identifier of the waiting node itself, because the response needs to reach the specific task where the paused virtual thread is waiting to be unparked.

The config depot carries ChangeConfig events for per-agent operational settings such as the maximum retry count. These events are partitioned randomly, meaning they are distributed across all tasks that run the stream topology. Because every task needs to apply any configuration change, random distribution is the correct strategy: over time, every task receives and processes every config event, keeping all tasks consistent. Config events are rare — they arrive on human timescales, driven by operators using the web UI — and their random partitioning reflects the fact that they have no co-location requirement.

The check-tick depot emits periodic tick events on a schedule configured at deployment time, typically every several seconds. These ticks have no payload beyond the fact that they exist. Their sole purpose is to wake up the stall-detection microbatch topology, which then scans the active-invokes set for executions that have not recorded progress within the configured stall threshold. The check-tick depot drives the stall detector, not the stream topology.

The GC tick depot emits periodic tick events on a slower schedule than the check-tick depot, typically on the order of minutes. Like the check-tick, a GC tick has no meaningful payload. Its purpose is to wake up the garbage collection microbatch topology, which identifies completed executions that have passed their retention deadline, marks them for deletion in the shared PState in a first phase, and then removes their entries from the root and node PStates in a subsequent pass. The slower cadence reflects the fact that GC can afford to run less frequently than stall detection and that its operations — durable deletions of PState entries — are more expensive per event.

The PState write depot carries PStateWrite events for all mutations to user-defined stores, including key-value stores, document stores, and PState-backed stores defined within the agent module. It is partitioned by key, using a hash partitioner that ensures writes to the same key always route to the same task. Each event carries the store name, the path expression identifying what to write, the value to write, and an agent source context including the agent task identifier, agent identifier, and retry generation number. The indirection through this depot — rather than writing directly to the backing PState — exists to provide retry safety: the stream topology that processes PStateWrite events checks the retry generation before applying the write, and discards any write whose generation number no longer matches the current generation for that execution. This ensures that a write from a failed execution that completed successfully before the failure is not applied again during a retry, preventing double-write corruption.

The analytics tick depot emits periodic tick events that wake up the analytics microbatch topology. This topology evaluates completed invocations against configured rules, extracts metric values, and accumulates them into the telemetry PState. The analytics tick fires on a schedule similar to the check-tick, typically every few seconds, reflecting the expectation that analytics results should remain reasonably current even in deployments with high invocation rates.

The global actions depot carries events that mutate shared, cross-agent configuration: additions and removals of rules, evaluators, human metrics, feedback queue configurations, datasets, and experiment configurations. These events are processed by the analytics microbatch topology rather than the per-agent stream topology, because they affect shared state rather than any individual execution's state. Partitioning is random, for the same reason as config events: global actions need to be applied everywhere, they arrive infrequently, and they have no meaningful co-location requirement.


## Appendix C: The Full PState Inventory

The root PState is the primary execution state store of the system. It is partitioned by task-id: all entries whose home task is task seventeen live on task seventeen, ensuring that the task processing an execution's events is the same task holding that execution's state. The root PState is keyed first by task-id and then by agent-id, the UUID assigned to each invocation. Each entry is a comprehensive execution record containing the invoke-id of the starting node, the original invocation arguments, any metadata provided by the caller at invocation time, the graph version identifying which version of the agent definition governs this execution, the final result once the execution completes, the current retry count, the ack-val used to track aggregation completion via the XOR mechanism, accumulated runtime statistics including latency measurements and token counts, the set of pending human input requests for any nodes currently paused awaiting a human response, a streaming buffer keyed by node name that accumulates streaming chunks in indexed order as they arrive, and a description of all forked child executions spawned during this invocation. The root PState is created and maintained by the stream topology.

The node PState is the execution graph store, holding one entry for every node invocation across all active and recently completed executions. Like the root PState, it is partitioned by task-id, co-locating node entries with the execution they belong to. It is keyed first by task-id and then by invoke-id, the UUID that identifies a specific invocation of a specific node within a specific execution. Each record contains the agent-id of the parent execution, the node's human-readable name, the invoke-id of the immediate parent node in the graph, and the task-id of the task that owns the parent agent's root record. Critically, it contains the emit list: a structured record of every downstream node this invocation emitted to, including the target node name, the target's invoke-id, the target's assigned task-id, and the arguments passed along. It also contains the nested operations list, which is a complete log of every significant operation performed during this node's execution — model calls with inputs and outputs, store reads and writes, tool invocations, human input requests — each with timing and result. Start and finish timestamps bracket the invocation's execution window. For aggregation nodes, the record also contains the accumulated state of the fan-in: the list of inputs received so far from upstream branches, the current partial aggregate value, and whether the aggregation has been fulfilled. The node PState is created and maintained by the stream topology.

The shared state PState holds cluster-wide coordination data that is not scoped to any single execution. It is not partitioned by execution but is instead organized by content type. It contains four principal structures. The history map records all past and current versions of the agent definition, keyed by version number, and is consulted during live module updates to determine what to do with in-flight executions. The active-invokes set is the authoritative list of all agent-ids currently running; executions enter this set when created and leave it when they complete, and it is the starting point for both the stall detector and the garbage collector. The GC-marked set is a staging area for executions that have been flagged for deletion: they have completed and passed their retention deadline, but the actual deletion of their root and node PState entries happens in the subsequent GC pass. The metadata index is an inverted map from metadata values to sets of agent-ids, enabling efficient lookup of executions by their metadata labels without scanning the entire root PState. The shared state PState is maintained jointly by the stream topology and the microbatch topologies.

The valid-invokes PState maps each agent-id to the current retry generation number for that execution. It is partitioned and co-located with the other execution PStates. The stream topology consults this PState as the very first step of processing any event: if the event's embedded retry generation number does not match the current generation stored here, the event is discarded. This fencing mechanism is what prevents events from stale, previously failed execution attempts from contaminating the state of a current retry. The valid-invokes PState is also the place where the stall detector records a new generation number when it decides to retry a stuck execution. It is written by the stall-detection microbatch topology when a stall is detected and read by the stream topology on every incoming event.

The telemetry PState holds the statistical summaries used by the analytics system to answer questions about execution performance over time. It is keyed by a three-part composite: agent name, metric identifier, and rule name. Together, these three parts identify a specific metric being tracked for a specific kind of execution under a specific analytics rule. The value stored at each key is a NumberStats structure built on top of a T-Digest sketch. A T-Digest is a compact probabilistic data structure that approximates the percentile distribution of a stream of numerical values. Rather than storing each individual measurement, it maintains a set of weighted centroids that together describe the shape of the value distribution, using memory measured in kilobytes regardless of how many millions of values have been accumulated. From a T-Digest, the system can compute approximate percentiles — the median, the ninety-fifth percentile, the ninety-ninth percentile — with bounded error and in constant time. The telemetry PState is written by the analytics microbatch topology and read by query topologies servicing the monitoring UI.

The cursor PState maps each combination of rule-id and task to the invoke-id of the last invocation processed by the analytics topology for that rule on that task. Each task in the module maintains its own cursor independently. When the analytics topology runs, it reads the root PState forward from the cursor position, processes each unprocessed invocation it finds, and advances the cursor to the invoke-id of the last invocation it processed before committing. The cursor ensures that each invocation is evaluated against each analytics rule exactly once per task, regardless of how many analytics ticks fire, and regardless of whether the topology restarts midway through a batch. The cursor PState is also the mechanism that makes historical backfill straightforward: to re-evaluate historical invocations under a new or modified rule, the cursor for that rule is simply reset to an earlier invoke-id, and the analytics topology advances it forward again from there on the next tick. The cursor PState is written and read exclusively by the analytics microbatch topology.


## Appendix D: The Execution State Machine

An execution begins in the Initiated state. This state is entered when the stream topology processes an AgentInitiate event. The topology creates a new entry in the root PState, assigning it an agent-id, recording the invocation arguments, metadata, and graph version, and initializing the ack-val and retry count. Simultaneously, the topology creates an entry in the node PState for the first node in the agent graph and schedules it by routing a NodeOp message to the appropriate task. The execution is added to the active-invokes set in the shared PState. At this point the execution exists in the system's records and its first node is queued for execution, but no user code has run yet.

From the Initiated state, the execution transitions immediately to the Running state as soon as the first node begins executing on its virtual thread. The Running state is the normal, active condition of an execution that is making progress. One or more nodes are executing, and NodeComplete events are flowing through the stream topology as nodes finish their work. Each NodeComplete causes the stream topology to update the node PState entry for the completed node with its emits, result, nested operations, and timing, then create new node PState entries and schedule new NodeOp messages for any nodes the completed node emitted to. The execution remains in the Running state so long as at least one node is still outstanding — still executing or still queued to execute. During the Running state, the root PState's last-progress timestamp is updated with each NodeComplete, providing the stall detector with evidence that the execution is alive.

A subset of the Running state is the Streaming state, entered when one or more nodes begin producing streaming output by calling the stream-chunk function. Streaming and Running are not mutually exclusive conditions — an execution that is streaming is also running — but the streaming behavior is worth describing as its own phase because it involves a distinct path through the system. When a node calls stream-chunk, the node executor appends a NodeStreamingResult event to the streaming depot rather than to the main agent depot. The stream topology processes this event and appends the chunk to the streaming buffer in the root PState, indexed by node name and chunk index. A client watching for streaming output reads from this buffer at the query topology level. Streaming ends when the node that was producing chunks completes and emits a NodeComplete; after that, the streaming buffer for that node is complete and will not receive further chunks.

The Awaiting Human Input state is entered when a node calls the get-human-input function. The node executor appends a NodeHumanInputRequest event to the human input depot. The stream topology processes this event and adds the request to the human-requests set in the root PState, recording the waiting node's name, invoke-id, and prompt. On the task where the node is running, the virtual thread that is executing that node parks itself — it suspends execution and releases its underlying OS thread, waiting to be unparked by a future response. The execution is still considered running from the perspective of the active-invokes set, but that particular node is not making progress. If the human does not respond before the stall detection threshold, the stall detector will eventually trigger a retry. When a human provides a response, a HumanInput event is appended to the human input depot, routed to the waiting node's task. The stream topology processes this event, removes the corresponding entry from the human-requests set in the root PState, and unparks the waiting virtual thread, which resumes executing with the human's response in hand.

The Retrying state is entered when a RetryAgentInvoke event is processed by the stream topology. This event is generated by the stall-detection microbatch topology when it determines that an execution has not made progress within the configured stall threshold. When the stream topology processes RetryAgentInvoke, it first checks that the retry generation number in the event matches the current generation in the valid-invokes PState — a check that prevents a delayed or duplicate retry signal from restarting an execution that has since recovered on its own. If the check passes, the topology increments the retry generation number in the valid-invokes PState, reinitializes the root PState entry for the new attempt, and schedules the first node again from scratch. Any events from the previous attempt — NodeComplete events that were in flight when the stall was detected, streaming chunks that had not yet been processed — will now arrive at the stream topology carrying the old, superseded generation number and will be discarded silently. The execution resumes from the beginning, with the same agent-id, as though it had just been initiated.

The Complete state is entered when the stream topology processes a NodeComplete event that carries a non-empty result value. A result represents a terminal output from the execution — the node that produced it declared it as the final answer, not merely as input to a downstream node. The stream topology writes the result to the root PState entry, marks the execution as complete, and removes the agent-id from the active-invokes set in the shared PState. The execution record remains in the root and node PStates — clients can still read it, the analytics topology can still process it against its cursor — but the execution is no longer live. The last-progress timestamp is updated one final time.

The GC-Marked state is entered when the garbage collection microbatch topology, running on its own tick schedule, identifies the completed execution as having passed its configured retention deadline. The topology moves the agent-id from the completed pool into the GC-marked set within the shared PState. The root and node PState entries for the execution remain fully intact at this point. The GC-marked set is a staging area, and entries are not deleted in the same pass that marks them. The two-phase approach ensures that any in-flight reads of the execution's data — from a client fetching a trace, from the analytics cursor processing the invocation — complete before the data is removed.

The Deleted state is the final state, entered in the GC pass subsequent to GC-Marking. The garbage collection topology reads the GC-marked set, removes the flagged entries from both the root PState and the node PState, and removes the corresponding entries from the GC-marked set. After this commit completes, all persistent state associated with the execution has been cleaned up. The execution no longer exists in any PState. Its record in the depots — the original events — remains there according to the depot's own retention configuration, but no derived state remains in the system. The storage footprint of that execution has been returned to the pool.


## Appendix E: The Analytics Pipeline, Step by Step

The journey of an invocation through the analytics pipeline begins before the analytics system touches it at all. It begins in the stream topology. When a node declares a final result and the stream topology processes the corresponding NodeComplete event, it writes the result, timing, and statistics to the root PState entry and simultaneously updates the node PState entry for that final node with its nested operations and finish timestamp. Alongside these writes, the stream topology removes the agent-id from the active-invokes set in the shared PState, marking the execution as complete. At this moment, the invocation has a complete and stable record in both the root PState and the node PState. It is no longer changing. It is now readable.

The analytics system does not react to this completion directly. There is no event telling the analytics topology that a specific invocation just finished. Instead, the analytics topology operates on a schedule: it wakes up when a tick fires from the analytics tick depot. When that tick fires, the analytics microbatch topology begins processing. On each task independently and in parallel, the topology reads the root PState forward from the position of the cursor — the invoke-id of the last invocation that was processed on that task for that rule. Everything recorded in the root PState after the cursor position represents invocations that have completed since the last analytics tick and have not yet been evaluated.

The topology works through these unprocessed invocations one by one within the batch. For each invocation, it begins by applying the rule's scope filter. A rule may be configured to apply to all agent types in the module, or it may be scoped to a specific agent by name. If this invocation belongs to an agent that the rule does not cover, the invocation is skipped immediately and the cursor advances past it. If the scope check passes, the topology checks the invocation's completion status: did it succeed, or did it error? Some rules are defined to evaluate only successful executions; others target only failures; others apply to both. A mismatch between the invocation's status and the rule's status scope causes the invocation to be skipped.

For invocations that pass the scope and status filters, the topology next evaluates the rule's sampling rate. If the rule is configured to evaluate only a fraction of matching invocations — say, one in ten — the topology applies a deterministic sampling function to the invocation's invoke-id to decide whether this particular invocation is in or out. This sampling is deterministic rather than random, meaning that the same invocation will always be in-sample or out-of-sample for a given rule, regardless of how many times the cursor is rewound and the batch is re-run. For invocations that are in-sample, the topology proceeds to evaluate the rule's conditions: structured filters on the invocation's input arguments, output value, metadata fields, and execution statistics. An invocation must satisfy all configured conditions to be considered a match. If any condition fails, the invocation is skipped.

For an invocation that passes all filters and conditions, the topology dispatches it to the rule's action function. The action receives the full context of the invocation: the input arguments passed to the agent, the output value it returned, the metadata it carried, the timing breakdown showing how long each node took, and any run-level information indicating which experiment configuration was active. The action does whatever it is configured to do: calling an LLM judge to evaluate output quality and storing the resulting score, adding the invocation to a dataset for later fine-tuning or evaluation, calling a webhook to notify an external system, or executing arbitrary custom logic registered by the developer. The analytics topology does not constrain what actions can do — it guarantees only that matching invocations reach the action exactly in the order they completed.

At the same time as rule evaluation, and in the same pass over the unprocessed invocations, the topology performs telemetry aggregation. For each invocation, it evaluates any metric definitions associated with the rule. A metric is defined by a value function: a function that accepts the invocation record and extracts a numerical value. Common metric value functions extract total wall-clock latency from invocation creation to completion, token counts summed across all model calls in the execution, binary success or failure indicators, or evaluator scores if an LLM judge has already run against this invocation. Each extracted value is fed into the T-Digest sketch in the telemetry PState keyed by the combination of agent name, metric identifier, and rule name. The T-Digest absorbs the new value by merging it into its compressed centroid representation, updating the sketch's approximation of the value distribution without storing the individual data point. The memory cost of this update is constant regardless of how many millions of previous values the sketch already represents.

After processing all invocations in the current batch — up to the configured maximum batch size — the topology commits. This commit is atomic. The cursor for each rule on each task advances to the invoke-id of the last invocation that was processed, the updated T-Digest sketches are written to the telemetry PState, any state produced by action functions is committed, and all of this happens together in a single microbatch commit. Either every change in the batch is durable and visible, or none of them are. If the topology fails mid-batch before committing — if a machine crashes, if the process is interrupted — Rama will restart the topology and rerun the batch from the cursor position it last committed to. Some invocations may be processed twice in this scenario, and the T-Digest may receive a value twice, but the error introduced by an occasional duplicate is negligible for statistical purposes and vastly simpler than the alternative of a true exactly-once guarantee.

After the commit, the cursor sits at a new, advanced position. Any invocations processed in this batch will not be processed again on the next analytics tick. They have been evaluated. Their metric values have been incorporated. Their cursor position has been passed. The next tick will advance the cursor further, processing whatever invocations completed between now and then.

The final leg of the pipeline is the query. The telemetry PState accumulates T-Digest sketches continuously, updated on every analytics tick, but that data is only useful when something reads it. When the monitoring UI requests analytics data — asking for the p50, p90, and p99 latency of a specific agent under a specific rule over a specific time window — it calls a query topology. The query topology is a synchronous, request-reply mechanism that runs on the task owning the relevant partition of the telemetry PState. The topology reads the T-Digest sketch for the requested combination of agent name, metric identifier, and rule name, and then evaluates the sketch to compute the requested percentiles. The T-Digest computes approximate percentiles by interpolating over its centroid representation, returning a result in constant time regardless of how many individual measurements have been accumulated. These approximate percentile values are returned to the query topology caller and from there to the UI, where they appear as the latency distribution charts in the analytics view.

The end-to-end path from NodeComplete to chart value touches the stream topology, the root PState, the node PState, the shared PState, the analytics tick depot, the analytics microbatch topology, the cursor PState, the telemetry PState, and the query topology in sequence. Each component has a single, well-defined responsibility. The stream topology records what happened. The analytics topology evaluates what it means. The cursor ensures each invocation is evaluated exactly once per rule. The T-Digest summarizes the distribution compactly. The query topology exposes the summary on demand. The pipeline is not a monolith but a chain of specialized components, each doing one thing, together turning the raw event of a completed execution into an observable data point in the monitoring system.
